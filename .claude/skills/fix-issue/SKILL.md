# Issue駆動の修正フロー（運用計画フェーズ4 ②〜⑥）

GitHub Issue を起点に、修正からPR作成までを自動で進める。
人間の関与は「起票（済み）・条件付き設計確認・PRマージ承認」のみ。

## 前提

- 引数はIssue番号（例: `/fix-issue 12`）。番号がなければユーザーに確認する
- 作業前に working tree が clean であることを確認する。汚れていたらユーザーに確認してから進める
- **複数のIssueがあっても並行処理せず、1件ずつ直列で対応する**（安全性重視の運用方針）。
  1件をPR作成まで進めてから次のIssueに着手する。同じファイル・同じ機能に触るIssue同士は、
  前のPRがマージされてから次に着手する（コンフリクト防止）

## 手順

### ② 影響範囲の分析・調査

1. `gh issue view <番号> --comments` でIssue本文とコメントを読む
2. 関連するコード・SPEC（`docs/SPEC-*.md`）を探索し、以下を整理する:
   - 修正対象のファイルと箇所
   - 依存関係（同じ文言・ロジックを参照する他の箇所、呼び出し元）
   - リスク（壊れうるもの、テーマ・RLS等の規約に触れるか）
3. Issueの記載が曖昧で修正内容を特定できない場合は、推測で進めずユーザーに質問する

### ③ 設計確認の分岐

CLAUDE.md「人間への設計確認が必要な変更」の基準（DBスキーマ変更・認証フロー変更・
破壊的API変更・セキュリティ関連・3ファイル以上のリファクタリング）に1つでも該当するなら、
**実装に着手する前に** AskUserQuestion で分析結果と設計案を提示し、承認を得る。
該当しなければ確認なしで④へ進む。

### ④ 修正＋検証

1. **現在のブランチが main であることを確認する**（`git branch --show-current`）。
   main 以外にいたら、別セッションの作業が残っている可能性がある——勝手に checkout せず
   ユーザーに状況を報告して指示を仰ぐ
2. main を最新化し（`git pull`）、ブランチ `fix/issue-<番号>-<短い英語slug>` を作成
3. 修正を実装する（Issueのスコープに限定。ついで修正はしない——気づきはIssue起票を提案）
4. `npm run typecheck` と `npm run lint` を実行し、エラーを解消する
5. UIに影響する変更はブラウザペインで実際に確認する
6. 認証・RLS・秘密情報に触れた場合は security-reviewer を必ず通す（自動フローでも省略しない）

### ⑤ 自己レビュー

新規コンテキスト（subagent）に diff とIssue内容を渡してレビューさせる。指示文には
「Issueの要求がすべて実装されているか、スコープ外の変更がないかを確認。
正しさと要件に関わるギャップのみ報告。スタイルの好みは報告しない」と明記する。
指摘があれば④に戻って修正し、再レビューする。

### ⑥ PR作成

1. **公開情報チェック**: コミット前に diff 全体を CLAUDE.md 規約「公開リポジトリ」の観点で確認する
   （秘密情報の実値・実メールアドレス・私的リポジトリ名・未公開作品の実タイトル/引用・
   インフラ識別子が含まれていないか。言及が必要なら既存の伏せ字表記を維持する）。
   dev-log 等への書き戻しを含むPRでは特に注意する
2. **コミット直前に現在のブランチを再確認する**（`git branch --show-current`）。
   ④で作ったブランチ以外（特に main）にいたら、そのままコミットせず状況をユーザーに報告する。
   ④の確認は**着手前**のものであって、そこからコミットまでの間にブランチが変わっていないことは
   保証しない——「ブランチを作った」と「ブランチにいる」は別の事実（INC-3）
3. `fix:` プレフィックスでコミットする。**`git commit` と `git push` を1コマンドに束ねない**
   （束ねると、コミット結果を確かめてから push を判断する機会が失われる）
4. `git push origin <ブランチ名>` で push する。**push 先のブランチ名を必ず明示する**——
   `git push` 単独は追跡ブランチへ押し込むため、main にいることに気づかないまま
   **リモート main への直接 push（＝本番自動デプロイ）が通り得る**。
   push 後、`git ls-remote --heads origin <ブランチ名>` とローカル HEAD の SHA が
   一致することを確認する
5. `gh pr create` でPRを作成する。本文に含めるもの:
   - 概要（何をなぜ直したか）
   - 影響範囲分析の要約（②の結果）
   - 変更点リスト
   - 検証結果（typecheck / lint / 動作確認の内容）
   - `Closes #<番号>`（マージでIssueが自動クローズされる）
6. PRのURLをユーザーに提示し、**マージ承認を依頼して終了する**

2〜4は dev-log・incident-log 等への書き戻しコミットでも同じように踏む
（INC-3 はその書き戻し中に、ブランチを作ったのにコミットが main 上に載った事象）。

## 禁止事項

- main への直接push・直接コミット（本番反映は必ず人間のPRマージ→Vercel自動デプロイ経由）
- PRの自分でのマージ
- Issueに書かれていない変更の混入
