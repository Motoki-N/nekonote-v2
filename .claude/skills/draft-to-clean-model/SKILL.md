# 草稿→浄書モデル（手帳→プロットモデル）のデータ設計思想

紙の手帳にアイデアを書き留め、後からプロットに落とし込んでいく体験の再現。第一期の失敗（カテゴリという「器」を先に決めさせて自由度を失い、Notionに流出）への直接の対策。

## 設計原則：構造はテキストとして持ち、システムが管理する構造を最小にする

1. **入力は白紙から**：ノートはフォーマット・カテゴリの事前指定なしのMarkdown。作成の手数を最小にする
2. **分類は後から**：タグは書いた後に付ける。カテゴリ横断・複数タグ可
3. **構造化はテンプレート挿入で**：「プロットに落とし込む」= 分類に応じたMarkdown雛形をノートに挿入すること。**DBスキーマの変換ではない**
4. **落とし込み後も自由**：テンプレート挿入後もノートはただのMarkdown。追記・逸脱が可能

## スキーマ上の帰結（重要）

- 中核は `notes`（Markdown生データ）＋ `tags`（多対多、`note_tags`）のみ
- **`characters` / `chapters` のような構造化テーブルは作らない**（第一期で作って失敗した）。キャラクター設定は「キャラクターテンプレートが挿入されたノート」として保持する
- `tags.kind` = `category`（キャラクター・世界観・あらすじ等）| `working_title`（仮タイトル＝作品の卵の名前）
- 仮タイトルタグによる絞り込みで「同じ作品候補に属するノート群」を一覧できる。プロジェクト確定前のノートはプロジェクトに属さず、仮タイトルタグで緩く束ねる
- 企画書（`proposals`）は「レポートの表紙」、紐づくノート群（`proposal_notes`）が「本文」。企画書がノートの内容をコピーして取り込むのではなく、参照で紐づける

## 実装時の判断基準

新しい情報を保存したくなったら、次の順で検討する：

1. まず「テンプレートを用意してノートに書いてもらう」で足りないか？（デフォルトの答え）
2. AIや画面が**確実に構造として参照する必要がある**データか？（例：シーンの並び順、シーンの感情の変化量、企画書のジャンル・ターゲット層）→ その項目だけカラム化する
3. それでも独立テーブルが必要と感じたら、この思想への逸脱としてユーザーに確認する

テンプレート自体もDBの固定スキーマではなくMarkdown雛形として管理する。
