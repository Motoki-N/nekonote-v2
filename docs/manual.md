## 1. ネコノテAIとは

小説をはじめとする長文の執筆を支援するWebアプリ。**作品そのものは人間が書き、AIはペルソナ（人格）を持つエージェントとして、構想のネタ出し・企画レビュー・構成設計・校正の各フェーズに伴走する**。原稿の実体はGitHubリポジトリに置き、アプリはレビューと進捗管理に専念する。執筆そのものも、縦書きエディタ（→ §8）でアプリ内から行える。

小説のほか、技術書などの解説書にも対応する（→ §5・§6）。

### 1.1 設計の考え方——「手帳→プロットモデル」

本アプリの中核にあるのは、**紙の手帳にアイデアを書き留め、後からプロットに落とし込んでいく**という執筆の体験をそのまま再現する、という考え方である。

- **入力は白紙から**: ノートは分類もフォーマットも決めずに書き始められる。「キャラクター設定を登録する」といった器を先に選ばされることはない
- **分類は後から**: 書いたあとにタグを付ける。1つのノートに複数のタグを付けてよいし、後から付け替えてもよい
- **落とし込みはテンプレート挿入で**: 「プロットに落とし込む」とは、キャラクターやテーマの雛形をノートに差し込むこと。データベースの構造が変わるわけではない
- **落とし込んだ後も自由**: 雛形を入れた後もノートはただの文章のまま。項目を足しても、雛形から逸脱しても構わない

この結果、アプリの側は「キャラクター表」「章立て表」のような固定の入力フォームを持たない。持っているのは**ノートとタグ、そしてそれを束ねる企画書**だけである。企画書はレポートの表紙にあたり、紐づけたノート群がその本文になる。AIにレビューを頼むと、この「表紙＋本文」がひとまとめで渡される。

構成設計（ビートボード・目次ボード）と原稿だけは例外的に構造を持つ。並び順や転換点、感情の起伏は、AIと画面が構造として読む必要があるためである。

### 1.2 執筆フェーズと画面の対応

| フェーズ | 使う画面 | 主に関わるAI |
|---|---|---|
| 構想（ネタ集め） | ノート | アシスタント（掘り下げ） |
| 企画 | プロジェクト / 企画書 | 担当編集・技術書編集者（レビューゲート・キャラクターレビュー） |
| 構成設計 | ビートボード / 目次ボード | 担当編集・技術書編集者（構成・シーンレビュー） |
| 執筆・組版・入稿 | エディタタブ（縦書きエディタ） | 校正さん（選択範囲の校正のみ） |
| 推敲・レビュー | 原稿タブ | 校正さん（校正）、読者代表・エンジニア読者（講評）、書店員（売り込み分析・あらすじ・キャッチコピー） |
| イラスト | アトリエ | イラストレーター（表紙・挿絵・キャラクター・コンセプトアート） |
| 記事執筆 | Zenn | —（AIなし） |
| 進捗管理・雑談 | ダッシュボード | アシスタント（スケジュール）、喫茶店のマスター（壁打ち） |

### 1.3 標準ペルソナ9人

- **アシスタント**（対話型）: ネタの掘り下げ・整理・スケジュール相談の相手
- **喫茶店のマスター**（対話型）: 漠然とした構想の壁打ち相手。締めにメモをまとめてくれる
- **担当編集**（レビュー型）: 企画書・キャラクター・構成・シーンをレビューする
- **校正さん**（レビュー型）: 原稿の誤字脱字・表記揺れを機械的にチェックする
- **読者代表**（レビュー型）: ターゲット層になりきった主観的感想を賛否両論で返す（辛辣なこともある）
- **近所の書店員**（レビュー型）: 作家のサポーターとして「どう売り込むか」を分析する。あらすじ・キャッチコピーの作成も担当
- **イラストレーター**（イラスト型）: 企画書・原稿を読んで作画案を2〜3案提案し、画像生成モデルでイラストを描く（→ §9）
- **技術書編集者**（レビュー型・技術書向け）: 対象読者の定義・前提知識の積み上げ・用語の一貫性を重点的に見る
- **エンジニア読者**（レビュー型・技術書向け）: 想定読者になりきり、どこで詰まったか・何ができるようになったかを実感ベースで返す

技術書向けの2人は、執筆ジャンルが「技術書」のプロジェクトで自動的に既定として選ばれる。

### 1.4 レビュープロファイル13種（観点のプリセット）

企画書レビュー / キャラクターレビュー / 構成レビュー / シーンレビュー / 校正・校閲 / 読者講評 / 売り込み分析 / あらすじ作成 / キャッチコピー作成 ／（技術書向け）技術書企画書レビュー / 技術書構成レビュー / 技術書講評 / 技術書校正。

レビュー実行時に「プロファイル（観点）＋担当ペルソナ＋対象」の組で呼び出す。標準のプロファイル・ペルソナは読み取り専用で、「複製して編集」で自分好みに調整できる（→ §12）。

いずれのAIも**本文を書く係ではない**。本アプリがAIをどう使い、どう使わないか——コンテスト応募時のAI利用の開示を含めて——は §14 にまとめている。

## 2. ログイン

- `/login` から **Googleでログイン**。許可リストに載ったアカウントのみサインインできる
- セッションが切れた状態で編集していた内容はブラウザ内に退避され、再ログイン後に復元を提案される（書きかけの消失防止）
- テーマ（ライト/ダーク）はヘッダーのトグルで切替
- ヘッダーのグローバルナビから **プロジェクト / ノート / アトリエ / 相談 / Zenn** へ移動できる。ロゴをクリックするとダッシュボードへ戻る

## 3. ダッシュボード

トップページ（`/`）は「作業基地」。以下が並ぶ:

- **プロジェクト概況カード**（進行中プロジェクトごと）:
  - 企画書ステータスバッジ（draft / in_review / approved）・締切カウントダウン
  - 最新の総文字数と**直近30日の文字数推移の折れ線**
  - **「今すぐ集計」ボタン**: GitHubの原稿から当日の総文字数を集計して記録する（repo/PAT設定済みのプロジェクトのみ表示）。進捗記録は原稿タブを開いたときにも自動で走る
  - **執筆スケジュールブロック**（アシスタントとの相談で確定保存した場合のみ表示）: 1日あたり目標字数・マイルストーン一覧（チェックボックスで手動達成、目標字数があれば実文字数との比較で自動達成）。ゴミ箱アイコンで削除
  - 企画書・構成ボード・原稿タブへの導線
- **「相談する」ボタン**: 相談パネルを開く（→ §10）
- **「アトリエ」ボタン**: イラスト生成ページを開く（→ §9）

### 締切リマインドメール

マイルストーンに締切を設定しておくと、**締切の3日前と前日**に、未達成のものだけメールで通知される（1日1回の自動チェック）。達成済みにチェックを入れたマイルストーン、目標字数に到達したマイルストーンは通知されない。

## 4. ノート（構想メモ）

`/notes`。「紙の手帳」に相当する。**入力は白紙から・分類は後から**が思想（→ §1.1）。

[SCREENSHOT: ノート一覧。タグ絞り込みとカードが並んだ状態]

### 基本操作

- **作成**: 一覧の新規作成ボタン1クリックで空ノートが開く
- **エディタ**: Notion風のWYSIWYG。見出し（H1〜H3）・リスト・太字/斜体・リンク・引用・区切り線に加えて、**表・画像・コードブロック・ファイル添付**が使える（保存はMarkdown）
  - 画像・ファイルはツールバーのボタンから添付する。png / jpg / webp / gif / pdf / txt・**10MBまで**。画像は本文に埋め込まれ、それ以外はリンクとして挿入される
- **自動保存**: 入力停止後数秒で自動保存（保存状態は常時表示）。オフライン時はローカル退避→復帰時に復元提案
- **Undo/Redo**: Cmd/Ctrl+Z・Shift+Cmd/Ctrl+Z。保存タイミングをまたいで遡れる
- **並び順**: 一覧のソートメニューで「更新が新しい/古い順・作成が新しい/古い順」を切り替えられる
- **一括エクスポート**: 一覧のエクスポートボタンで、ごみ箱以外の全ノートを **1ノート＝1つの `.md` ファイル**（タグ・作成日時のフロントマター付き）にまとめたZIPをダウンロードできる

### バージョン履歴

- エディタの「バージョン履歴」ボタンでパネルを開く。自動保存のたびに版が増えるのではなく、**10分間隔に間引いて**上書き前の内容が記録される
- 版を選んで「この版に復元」できる。復元の直前に現在の内容も新しい版として保存されるため、復元自体をやり直せる

### タグ

- タグ入力欄から既存タグを選択、なければその場で新規作成
- 種類は2つ: **category**（コンセプト・キャラクター等の分類）と **working_title**（仮タイトル＝作品の卵の名前）
- 仮タイトルタグで「同じ作品候補のノート群」を束ね、一覧で絞り込める（複数タグはAND）
- **編集・削除・統合**: 一覧のタグチップ横の鉛筆ボタンで「タグを編集」を開く。名前を書き換えて保存すれば改名でき、同じ種類の既存タグと同じ名前にすると**そのタグへ統合**される（付いていたノートは統合先に付け替わる）。ゴミ箱ボタンでタグ自体を削除できる（ノートは残る）。統合・削除は元に戻せないため確認が出る

### テンプレート挿入（プロットに落とし込む）

- 挿入メニューからテンプレート（コンセプト / キャラクター / テーマ / 世界観）を選ぶと、カーソル位置に雛形が挿入され、対応するcategoryタグが自動付与される
- 挿入後もただのMarkdown。追記・逸脱は自由（構造は強制されない）

### AI掘り下げ（アシスタント）

- エディタの「掘り下げ」ボタンでパネルを開く（デスクトップ=右サイド、スマホ=ボトムシート）
- ノートの内容（編集途中の未保存分も含む）を踏まえて、要約と深掘り質問でネタを膨らませてくれる
- 会話はノートごとに1スレッドが保存される。応答の「ノートに挿入」でカーソル位置に取り込める（1回のUndoで取り消し可）
- 「会話をリセット」で仕切り直し

[SCREENSHOT: ノートエディタ＋掘り下げパネルを開いた状態]

### ごみ箱

- 削除はごみ箱への移動（トーストの「元に戻す」で即復元）。ごみ箱ビューから復元・完全削除できる。自動パージはしない

## 5. プロジェクトと企画書

`/projects`。書き上げる本ごとにプロジェクトを作る。

### プロジェクト作成

- タイトル（必須）、**執筆ジャンル**（小説 / 技術書 / その他。既定は小説）、イベント名・締切・目標ページ数（任意）
- 執筆ジャンルによって、企画書の初期テンプレートと構成設計の画面（→ §6）、レビューの既定ペルソナが変わる
- **仮タイトルタグを選ぶと**、そのタグの付いたノート群が候補表示され、チェックした分が企画書に一括紐づけされる
- 作成と同時に企画書が1つ自動作成される（1プロジェクト1企画書）
- 原稿連携する場合はプロジェクト編集で **repo**（`owner/repo` 形式）と **base_path**（リポジトリ内のフォルダ）を設定する（→ §7）。repo を初めて設定して保存すると、新規リポジトリ向けの**初期セットアップ**（テンプレート展開）が提案される（→ §8）
- プロジェクト配下は **企画書 / 構成ボード / 原稿 / エディタ / レビュー履歴** の5タブ構成（構成ボードのタブ名は執筆ジャンルで「ビートボード」「目次」と変わる）

[SCREENSHOT: プロジェクト一覧とプロジェクト作成ダイアログ]

### 企画書エディタ（`/projects/[id]`）

- メタ情報は4フィールド: **執筆ジャンル**（小説 / 技術書 / その他・後から変更可）・**執筆目的**（例:「技術書典で頒布する」「商業出版を目指す」）・**内容ジャンル**（ファンタジー、Webフロントエンド等の自由記述）・**ターゲット層**
- 本文エディタはノートと同じ記法・自動保存。初期本文にはジャンル別の見出しテンプレが入っている（小説＝コンセプト / キャラクター / テーマ、技術書＝テーマ / 参加イベント / ターゲット読者 / 本のゴール、その他＝白紙）
- 執筆ジャンルを後から変えても**本文は書き換わらない**（テンプレートの再適用はしない）
- **紐づけノート**: 検索して個別追加・解除もできる。紐づけたノートはレビューの材料としてAIに渡る（企画書＝表紙・ノート＝本文の関係）
- **バージョン履歴**: ヘッダーの履歴ボタンから。10分間隔に間引いたスナップショットに加えて、**レビュー実行時には必ず1版残る**。版を選ぶと「その版 → 次の版（最新は現在の本文）」の差分が表示され、レビュー反復ごとの改稿を追える。「この版に復元」も可能

[SCREENSHOT: 企画書エディタ。4フィールドと本文、紐づけノートが見える状態]

### 企画書レビュー（レビューゲート）

- 「レビュー」ボタン→パネルで「レビューを受ける」→ 担当編集（技術書なら技術書編集者）のフィードバック文書がストリーミング表示される
- フィードバック末尾に**判定バッジ（承認 / 差し戻し）**が付く
- 指摘を受けて企画書を改稿し、**返答メモ**（改稿の意図や反論）を書いて再レビュー→前回指摘の改善を見てもらえる、の反復
- 判定が「承認」になると**「企画を通す」ボタン**が出る→確定で status が approved に。承認後の編集でステータスは変わらない（ゲートは演出。再審査したければ新しいレビューを回す）
- フィードバックは「**ノートに転記**」でノート化できる（指摘を手元に残して改稿の材料にする用途）
- パネルのプロファイルセレクタで複製プロファイルに切替可能。プロファイルごとにセッション（履歴）が並存する。担当ペルソナは新規セッション開始時のみ変更できる

[SCREENSHOT: 企画書レビューパネル。判定バッジ付きのフィードバックが表示された状態]

### キャラクターレビュー

- 企画書画面の「キャラクター」ボタンから（「レビュー」パネルとは排他表示）
- 企画書＋紐づけノート一式を材料に、5つの問い（誰が・何を・なぜ・失敗の代償・どう変わるか）でキャラクター設計をレビューする
- 合否判定はなし。企画書ステータスとも無関係（approved 後のキャラブレ点検にも使える）。紐づけノート0件でも実行でき、資料不足はそのまま指摘される

### レビュー履歴タブ

`/projects/[id]/reviews`。そのプロジェクトで実行した**全フェーズのレビュー**（企画書・構成・シーン・キャラクター・講評）を作成日時の降順で一覧できる。

- 各行にフェーズバッジ・プロファイル名・ペルソナ名・ステータス（実施中 / 完了 / 失敗）・フィードバック回数・最新判定・日時が並ぶ
- 行を開くとレビューの往復（第N回のフィードバック本文・判定・返答メモ）を読み取り専用で表示。**コピー**ボタンで本文をクリップボードへ
- 「企画を通す」で完了したセッションも、ここからならいつでも読み返せる

## 6. 構成設計（ビートボード / 目次ボード）

`/projects/[id]/board`（プロジェクトのタブから）。**執筆ジャンルによって画面が変わる**。

- **小説** → ビートボード（付箋を並べる構成設計。§6.1）
- **技術書 / その他** → 目次ボード（章を並べる目次づくり。§6.2）

ジャンルを切り替えても、もう一方のボードのカードは消えない（表示されなくなるだけで、戻せば元の順序のまま残っている）。

### 6.1 ビートボード（小説）

[SCREENSHOT: ビートボード全景。4レーンにシーンカードが並び、下部に感情の折れ線が見える状態]

#### 構成テンプレート6種

ボードヘッダーのセレクトで、構成の手法を選べる。既定は4部構成。

| テンプレート | レーン |
|---|---|
| **4部構成**（既定） | 設定 / 反応 / 攻撃 / 解決 |
| **三幕構成** | 第一幕（発端） / 第二幕 前半（葛藤） / 第二幕 後半（葛藤） / 第三幕（結末） |
| **ストラクチャー式** | リアクション1 / リアクション2 / アクション1 / アクション2 |
| **Save The Cat式** | パート1 〜 パート4 |
| **ヒーローズジャーニー式** | 別離 / 試練への降下 / イニシエーション / 帰還 |
| **ストーリー解剖学式** | パート1 〜 パート4 |

- テンプレートごとに転換点（プロットポイント・ミッドポイント・きっかけ・クライマックス等）の語彙とレーン配置が定義されている
- **切り替えはいつでも可能**。確認ダイアログののち、全シーンが新テンプレートの先頭レーンへ集約され、転換点マークは解除される。タイトル・本文・感情・ノート紐づけ・原稿紐づけは保持される（構成の承認状態はリセットされる）

#### シーンカード

- 「＋シーンを追加」でカード作成 → 編集ダイアログが開く
- ダイアログの項目: タイトル・本文・感情の変化・パート（レーン）・転換点アンカー・**紐づけノート**・**紐づけ原稿ファイル**
  - 本文には新規作成時に4観点（シチュエーション / 起きること / 感情の変化 / 葛藤）の見出しが初期値として入る。不要なら消してよい
  - 紐づけた原稿ファイルは「エディタで開く」リンクから直接開ける
  - **保存ボタンはない**。閉じる操作（×・ESC・外側クリック）で変更があれば保存される
  - ダイアログ下部の「前のシーン」「次のシーン」でカードを渡り歩ける
- **D&D**: レーン内並び替え・レーン間移動（移動でパートも変わる）。タッチは長押しでドラッグ
- カード削除は確認ダイアログ→即削除（ごみ箱なし。短文メモなので再作成コストが低い）

#### 転換点アンカー

- **境界の転換点**（4部構成なら PP1 / ミッドポイント / PP2）はレーン末尾の定位置スロットに固定表示される。未設定のスロットは薄いプレースホルダーで「まだ決まっていない転換点」が見える
- それ以外の転換点（ピンチポイント等）はバッジ付きの通常カードとしてレーン内自由。ただし**転換点同士の相対順**はテンプレート定義の順序に従う必要があり、逆順になるドロップは差し戻される
- 1転換点1シーン。他のシーンに付いているアンカーを選ぶと付け替えになる。パートを変えると境界アンカーは自動解除

#### 感情の起伏

- シーンごとに設定するのは「そのシーンを通して感情がどれだけ動いたか」の**変化量**（-9〜+9。0=変化なし）。始点・終点を別々に持たないので、シーンを並べ替えても前後との辻褄合わせが要らない
- カードには変化量のバッジ（増減の向きをアイコンで表示）、ボード下部には構成順に変化量を積み上げた**到達値**の折れ線が表示される。折れ線は0から始まり、上下限は -9〜+9
- 感情が上下限に達していて変化量を反映しきれないシーンは、カードのバッジ・編集ダイアログの感情欄・折れ線の点が**赤字**になる。前のシーンの変化量を見直す合図

#### 構成レビュー / シーンレビュー

- **構成レビュー**: ボードヘッダーから。全シーン＋企画書を材料に、**採用中のテンプレートの観点で**レビューされる（AIには現在のレーン構成と転換点の一覧が渡る）
- **シーンレビュー**: カードから起動。対象シーン＋全体の流れ＋企画書を材料に4観点（シチュエーション / 出来事 / 感情の変化 / 葛藤）でレビュー
- どちらも企画書レビューと同じ**反復型のゲート**。フィードバック末尾に判定バッジ（承認 / 差し戻し）が付き、返答メモを書いて再レビューを繰り返す。承認が出ると「**構成を通す**」「**シーンを通す**」ボタンが現れ、確定でボードに承認バッジが付く
- 構成レビューのフィードバックは「**ノートに転記**」でノート化できる

### 6.2 目次ボード（技術書・その他）

解説書の構成設計は「どういう内容をどの順番で書くか＝目次を組み立てる」ことなので、小説のような転換点・感情の構造は持たない。

[SCREENSHOT: 目次ボード。章カードが縦一列に並んだ状態]

- **章カードの縦1列**（階層なしのフラットな並び）。D&Dで並び替え
- 章カードの項目はタイトル・内容メモ・紐づけ原稿ファイルのみ
- **定番構成テンプレ3種**を同梱。空のボードではカード型で提示され、カードがある状態でも「定番構成から追加」メニューから末尾に一括追加できる

## 7. 原稿と校正・講評

`/projects/[id]/manuscript`（原稿タブ）。原稿の実体はGitHubリポジトリ、ネコノテは「AIによる差分レビューの場」。

### 前提設定（初回のみ）

1. `/settings` で **GitHub Fine-grained PAT** を登録（対象リポジトリ限定・Contents: Read/Write。→ §12）
2. プロジェクト編集で **repo / base_path** を設定（新規リポジトリの場合は repo の初回設定時に初期セットアップが提案される → §8）

### 原稿の閲覧

- base_path 配下の `.md` / `.txt` がファイル一覧に出る。開くと本文が読み込み専用で表示される（この画面では編集しない。執筆はエディタタブ →§8、または普段のエディタで）
- ファイル表示ヘッダの「**エディタで開く**」リンクで、同じ章を縦書きエディタで開ける（相互リンク）
- 前回の校正以降に原稿が更新されていると「原稿が更新されています」バナーが出る
- ファイルを開くと当日の総文字数が進捗として自動記録される（ダッシュボードのグラフの元データ）

[SCREENSHOT: 原稿タブ。ファイル一覧と本文、右側に校正パネル]

### コミット履歴と差分（履歴パネル）

ファイルを開いているときにヘッダーの「**履歴**」ボタンから開く。GitHubへ見に行かずに、校正コミットやエディタでの保存の結果をアプリ内で確認できる。

- 開いているファイルの**最新30件**のコミットを新しい順に表示（メッセージ・日時・短縮SHA）
- コミットを選ぶと、そのコミットでの変更内容（親コミットとの差分）が展開される。**行単位の色分けに加えて、行内の変わった文字だけを強調**するため、段落の中の一字修正も見つけられる
- 差分が大きすぎるコミットは「差分を表示できません」と表示される
- 校正パネル・講評パネルとは排他表示（同時に開くのは1つ）

### AI校正（校正さん）

- 原稿ビューの「校正を受ける」→ その時点の最新原稿に対して実行→ **提案カード**（原文抜粋 / 修正案 / 理由）が逐次表示される
- 各カードを **受入 / 拒否 / 保留** で処理する。原稿が更新されて原文が見つからなくなった提案は「適用不能」表示になる（安全弁）
- **「確定分をコミット」**: 受入済みの提案をまとめて適用し、1コミットでGitHubへ書き戻す
- **「保留をコメントで書き戻す」**: 保留中の提案をファイル単位で一括して、原稿の該当箇所の直前に `<!-- [ネコノテ校正・保留] … -->` コメントとして1コミットで書き戻す。書き戻した提案には「コメント書き戻し済み」バッジが付き、以後の消化（採否の判断・コメント削除）は縦書きエディタのコメント一覧で行う（→ §8）。コメントはプレビュー・入稿PDFには一切現れない
- 再校正すると未処理（pending）の提案は新しい提案に置き換わる。**保留はコミット後も残り**、後から受入/拒否できる
- 執筆中に「いま書いた範囲だけ」を校正したい場合は、縦書きエディタの**選択範囲校正**を使う（→ §8）

### 講評（読者代表・書店員）

- 原稿タブヘッダーの「講評」ボタン→ プロファイル（読者講評 / 売り込み分析 / あらすじ作成 / キャッチコピー作成。技術書プロジェクトでは技術書講評）とペルソナを選んで実行
- base_path 配下の**全原稿ファイルを結合した「作品全体」**への講評が返る。読み切り型で、履歴が一覧に残る（反復・返答メモなし）
- 各講評の「**レビューメモへ書き戻す**」ボタンで、講評全文を原稿リポジトリの専用メモファイル `manuscripts/00-review-notes.md` へ `<!-- -->` コメントとして追記コミットできる。このファイルは本文の章立て（entry）に載らないため、本・入稿PDFには一切出ない。縦書きエディタの章一覧の末尾（「entry未登録」印つき）から開いて読める
- 読者講評と書店員担当のプロファイル（売り込み分析・あらすじ作成・キャッチコピー作成）は、企画書の内容ジャンル・ターゲット層が未設定だと実行できない（なりきり先・売り込み先がないため）。15万字超は実行前確認、30万字超は実行不可

## 8. 縦書きエディタ（執筆・組版・入稿PDF）

`/projects/[id]/editor`（プロジェクトのタブから）。**横書きで書いて、縦書きで確認し、印刷所に出せる入稿PDFまで作る**エディタ。原稿の実体は原稿タブと同じGitHubリポジトリで、保存のたびにコミットが作られる（アプリのDBには原稿を置かない）。

[SCREENSHOT: 縦書きエディタ。左に横書き入力ペイン、右に縦書きプレビュー]

### 前提

- §7 と同じ **PAT（Contents: Read/Write）＋ repo / base_path** の設定
- 原稿リポジトリがテンプレート構成（`manuscripts/` 配下の章ファイル・`book.config.js`・`themes/`・入稿ビルド用 GitHub Actions。雛形は本リポジトリの `docs/templates/manuscript-repo/`）に従っていること
- 原稿フォーマットは **VFM**（Vivliostyle Flavored Markdown）。ルビは `{漢字|かんじ}`、メモはHTMLコメント `<!-- -->`

### 新しい原稿リポジトリを作る（作品の新規開始時）

作品ごとに1リポジトリ。**アプリ内の初期セットアップ**で作るのが基本（ローカルにGit環境がなくてもよい）。

#### アプリ内セットアップ（推奨）

1. **GitHubでリポジトリを新規作成**: プライベートで作る（空でも README 付きでもよい）。リポジトリ名はローマ字ケバブケース（例: `ryu-no-su`）
2. **PATの対象に追加**: `/settings` の Fine-grained PAT の対象リポジトリに新リポジトリを追加する（権限は Contents ＋ Workflows の Read and write。→ §12）
3. **プロジェクト編集で repo を設定**: 保存すると「原稿リポジトリの初期セットアップ」ダイアログが開く（repo を未設定→設定にしたときだけ）
4. **作品情報を入力して実行**: 作品タイトル・著者名・出力ファイル名（入稿PDF等の名前）を入力すると、テンプレート一式が作品情報に置換されて**1コミットで展開**される
   - リポジトリに既にファイルがある場合は、全ファイルが `backup-<日時>/` へ退避されてから展開される
   - 完了時に base_path は空（リポジトリルート）に自動設定される
5. **動作確認**: エディタタブで章一覧が entry 順に表示されればOK。入稿ビルド用の GitHub Actions も展開済みで、そのまま動く

#### 手動セットアップ（ローカルGitで作る場合）

テンプレート（本リポジトリの `docs/templates/manuscript-repo/`）を手元でコピーして作る従来の手順。

1. **テンプレートをコピー**: `docs/templates/manuscript-repo/` を作業フォルダへコピーする。フォルダ名＝リポジトリ名（ローマ字ケバブケース。例: `ryu-no-su`）
2. **作品情報を書き換え**: 次のファイルに残っているサンプルのタイトル（`竜の巣`）・出力ファイル名（`ryu-no-su`）・著者名を作品用に置換する
   - `book.config.js` / `book.config.b6.js` / `book.config.epub.js` … 書誌情報と出力ファイル名
   - `package.json` … name と `check:pages` の出力パス
   - `.github/workflows/build-pdf.yml` / `build-epub.yml` … 出力ファイル名
   - `manuscripts/00-tobira.md`（扉）・`99-okuzuke.md`（奥付）
3. **挿絵の管理設定**: テンプレートの `images/.gitignore` は検証用に画像を除外しているので削除する（実作品では挿絵をGit管理する。リポジトリが太ってきたら Git LFS へ移行）
4. **GitHubへ**: プライベートリポジトリを作成して push する

   ```bash
   git init -b main && git add -A && git commit -m "原稿リポジトリを初期作成"
   gh repo create <リポジトリ名> --private --source=. --push
   ```

5. **ネコノテと接続**: `/settings` の Fine-grained PAT の対象リポジトリに新リポジトリを追加し（→ §12）、プロジェクト編集で **repo / base_path** を設定する（テンプレート構成なら base_path は**空欄のまま**にする＝リポジトリルート。`manuscripts` を設定すると縦書きエディタの章一覧が表示されない）
6. **動作確認**: エディタタブで章一覧が entry 順に表示され、保存するとコミットが作られればOK。入稿ビルド（→ 入稿ビルドの節）は push 済みの Actions がそのまま動く

### 画面構成

- **章一覧サイドバー**: `book.config.js` の entry 順に章ファイルを表示（折りたたみ可）。entry未登録のファイルは末尾に印つきで表示。未保存の待避がある章にはインジケータが付く。「新規章ファイルの作成」もここから（雛形入りで作成＝コミット。entryへも自動追記される）
- **入力ペイン（横書き）**: プレーンテキストエディタ。ルビ・コメント・見出しがハイライトされる
- **プレビューペイン（縦書き）**: 実際の判型どおりのページ分割・ノンブル込みで表示される。入力停止後数秒（デバウンス）で再組版。プレビューと入稿PDFは同じ組版エンジン（Vivliostyle）なので、見た目がズレない
- デスクトップは左右2ペイン（比率ドラッグ可変・プレビュー折りたたみ可）。スマホは崩れない最低限の表示のみ
- プレビューの既定は**編集中の章のみ**（高速）。**全体プレビュー**は明示操作で、全章を通したページ分割・ノンブルを確認できる（目次ページだけは入稿ビルドでのみ生成される。UI上にも注記あり）

### 執筆と保存（保存＝コミット）

- `Cmd/Ctrl+S` または保存ボタン → コミットメッセージを確認・編集 → コミット。コミット先は章一覧サイドバー上部のセレクタで選んでいるブランチ（既定はデフォルトブランチ。切替・作成・PR作成もこのセレクタから）
- 未保存の編集はブラウザ（IndexedDB）へ自動待避され、リロード・クラッシュしても失われない。章を開き直すと「未保存の編集があります」バナーで復元/破棄を選べる
- 他所（VS Code等）からのpushと競合した場合は「原稿がリモートで更新されています」→ **マージビュー**（左=リモート最新・右=ローカル編集）でチャンク単位に取り込んで再保存する。自動マージはしない

### ツールバー（入力補助）

記法を知らなくても使えるボタン群。挿入結果はすべて素のVFMテキスト。

- **ルビ**: 選択→ボタン→読みを入力→ `{選択文字|読み}` に置換
- **傍点・縦中横**: 選択→ボタンでクラス指定記法に置換（縦中横は2〜3桁の半角英数向け）
- **コメント**（`Cmd/Ctrl+/`）: 選択範囲を `<!-- -->` で包む（未選択なら空コメントを挿入）。没にした文章の保留にも使える
- **画像**: ボタンまたは入力ペインへの**ドラッグ&ドロップ**で、`images/` へ即コミット＋カーソル位置に挿入記法を追記（本文中カット / 全面挿絵を選択）。png / jpg / jpeg / webp / gif・10MBまで
- **字数カウント**: 本文のみを数える（コメント・フロントマター・記法・ルビの読みは除外）。「約◯ページ」の見積り付きで、プレビュー完了後は実ページ数を表示

### 選択範囲の校正

執筆中に「いま書いた範囲だけ」を校正さんに見てもらえる。章全体を投げ直さないので速く、コストも小さい。

- 校正パネルを開いた状態で、入力ペインで**10文字以上を選択**すると「**選択範囲を校正（N字）**」ボタンが出る
- 返ってきた提案の扱い（受入 / 拒否 / 保留・確定分のコミット・保留の書き戻し）は全文校正とまったく同じ
- 範囲外の未処理の提案は消えずに残る（置き換わるのは選択範囲内の提案だけ）
- 未保存の編集があるときは実行できない。先に保存する

### コメント一覧

- 編集中の章の `<!-- -->` コメントを出現順に一覧表示。クリックで該当行へジャンプ
- コメントはプレビューにも入稿PDFにも**一切現れない**（構成メモ・没文の保留・校正の書き戻し置き場として安全）

### 書籍設定フォーム

ヘッダーの「書籍設定」から。実体はリポジトリ内のファイルで、フォームは該当箇所だけを書き換えて**差分プレビュー→コミット**する。

1. **書誌情報**: `book.config.js` のタイトル・著者
2. **章順（entry管理）**: 並べ替え・entry未登録章の取り込み・除外
3. **組み設定**: 行数・字詰め・行送り・フォントサイズ（判型タブで文庫A6 / B6を切替編集）
4. **奥付**: 発行日・著者・発行・連絡先・印刷の各フィールド（テンプレート構造が検出できた場合のみ）

フォームが対応できない構造のファイルは読み取り専用になり、VS Code等での直接編集が案内される（壊れた書き換えはしない）。

### 入稿ビルド（PDF / EPUB の書き出し）

- ヘッダーの「入稿ビルド」→ **種別（入稿PDF / EPUB）**とタグ名を確認して実行 → GitHub Actions がファイルを生成し、同タグのGitHub Releasesに添付する
  - **入稿PDF**（タグは `v*-nyuko` 形式）: 印刷所提出品質のPDF（PDF/X-1a・フォント埋め込み・ノンブル・目次・奥付込み）
  - **EPUB**（タグは `v*-epub` 形式）: 電子書籍配布用のEPUB
  - タグ名は自動提案される
- 完了は自動で検知され（30秒間隔のポーリング・最長15分）、UIにダウンロードリンクが出る。タイムアウト時はActionsページへのリンクが案内される
- 入稿PDFのビルド時には総ページ数（4の倍数チェック）や画像の解像度・カラー混入も検査される
- 「どのコミットを入稿したか」がタグとしてGitに残る

[SCREENSHOT: 入稿ビルドダイアログ。種別選択とタグ名の入力]

### 青空文庫形式の書き出し（投稿サイトへの転載）

カクヨム・小説家になろう等へ転載するために、**開いている章**を青空文庫形式のプレーンテキストへ変換して取り出せる。原稿には一切手を加えない、読み取り専用の書き出しである。

- ツールバー右側の「**書き出し**」ボタンからダイアログを開く
- **書き出し先サイトを選ぶ**（青空文庫 / カクヨム / 小説家になろう。既定は青空文庫）と、その記法に合わせて変換結果が変わる
  - ルビは3サイト共通で `｜親文字《よみ》`
  - 傍点はカクヨムなら `《《…》》`、なろうなら中黒ルビで代用、青空文庫なら `［＃「…」に傍点］`
  - 縦中横・改ページ・割注の注記は、解釈しないサイト向けには自動的に外れる
- コメント・フロントマター・画像記法は出力に含まれない
- ルビの文字数上限（カクヨム: 親文字20字・ルビ50字 ／ なろう: 各10字）を超えるルビがあると、ダイアログに警告として列挙される
- 変換されるのは**いまエディタに見えている内容**（未保存の編集も含む）。「クリップボードにコピー」と「.txt をダウンロード」の両方が使える

### ネコノテ連携（相互リンク）

- ヘッダーの「**レビュー**」→ 編集中の章を開いたまま原稿タブ（校正・講評）へ。原稿タブの「**エディタで開く**」で戻ってくる
- 校正の保留提案・講評は、§7 の書き戻し機能で `<!-- -->` コメントとして原稿に持ち帰れる。書き戻されたコメントはこのエディタのコメント一覧に載り、執筆→レビュー→推敲のループがアプリ内で一周する

## 9. アトリエ（イラスト生成）

`/atelier`（ヘッダーのナビ、またはダッシュボードの「アトリエ」ボタンから）。ペルソナ「**イラストレーター**」に、プロジェクトの資料を踏まえたイラストを依頼する。生成対象は4種:

- **表紙イラスト**
- **文中の挿絵**（原稿の指定シーンに合わせて描く）
- **キャラクターイラスト**（キャラクター設定資料に載せる想定）
- **コンセプトアート**（世界観を表すイラスト）

ページ上部のプロジェクトセレクタで対象プロジェクトを選ぶ。イラストレーターは種別に応じた資料（表紙・コンセプトアート=企画書一式＋原稿全文、キャラクター=企画書一式、挿絵=選択した原稿ファイル＋場面の補足）を自動で読み込む。

[SCREENSHOT: アトリエ。依頼フォームと生成済みイラストのギャラリー]

### 依頼の流れ（2段階）

1. **依頼フォーム**: 種別・カラー/モノクロ・アスペクト比（種別ごとのデフォルトあり: 表紙/挿絵/キャラクター=縦2:3、コンセプトアート=横16:9。縦/横/正方形から変更可）・描いてほしい対象/構図/雰囲気（自由記述）を入力。挿絵の場合は原稿ファイルを選び「どの場面か」を補足する
2. **「案を出してもらう」**: イラストレーターが資料を読んで**2〜3案**（タイトル・狙いの説明・画像生成プロンプト）を提案する
3. **案を選んで生成**: 案を選択し、プロンプトを微調整してから「**この内容で描いてもらう**」。生成は10〜30秒程度。完成した画像はギャラリーに自動保存される
- 慣れてきたら案出しを飛ばし、画像生成プロンプトを直接書いてそのまま生成することもできる

### 参照画像（キャラ・絵柄の一貫性）

- 依頼フォームでギャラリーの既存イラストを1枚添付できる。「このキャラで挿絵を」「この絵柄を保って」という依頼に使う
- 生成結果の直下の「**修正を依頼**」で、いま生成した画像を参照画像にした編集依頼（文字入れ・ポーズ修正・色味変更など）をワンステップで開始できる
- **表紙の文字入れ**もこの仕組みで行う: まず絵のみを生成し、確定後に「タイトル『○○』を入れて」と編集依頼する

### ギャラリー

- 選択中プロジェクトの生成イラストをグリッド表示（新しい順・種別バッジ＋タイトル付き）。失敗作も比較検討の材料としてすべて残る
- **タイトル**はその場でインライン編集できる（初期値は「プロジェクト名＋種別」で自動付与。重複可）
- 各画像から: 拡大表示（**依頼プロンプトが説明文として表示**される）・ダウンロード・「参照画像にして依頼」（プロンプトがフォームへ引き継がれ、追加依頼の下敷きになる）
- **削除**は確認ダイアログ→物理削除（復元不可。画像は再生成できるためごみ箱はない）。他の画像の参照元になっている場合は警告が出る

### 制限・モデル

- 生成は1回1枚。レートリミットは**案出し 5回/分・50回/日、画像生成 2回/分・20回/日**（画像生成は本アプリで最もコストの高い操作）
- 画像生成モデルは設定画面のAIモデル設定「image」枠で差し替えられる（→ §12）。デフォルトはGoogleのGemini画像生成系。生成の遅いモデルに差し替えるとタイムアウト（60秒）する場合がある

## 11. Zenn連携（記事の執筆・投稿）

`/zenn/new`（ヘッダーのナビ「Zenn」から）。技術ブログ [Zenn](https://zenn.dev) の GitHub 連携リポジトリへ、アプリから直接記事を書いて投稿できる。記事の実体もリポジトリの `articles/<slug>.md` で、アプリのDBには持たない（原稿と同じ思想）。

**新規投稿のための画面**である。既存記事の一覧や開き直しての編集はできない（画面を開いている間の再保存＝同じファイルへの再コミットはできる）。

[SCREENSHOT: Zenn投稿画面。上部のフロントマターフォームと2ペインのエディタ・プレビュー]

### 前提

1. `/settings` の **GitHub連携**でPATを登録し、その**対象リポジトリにZenn連携リポジトリを含める**
2. `/settings` の **Zenn連携**でリポジトリ（`owner/repo` 形式）を登録する（→ §12）

### 執筆

- 画面上部が**記事情報フォーム**: タイトル・絵文字・種別（tech / idea）・トピック（最大5つ）・slug・公開チェック
  - **slug** は開いたときに自動生成される（英小文字・数字・`_`・`-` の12〜50字）。手直しできるが、**一度コミットすると変更できない**（別ファイルになるため）
- 左が **Markdownエディタ**、右が **Zennと同じ見た目のプレビュー**。Zenn独自記法（`:::message`、ファイル名付きコードブロック等）もそのまま書ける
  - プレビュー領域はZennの見た目を再現するため、アプリをダークテーマにしても白背景のまま表示される
- **画像の挿入**: ヘッダーの「画像を挿入」から。選んだ画像は `images/<slug>/` へ即コミットされ、カーソル位置に `![…](/images/…)` が挿入される。**1枚3MBまで**・png / jpg / jpeg / webp / gif
- 未保存のまま画面を離れようとすると警告が出る

### 投稿

- 保存すると**確認ダイアログ**が必ず出る。リポジトリ名・ファイルパス・公開状態が明示される
  - **公開チェックの既定はオフ**（下書き投稿）。オンにすると「公開記事として投稿します。コミットと同時にZennで公開されます」と強調表示される
- 確定するとコミットされ、Zenn側が自動でデプロイする
- 投稿後も本文を編集して再保存できる（同じファイルへの2コミット目以降）。GitHub側で先に編集されていた場合は競合エラーになる

## 12. 設定

`/settings`。6セクション:

1. **AIモデル設定**: 能力帯（high / medium / low / image）ごとに provider と model_id を差し替えられる。空欄ならコード内デフォルト（high=Anthropic claude-sonnet-5 / medium=OpenAI gpt-5.4-mini / low=Google gemini-3.1-flash-lite / image=Google gemini-3.1-flash-image-preview）。**image はアトリエの画像生成用**（→ §9）。APIキー未設定のプロバイダには警告バッジが出る
2. **AI使用量（直近30日）**: AI機能ごとの呼び出し回数と入出力トークン数の一覧。どの機能にコストがかかっているかを把握できる（金額はプロバイダ側の管理画面で確認する）
3. **ペルソナ**: 標準9人は閲覧＋「複製」のみ。複製・自作した行は編集（名前・性格プロンプト・能力帯・参照範囲・型）・削除ができる
4. **レビュープロファイル**: 標準13種は閲覧＋「複製」のみ。複製・自作した行は編集（名前・対象フェーズ・観点プロンプト・既定ペルソナ）・削除ができる。削除してもレビュー履歴は残る
5. **GitHub連携**: Fine-grained PAT の登録・差し替え・削除。登録時に疎通検証され「@ユーザー名 として接続済み」と表示される。**登録済みPATの値は二度と表示されない**（暗号化保存）。権限は対象リポジトリ限定で **Contents: Read and write** ＋ **Workflows: Read and write**（後者は初期セットアップ（→ §8）でビルド用ワークフローを書き込むために必要）
6. **Zenn連携**: Zenn記事の投稿先リポジトリ（`owner/repo` 形式）の登録・差し替え・削除（→ §11）。投稿にはGitHub連携のPATを使うため、そのPATの対象にこのリポジトリを含めておく必要がある

## 13. 制限事項・トラブルシューティング

### 既知の制限

- **シングルユーザー前提**: 共有・共同編集機能はない。端末間の同時編集は後勝ち（last-write-wins）
- **レートリミット**: 相談・掘り下げチャットは10回/分・300回/日、レビュー・校正は各3回/分・60回/日、アトリエは案出し5回/分・50回/日・画像生成2回/分・20回/日。超えると429エラー（少し待てば回復）
- **原稿ファイル**: 1ファイル1MBまで・`.md` / `.txt` のみ。原稿タブでは読み込み専用（編集は縦書きエディタで）。**原稿タブの校正・講評・履歴・進捗記録はデフォルトブランチ固定**
- **講評の文字数上限**: 全原稿の合計30万字まで（15万字超は実行前に確認が入る）
- **ノートの記法**: Markdown往復の安全な範囲に限定される。表はセル内が1行のインライン内容のみ往復安全（セル内の `|` は列ずれの原因になるため非推奨・セル内の複数段落は保存時に1行へ潰れる）。列幅リサイズは Markdown に載らないため無効。添付は10MBまで
- **縦書きエディタ**: 原稿リポジトリがテンプレート構成（`book.config.js`＋`manuscripts/`＋`themes/`）に従っている前提（新規リポジトリは初期セットアップで自動構成できる → §8）。ブランチ切替・作成・PR作成には対応するが、**入稿ビルド（タグ作成）はデフォルトブランチ固定**。スマホは崩れない表示のみ（入力/プレビューのタブ切替なし）。全体プレビューに目次ページは出ない（目次込みの最終確認は入稿ビルドで）
- **青空文庫形式の書き出し**: 開いている1章のみ（複数章の結合はできない）。本文自体に `《` `》` `｜` `［＃` が含まれる場合のエスケープは行わない
- **Zenn連携**: 新規投稿専用。既存記事の一覧・開き直し編集・公開状態の切替・削除はできない。プレビューにリンクカードや数式は展開されない
- **アトリエ**: 生成は1回1枚。参照画像はアプリ内の生成物のみ（外部画像のアップロード不可）。削除は物理削除で復元不可

### よくあるエラーと対処

| 症状 | 原因と対処 |
|---|---|
| AIパネルに「このプロバイダのAPIキーが未設定です」 | 該当プロバイダのAPIキーが設定されていない。設定画面のAIモデル設定で別プロバイダに切り替える |
| 原稿タブが「PATを登録してください」誘導を出す | PAT未登録または削除済み。`/settings` で登録する |
| GitHub関連の401/403エラー | PATの失効・権限不足。GitHubで再発行して差し替える |
| 初期セットアップで「Workflows: Read and write 権限がない」エラー | Fine-grained PAT に Workflows 権限がなく、ビルド用ワークフローを書き込めない。GitHubのPAT設定で権限を追加してから再実行する（→ §12） |
| 初期セットアップで「リポジトリ ○○ が見つかりません」 | リポジトリ名の誤りか、PATの対象リポジトリに新リポジトリが入っていない。`/settings` のPATを対象リポジトリ込みで差し替える（→ §12） |
| 「原稿が更新されています」バナー | 前回校正後に原稿が更新された。そのまま校正し直せば最新版に対して実行される（既存の提案は残り、原文が見つからないものは適用不能表示になる） |
| 校正の提案が「適用不能」 | 原稿の該当箇所が変わって原文抜粋が見つからない。その提案は拒否し、必要なら再校正する |
| 選択範囲校正で「選択範囲が最新の原稿に見つかりません」 | 選択後に原稿が別経路で更新された。保存し直してから選択し直す |
| エディタの保存時に「原稿がリモートで更新されています」 | 他所（VS Code等）からのpushと競合した。マージビューでリモートの変更を取り込んでから再保存する |
| ボードで「転換点の順序が定義と違う」旨のエラー | 転換点付きのカードを、テンプレート定義と逆の順序に置こうとした。定義順どおりに並べ替える（→ §6.1） |
| 入稿ビルドが15分でタイムアウト | Actionsの実行が失敗している可能性。案内されるGitHubのActionsページでログを確認する |
| 保留の書き戻しが失敗する | 保留提案の原文が現在の原稿で一意に見つからない。案内に従って該当提案を未処理に戻すか拒否してから再実行する |
| Zenn投稿で「このslugの記事が既に存在します」 | 同じ slug の記事がリポジトリにある。slug を変更して投稿し直す |
| レビュー実行・イラスト生成が429エラー | レートリミット。1分ほど待って再実行 |
| ログインできない | 許可リスト外のGoogleアカウント。許可済みアカウントでログインする |

### 不具合を見つけたら

**GitHub Issue へ起票する**: https://github.com/Motoki-N/nekonote-v2/issues/new/choose

- 「不具合報告」「要望・改善提案」のテンプレートから選ぶ
- **1 Issue = 1 件**にする（修正フローが1 Issue単位で回るため）
- 発生画面・再現手順・期待する挙動・実際の挙動（エラーメッセージはそのまま貼る）があると対応が早い。文言変更の要望は最終的な文言を正確に書く

## 14. AI利用の考え方（執筆主体は人間）

小説執筆へのAI利用には批判もある。その多くは「文章をAIに書かせること」への批判であり、本アプリはその立場を共有する。**小説は人間が書く。AIは執筆を取り巻く人々——編集者・校正者・読者・書店員——の代役であって、作家の代役ではない。** この章では、その姿勢がアプリの設計にどう反映されているかと、小説コンテスト応募時にAI利用をどう説明すればよいかをまとめる。

### 14.1 設計上のこだわり（何をAIにさせないか）

- **本文を生成するAI機能はない**: 執筆画面である縦書きエディタ（→ §8）には、校正（誤字脱字・表記揺れの指摘）以外のAI機能を一切載せていない。「続きを書いて」「この場面を書いて」に相当する機能は存在せず、今後も追加しない
- **AIの出力は「原稿の外」に置かれる**: 相談・掘り下げ・レビュー・講評の応答は、チャット履歴・レビュー履歴・ノートに保存され、原稿本文には混ざらない。原稿リポジトリへ書き戻す場合も `<!-- -->` コメント（本・入稿PDFには一切出力されない領域。→ §8）としてのみ書き戻される
- **原稿本文に触れる唯一の例外は校正**（→ §7・§8）。それも「AIが提案 → 人間が1件ずつ受入/拒否 → 受入分だけ反映」であり、AIが本文を勝手に書き換えることはない。反映される変更は誤字脱字・表記揺れの修正という字句レベルにとどまる
- **反映はすべてGitコミットとして記録される**: 原稿への変更は必ずコミットになるため、「いつ・どの箇所に・何を反映したか」が履歴として残り、後から検証できる（原稿タブの履歴パネルでそのまま読める）

### 14.2 機能別のAI関与度

| 機能 | AIがすること | 出力は本文に入るか |
|---|---|---|
| 相談・掘り下げ（→ §4, §10） | 構想の壁打ち・整理・深掘り質問 | 入らない（ノート＝構想メモ止まり。取り込みは人間の明示操作） |
| 企画書・キャラクター・構成・シーンレビュー（→ §5, §6） | 助言・指摘 | 入らない（レビュー履歴に残るのみ） |
| 校正（→ §7, §8） | 誤字脱字・表記揺れの修正提案 | 人間が受け入れた提案のみ反映される（字句修正レベル） |
| 講評・売り込み分析（→ §7） | 感想・分析 | 入らない（履歴とコメント書き戻しのみ） |
| あらすじ・キャッチコピー作成（→ §7） | 宣伝文の生成 | 本文には入らないが、**AIが生成した文章**である点に注意（→ 14.3） |
| アトリエ（→ §9） | イラスト生成 | 本文外だが、生成画像は**AI生成物**である（→ 14.3） |
| 縦書きエディタの執筆（→ §8） | —（校正以外のAI機能なし） | — |
| Zenn記事の執筆（→ §11） | —（AI機能なし） | — |

### 14.3 コンテスト応募時のガイド

小説投稿コンテストの多くは「本文の全部または大部分をAIに生成させた作品は不可・補助的な利用（固有名詞の提案、校正など）は可・利用した場合は内容を開示」という規定を置いている。本アプリの標準的な使い方はこの「補助的な利用」の範囲に収まるよう設計されているが、**規定を守る責任は作家自身にある**。応募時は以下を確認する。

1. **本文はAIに書かせない**: アプリ設計上そうなっているが、運用でも徹底する。チャットやレビューの応答文をそのまま本文へコピーしない（応答は構想メモ・改稿判断の材料にとどめる）
2. **利用箇所を具体的に開示する**: 「作品のどの部分でどのようにAIを用いたか」の記載を求められたら、実際の利用に即して書く。記載例:
   > 本作は執筆支援ツールを補助的に使用した。使用箇所は次のとおり: (1) 構想段階のアイデア整理・深掘り（AIとの対話。本文には使用していない）、(2) 作中の固有名詞の候補出し、(3) 企画・構成に対する助言の受領、(4) 脱稿後の誤字脱字・表記揺れの校正（AIの指摘を著者が1件ずつ確認のうえ反映）。本文の生成にAIは使用していない。
3. **制作過程を開示できるようにしておく**: 「求められた場合は制作過程（プロンプトの入出力内容など）をすべて開示できるように」という規定に対して、本アプリは相談・掘り下げの会話履歴（→ §10 `/chats`）、レビュー・講評の履歴（→ §5 レビュー履歴タブ）、校正の採否と反映コミット（Git履歴）を保持しており、そのまま開示に使える。履歴を削除すると開示できなくなるため、応募作に関わるスレッドは選考が終わるまで残しておく
4. **あらすじ・キャッチコピーを応募書類に流用しない**: シノプシス提出が必要なコンテストでは、書店員が生成したあらすじをそのまま提出せず、参考にとどめて自分で書く。使う場合はそれ自体がAI生成文であることを開示する
5. **AI生成イラストの扱いは要項を確認する**: アトリエの生成画像は本文とは別に規定されることが多い。表紙・挿絵として添付してよいかはコンテストごとに確認する
6. **利用規約・著作権を守る**: 本アプリが呼び出すAIモデル（Anthropic / OpenAI / Google。→ §12）の利用規約に従う。特定の作家・作品の文体や絵柄の模倣を指示するなど、著作権侵害につながりうる依頼はしない
