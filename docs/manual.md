# 🐱 ネコノテAI ユーザーマニュアル

作成日: 2026-07-15（Sprint 7 ドッグフーディング向け）
更新日: 2026-07-17（縦書きエディタ・アトリエを追記）

小説執筆を支援するWebアプリ。小説そのものは人間が書き、AIはペルソナを持つエージェントとして、構想のネタ出し・企画レビュー・構成設計・校正の各フェーズに伴走する。原稿の実体はGitHubリポジトリで管理し、本アプリはレビューと進捗管理に専念する。執筆そのものも、縦書きエディタ（→ §8）でアプリ内から行える。

- 本番URL: https://nekonote-v2.vercel.app
- 不具合・要望の報告先: https://github.com/Motoki-N/nekonote-v2/issues （→ §12 保守対応）

## 1. はじめに（全体像と登場AI）

執筆フェーズとアプリの機能は次のように対応する:

| フェーズ | 使う画面 | 主に関わるAI |
|---|---|---|
| 構想（ネタ集め） | ノート | アシスタント（掘り下げ） |
| 企画 | プロジェクト / 企画書 | 担当編集（レビューゲート・キャラクターレビュー） |
| 構成設計 | ビートボード | 担当編集（構成・シーンレビュー） |
| 執筆・組版・入稿 | エディタタブ（縦書きエディタ） | —（AIなし。原稿タブと相互リンクで行き来） |
| 推敲・レビュー | 原稿タブ | 校正さん（校正）、読者代表（講評）、書店員（売り込み分析・あらすじ・キャッチコピー） |
| イラスト | アトリエ | イラストレーター（表紙・挿絵・キャラクター・コンセプトアート） |
| 進捗管理・雑談 | ダッシュボード | アシスタント（スケジュール）、喫茶店のマスター（壁打ち） |

### 標準ペルソナ7人

- **アシスタント**（対話型）: ネタの掘り下げ・整理・スケジュール相談の相手
- **喫茶店のマスター**（対話型）: 漠然とした構想の壁打ち相手。締めにメモをまとめてくれる
- **担当編集**（レビュー型）: 企画書・キャラクター・構成・シーンをレビューする
- **校正さん**（レビュー型）: 原稿の誤字脱字・表記揺れを機械的にチェックする
- **読者代表**（レビュー型）: ターゲット層になりきった主観的感想を賛否両論で返す（辛辣なこともある）
- **近所の書店員**（レビュー型）: 作家のサポーターとして「どう売り込むか」を分析する。あらすじ・キャッチコピーの作成も担当
- **イラストレーター**（イラスト型）: 企画書・原稿を読んで作画案を2〜3案提案し、画像生成モデルでイラストを描く（→ §9 アトリエ）

### レビュープロファイル9種（観点のプリセット）

企画書レビュー / キャラクターレビュー / 構成レビュー / シーンレビュー / 校正・校閲 / 読者講評 / 売り込み分析 / あらすじ作成 / キャッチコピー作成。レビュー実行時に「プロファイル（観点）＋担当ペルソナ＋対象」の組で呼び出す。標準のプロファイル・ペルソナは読み取り専用で、「複製して編集」で自分好みに調整できる（→ §11）。

## 2. ログイン

- `/login` から **Googleでログイン**。許可リストに載ったアカウントのみサインインできる
- セッションが切れた状態で編集していた内容は localStorage に退避され、再ログイン後に復元を提案される（書きかけの消失防止）
- テーマ（ライト/ダーク）はヘッダーのトグルで切替

## 3. ダッシュボード

トップページ（`/`）は「作業基地」。以下が並ぶ:

- **プロジェクト概況カード**（進行中プロジェクトごと）:
  - 企画書ステータスバッジ（draft / in_review / approved）・締切カウントダウン
  - 最新の総文字数と**直近30日の文字数推移の折れ線**
  - **「今すぐ集計」ボタン**: GitHubの原稿から当日の総文字数を集計して記録する（repo/PAT設定済みのプロジェクトのみ表示）。進捗記録は原稿タブを開いたときにも自動で走る
  - **執筆スケジュールブロック**（アシスタントとの相談で確定保存した場合のみ表示）: 1日あたり目標字数・マイルストーン一覧（チェックボックスで手動達成、目標字数があれば実文字数との比較で自動達成）。ゴミ箱アイコンで削除
  - 企画書・ビートボード・原稿タブへの導線
- **「相談する」ボタン**: 相談パネルを開く（→ §10）
- **「アトリエ」ボタン**: イラスト生成ページを開く（→ §9）

## 4. ノート（構想メモ）

`/notes`。「紙の手帳」に相当する。**入力は白紙から・分類は後から**が思想。

### 基本操作

- **作成**: 一覧の新規作成ボタン1クリックで空ノートが開く
- **エディタ**: Notion風のWYSIWYG。対応記法は見出し（H1〜H3）・リスト・太字/斜体・リンク・引用・区切り線（保存はMarkdown）
- **自動保存**: 入力停止後数秒で自動保存（保存状態は常時表示）。オフライン時はローカル退避→復帰時に復元提案
- **Undo/Redo**: Cmd/Ctrl+Z・Shift+Cmd/Ctrl+Z。保存タイミングをまたいで遡れる

### タグ

- タグ入力欄から既存タグを選択、なければその場で新規作成
- 種類は2つ: **category**（コンセプト・キャラクター等の分類）と **working_title**（仮タイトル＝作品の卵の名前）
- 仮タイトルタグで「同じ作品候補のノート群」を束ね、一覧で絞り込める（複数タグはAND）

### テンプレート挿入（プロットに落とし込む）

- 挿入メニューからテンプレート（コンセプト / キャラクター / テーマ / 世界観）を選ぶと、カーソル位置に雛形が挿入され、対応するcategoryタグが自動付与される
- 挿入後もただのMarkdown。追記・逸脱は自由（構造は強制されない）

### AI掘り下げ（アシスタント）

- エディタの「掘り下げ」ボタンでパネルを開く（デスクトップ=右サイド、スマホ=ボトムシート）
- ノートの内容（編集途中の未保存分も含む）を踏まえて、要約と深掘り質問でネタを膨らませてくれる
- 会話はノートごとに1スレッドが保存される。応答の「ノートに挿入」でカーソル位置に取り込める（1回のUndoで取り消し可）
- 「会話をリセット」で仕切り直し

### ごみ箱

- 削除はごみ箱への移動（トーストの「元に戻す」で即復元）。ごみ箱ビューから復元・完全削除できる。自動パージはしない

## 5. プロジェクトと企画書

`/projects`。書き上げる本ごとにプロジェクトを作る。

### プロジェクト作成

- タイトル（必須）、イベント名・締切・目標ページ数（任意）
- **仮タイトルタグを選ぶと**、そのタグの付いたノート群が候補表示され、チェックした分が企画書に一括紐づけされる
- 作成と同時に企画書が1つ自動作成される（1プロジェクト1企画書）
- 原稿連携する場合はプロジェクト編集で **repo**（`owner/repo` 形式）と **base_path**（リポジトリ内のフォルダ）を設定する（→ §7）
- プロジェクト配下は **企画書 / ビートボード / 原稿 / エディタ** の4タブ構成

### 企画書エディタ（`/projects/[id]`）

- ジャンル / ターゲット層の2フィールド＋本文エディタ（ノートと同じ記法・自動保存）。初期本文にコンセプト / キャラクター / テーマの見出しテンプレが入っている
- **紐づけノート**: 検索して個別追加・解除もできる。紐づけたノートはレビューの材料としてAIに渡る（企画書＝表紙・ノート＝本文の関係）

### 企画書レビュー（レビューゲート）

- 「レビュー」ボタン→パネルで「レビューを受ける」→ 担当編集のフィードバック文書がストリーミング表示される
- フィードバック末尾に**判定バッジ（承認 / 差し戻し）**が付く
- 指摘を受けて企画書を改稿し、**返答メモ**（改稿の意図や反論）を書いて再レビュー→前回指摘の改善を見てもらえる、の反復
- 判定が「承認」になると**「企画を通す」ボタン**が出る→確定で status が approved に。承認後の編集でステータスは変わらない（ゲートは演出。再審査したければ新しいレビューを回す）
- パネルのプロファイルセレクタで複製プロファイルに切替可能。プロファイルごとにセッション（履歴）が並存する。担当ペルソナは新規セッション開始時のみ変更できる

### キャラクターレビュー

- 企画書画面の「キャラクター」ボタンから（「レビュー」パネルとは排他表示）
- 企画書＋紐づけノート一式を材料に、5つの問い（誰が・何を・なぜ・失敗の代償・どう変わるか）でキャラクター設計をレビューする
- 合否判定はなし。企画書ステータスとも無関係（approved 後のキャラブレ点検にも使える）。紐づけノート0件でも実行でき、資料不足はそのまま指摘される

## 6. ビートボード（構成設計）

`/projects/[id]/board`（企画書ページのタブから）。4部構成・5転換点にもとづく付箋ボード。

### ボードとシーンカード

- 4レーン: **設定・反応・攻撃・解決**（スマホは縦積み）
- 「＋シーンを追加」でカード作成→編集ダイアログ（タイトル・本文・感情の起点→終点・パート・アンカー）。本文のplaceholderに4観点（シチュエーション / 起きること / 感情の変化 / 葛藤）のヒントあり
- **D&D**: レーン内並び替え・レーン間移動（移動でパートも変わる）。タッチは長押しでドラッグ
- カード削除は確認ダイアログ→即削除（ごみ箱なし。短文メモなので再作成コストが低い）

### 転換点アンカー

- **境界3点（PP1 / ミッドポイント / PP2）**はレーン末尾の定位置スロットに固定表示される。未設定のスロットは薄いプレースホルダーで「まだ決まっていない転換点」が見える
- **ピンチポイント1・2**はバッジ付きの通常カードとしてレーン内自由
- 1転換点1シーン。他のシーンに付いているアンカーを選ぶと付け替えになる。パートを変えると境界アンカーは自動解除

### 感情の起伏

- カードに感情バッジ（起点→終点のプラス/マイナス）、ボード下部に構成順の折れ線が表示される

### 構成レビュー / シーンレビュー

- **構成レビュー**: ボードヘッダーから。全シーン＋企画書を材料に、4部構成・5転換点の観点でレビュー
- **シーンレビュー**: カードから起動。対象シーン＋全体の流れ＋企画書を材料に4観点でレビュー
- どちらも反復型（返答メモ→再レビュー）。合否判定はなし

## 7. 原稿と校正・講評

`/projects/[id]/manuscript`（原稿タブ）。原稿の実体はGitHubリポジトリ、ネコノテは「AIによる差分レビューの場」。

### 前提設定（初回のみ）

1. `/settings` で **GitHub Fine-grained PAT** を登録（対象リポジトリ限定・Contents: Read/Write。→ §11）
2. プロジェクト編集で **repo / base_path** を設定

### 原稿の閲覧

- base_path 配下の `.md` / `.txt` がファイル一覧に出る。開くと本文が読み込み専用で表示される（この画面では編集しない。執筆はエディタタブ →§8、または普段のエディタで）
- ファイル表示ヘッダの「**エディタで開く**」リンクで、同じ章を縦書きエディタで開ける（相互リンク）
- 前回の校正以降に原稿が更新されていると「原稿が更新されています」バナーが出る
- ファイルを開くと当日の総文字数が進捗として自動記録される（ダッシュボードのグラフの元データ）

### AI校正（校正さん）

- 原稿ビューの「校正を受ける」→ その時点の最新原稿に対して実行→ **提案カード**（原文抜粋 / 修正案 / 理由）が逐次表示される
- 各カードを **受入 / 拒否 / 保留** で処理する。原稿が更新されて原文が見つからなくなった提案は「適用不能」表示になる（安全弁）
- **「確定分をコミット」**: 受入済みの提案をまとめて適用し、1コミットでGitHubへ書き戻す
- **「保留をコメントで書き戻す」**: 保留中の提案をファイル単位で一括して、原稿の該当箇所の直前に `<!-- [ネコノテ校正・保留] … -->` コメントとして1コミットで書き戻す。書き戻した提案には「コメント書き戻し済み」バッジが付き、以後の消化（採否の判断・コメント削除）は縦書きエディタのコメント一覧で行う（→ §8）。コメントはプレビュー・入稿PDFには一切現れない
- 再校正すると未処理（pending）の提案は新しい提案に置き換わる。**保留はコミット後も残り**、後から受入/拒否できる

### 講評（読者代表・書店員）

- 原稿タブヘッダーの「講評」ボタン→ プロファイル（読者講評 / 売り込み分析 / あらすじ作成 / キャッチコピー作成）とペルソナを選んで実行
- base_path 配下の**全原稿ファイルを結合した「作品全体」**への講評が返る。読み切り型で、履歴が一覧に残る（反復・返答メモなし）
- 各講評の「**レビューメモへ書き戻す**」ボタンで、講評全文を原稿リポジトリの専用メモファイル `manuscripts/00-review-notes.md` へ `<!-- -->` コメントとして追記コミットできる。このファイルは本文の章立て（entry）に載らないため、本・入稿PDFには一切出ない。縦書きエディタの章一覧の末尾（「entry未登録」印つき）から開いて読める
- 読者講評と書店員担当のプロファイル（売り込み分析・あらすじ作成・キャッチコピー作成）は、企画書のジャンル・ターゲット層が未設定だと実行できない（なりきり先・売り込み先がないため）。15万字超は実行前確認、30万字超は実行不可

## 8. 縦書きエディタ（執筆・組版・入稿PDF）

`/projects/[id]/editor`（プロジェクトのタブから）。**横書きで書いて、縦書きで確認し、印刷所に出せる入稿PDFまで作る**エディタ。原稿の実体は原稿タブと同じGitHubリポジトリで、保存のたびにコミットが作られる（アプリのDBには原稿を置かない）。

### 前提

- §7 と同じ **PAT（Contents: Read/Write）＋ repo / base_path** の設定
- 原稿リポジトリがテンプレート構成（`manuscripts/` 配下の章ファイル・`book.config.js`・`themes/`・入稿ビルド用 GitHub Actions。雛形は本リポジトリの `docs/templates/manuscript-repo/`）に従っていること
- 原稿フォーマットは **VFM**（Vivliostyle Flavored Markdown）。ルビは `{漢字|かんじ}`、メモはHTMLコメント `<!-- -->`

### 画面構成

- **章一覧サイドバー**: `book.config.js` の entry 順に章ファイルを表示（折りたたみ可）。entry未登録のファイルは末尾に印つきで表示。未保存の待避がある章にはインジケータが付く。「新規章ファイルの作成」もここから（雛形入りで作成＝コミット。entryへも自動追記される）
- **入力ペイン（横書き）**: プレーンテキストエディタ。ルビ・コメント・見出しがハイライトされる
- **プレビューペイン（縦書き）**: 実際の判型どおりのページ分割・ノンブル込みで表示される。入力停止後数秒（デバウンス）で再組版。プレビューと入稿PDFは同じ組版エンジン（Vivliostyle）なので、見た目がズレない
- デスクトップは左右2ペイン（比率ドラッグ可変・プレビュー折りたたみ可）。スマホは崩れない最低限の表示のみ
- プレビューの既定は**編集中の章のみ**（高速）。**全体プレビュー**は明示操作で、全章を通したページ分割・ノンブルを確認できる（目次ページだけは入稿ビルドでのみ生成される。UI上にも注記あり）

### 執筆と保存（保存＝コミット）

- `Cmd/Ctrl+S` または保存ボタン → コミットメッセージを確認・編集 → コミット。対象は**デフォルトブランチのみ**
- 未保存の編集はブラウザ（IndexedDB）へ自動待避され、リロード・クラッシュしても失われない。章を開き直すと「未保存の編集があります」バナーで復元/破棄を選べる
- 他所（VS Code等）からのpushと競合した場合は「原稿がリモートで更新されています」→ **マージビュー**（左=リモート最新・右=ローカル編集）でチャンク単位に取り込んで再保存する。自動マージはしない

### ツールバー（入力補助）

記法を知らなくても使えるボタン群。挿入結果はすべて素のVFMテキスト。

- **ルビ**: 選択→ボタン→読みを入力→ `{選択文字|読み}` に置換
- **傍点・縦中横**: 選択→ボタンでクラス指定記法に置換（縦中横は2〜3桁の半角英数向け）
- **コメント**（`Cmd/Ctrl+/`）: 選択範囲を `<!-- -->` で包む（未選択なら空コメントを挿入）。没にした文章の保留にも使える
- **画像**: ボタンまたは入力ペインへの**ドラッグ&ドロップ**で、`images/` へ即コミット＋カーソル位置に挿入記法を追記（本文中カット / 全面挿絵を選択）。png / jpg / jpeg / webp / gif・10MBまで
- **字数カウント**: 本文のみを数える（コメント・フロントマター・記法・ルビの読みは除外）。「約◯ページ」の見積り付きで、プレビュー完了後は実ページ数を表示

### コメント一覧

- 編集中の章の `<!-- -->` コメントを出現順に一覧表示。クリックで該当行へジャンプ
- コメントはプレビューにも入稿PDFにも**一切現れない**（構成メモ・没文の保留・校正の書き戻し置き場として安全）

### 書籍設定フォーム

ヘッダーの「書籍設定」から。実体はリポジトリ内のファイルで、フォームは該当箇所だけを書き換えて**差分プレビュー→コミット**する。

1. **書誌情報**: `book.config.js` のタイトル・著者
2. **章順（entry管理）**: 並べ替え・entry未登録章の取り込み・除外
3. **組み設定**: 行数・字詰め・行送り・フォントサイズ（判型タブで文庫A6 / B6を切替編集）
4. **奥付**: 発行日・著者・発行・連絡先・印刷の各フィールド（テンプレート構造が検出できた場合のみ）

フォームが対応できない構造のファイルは読み取り専用になり、VS Code等での直接編集が案内される（壊れた書き換えはしない）。

### 入稿ビルド（PDF書き出し）

- ヘッダーの「入稿ビルド」→ タグ名（`v*-nyuko` 形式・自動提案あり）を確認して実行 → GitHub Actions が入稿品質のPDF（PDF/X-1a・フォント埋め込み・ノンブル・目次・奥付込み）を生成し、同タグのGitHub Releasesに添付する
- 完了は自動で検知され（30秒間隔のポーリング・最長15分）、UIにPDFのダウンロードリンクが出る。タイムアウト時はActionsページへのリンクが案内される
- ビルド時に総ページ数（4の倍数チェック）や画像の解像度・カラー混入も検査される
- 「どのコミットを入稿したか」がタグとしてGitに残る

### ネコノテ連携（相互リンク）

- ヘッダーの「**レビュー**」→ 編集中の章を開いたまま原稿タブ（校正・講評）へ。原稿タブの「**エディタで開く**」で戻ってくる
- 校正の保留提案・講評は、§7 の書き戻し機能で `<!-- -->` コメントとして原稿に持ち帰れる。書き戻されたコメントはこのエディタのコメント一覧に載り、執筆→レビュー→推敲のループがアプリ内で一周する

## 9. アトリエ（イラスト生成）

`/atelier`（ダッシュボードの「アトリエ」ボタンから）。ペルソナ「**イラストレーター**」に、プロジェクトの資料を踏まえたイラストを依頼する。生成対象は4種:

- **表紙イラスト**
- **文中の挿絵**（原稿の指定シーンに合わせて描く）
- **キャラクターイラスト**（キャラクター設定資料に載せる想定）
- **コンセプトアート**（世界観を表すイラスト）

ページ上部のプロジェクトセレクタで対象プロジェクトを選ぶ。イラストレーターは種別に応じた資料（表紙・コンセプトアート=企画書一式＋原稿全文、キャラクター=企画書一式、挿絵=選択した原稿ファイル＋場面の補足）を自動で読み込む。

### 依頼の流れ（2段階）

1. **依頼フォーム**: 種別・カラー/モノクロ・アスペクト比（種別ごとのデフォルトあり: 表紙/挿絵/キャラクター=縦2:3、コンセプトアート=横16:9。縦/横/正方形から変更可）・描いてほしい対象/構図/雰囲気（自由記述）を入力。挿絵の場合は原稿ファイルを選び「どの場面か」を補足する
2. **「案を出してもらう」**: イラストレーターが資料を読んで**2〜3案**（タイトル・狙いの説明・画像生成プロンプト）を提案する
3. **案を選んで生成**: 案を選択し、プロンプトを微調整してから「**この内容で描いてもらう**」。生成は10〜30秒程度。完成した画像はギャラリーに自動保存される
- 慣れてきたら案出しを飛ばし、画像生成プロンプトを直接書いてそのまま生成することもできる

### 参照画像（キャラ・絵柄の一貫性）

- 依頼フォームでギャラリーの既存イラストを1枚添付できる。「このキャラで挿絵を」「この絵柄を保って」という依頼に使う
- 生成結果の直下の「**修正を依頼**」で、いま生成した画像を参照画像にした編集依頼（文字入れ・ポーズ修正・色味変更など）をワンステップで開始できる
- **表紙の文字入れ**もこの仕組みで行う: まず絵のみを生成し、確定後に「タイトル『○○』を入れて」と編集依頼する

### ギャラリー

- 選択中プロジェクトの生成イラストをグリッド表示（新しい順・種別バッジ＋タイトル付き）。失敗作も比較検討の材料としてすべて残る
- **タイトル**はその場でインライン編集できる（初期値は「プロジェクト名＋種別」で自動付与。重複可）
- 各画像から: 拡大表示（**依頼プロンプトが説明文として表示**される）・ダウンロード・「参照画像にして依頼」（プロンプトがフォームへ引き継がれ、追加依頼の下敷きになる）
- **削除**は確認ダイアログ→物理削除（復元不可。画像は再生成できるためごみ箱はない）。他の画像の参照元になっている場合は警告が出る

### 制限・モデル

- 生成は1回1枚。レートリミットは**案出し 5回/分・50回/日、画像生成 2回/分・20回/日**（画像生成は本アプリで最もコストの高い操作）
- 画像生成モデルは設定画面のAIモデル設定「image」枠で差し替えられる（→ §11）。デフォルトはGoogleのGemini画像生成系。生成の遅いモデルに差し替えるとタイムアウト（60秒）する場合がある

## 10. 相談（対話型ペルソナ）

ダッシュボードの「相談する」からパネルを開く。**アシスタント / 喫茶店のマスター**のタブ切替。

### アシスタント（スケジュール相談・整理）

- タブ内の**プロジェクトセレクタ**で対象を選ぶと、締切・残日数・直近の執筆ペース等の実データを踏まえた具体的な助言が返る（「指定なし」なら一般的な相談相手）
- スケジュール提案に納得したら「**これで確定して**」と言うと、マイルストーン＋日次目標が構造化保存され、ダッシュボードの概況カードに表示される（1プロジェクト1本・上書き。修正は再提案→再確定）
- 保存はプロジェクトを選択しているときだけ可能。頼んでいないのに勝手に保存はされない

### 喫茶店のマスター（壁打ち）

- 漠然とした構想を話すと、要約と深掘り質問で付き合ってくれる
- 「**メモにまとめて保存して**」と頼むと、会話の内容をまとめたノートが自動作成される（チャット内にリンク付きカードが出る）

### 共通操作

- 全AI応答に「ノートに保存」ボタン（応答をそのまま新規ノート化。タイトルは1行目から自動）
- 「新しい会話」でスレッドを切り替え（旧スレッドは履歴として残る）
- パネルの「履歴」リンク→ **`/chats`** で過去スレッドの一覧・リネーム・削除・再開ができる

## 11. 設定

`/settings`。4セクション:

1. **AIモデル設定**: 能力帯（high / medium / low / image）ごとに provider と model_id を差し替えられる。空欄ならコード内デフォルト（high=Anthropic claude-sonnet-5 / medium=OpenAI gpt-5.4-mini / low=Google gemini-3.1-flash-lite / image=Google gemini-3.1-flash-image-preview）。**image はアトリエの画像生成用**（→ §9）。APIキー未設定のプロバイダには警告バッジが出る（キー自体はVercelの環境変数で管理）
2. **ペルソナ**: 標準7人は閲覧＋「複製」のみ。複製・自作した行は編集（名前・性格プロンプト・能力帯・参照範囲・型）・削除ができる
3. **レビュープロファイル**: 標準9種は閲覧＋「複製」のみ。複製・自作した行は編集（名前・対象フェーズ・観点プロンプト・既定ペルソナ）・削除ができる。削除してもレビュー履歴は残る
4. **GitHub連携**: Fine-grained PAT の登録・差し替え・削除。登録時に疎通検証され「@ユーザー名 として接続済み」と表示される。**登録済みPATの値は二度と表示されない**（暗号化保存）

## 12. 保守対応（不具合・要望への対応フロー）

使っていて見つけた不具合・欲しくなった改善は、**GitHub Issue に起票するだけ**で修正フローに乗る。アプリ本体のコード修正は Claude Code の自動化フロー（`/fix-issue` スキル）が担い、人間の関与は「起票」「（条件付き）設計確認」「PRのマージ承認」の実質2〜3箇所。

### 12.1 フローの全体像

```
① 人間：Issue起票
        ↓
② AI：影響範囲の分析・調査
        ↓
③ 分岐：アーキテクチャ変更が必要？
   ├─ YES → 人間に設計確認（承認待ち）
   └─ NO  ↓
④ AI：コード修正 + テスト実行
        ↓
⑤ AI：自己レビュー → 問題あれば④に戻る
        ↓
⑥ AI：PR作成（説明・変更サマリー付き）
        ↓
⑦ 人間：最終確認 → マージ承認
        ↓
⑧ 自動デプロイ（Vercel: main へのマージで本番反映）
```

### 12.2 ① Issueの起票（人間）

https://github.com/Motoki-N/nekonote-v2/issues/new/choose からテンプレートを選ぶ:

- **不具合報告**: 発生画面・再現手順・期待する挙動・実際の挙動（エラーメッセージはそのまま貼る）
- **要望・改善提案**: やりたいこと・背景/理由

起票のコツ:

- **1 Issue = 1 件**にする（複数の問題をまとめない。フローが1 Issue単位で回るため）
- 文言変更の要望は**最終的な文言を正確に**書く（試運転 Issue #1 の教訓: 例示の句読点の位置までそのまま実装される）
- 対象箇所が曖昧だとAIから質問が返ってくるので、「どの画面のどの表示か」を補足欄に書いておくとスムーズ

### 12.3 ②〜⑥ 修正の実行（AI）

Claude Code のセッションで **`/fix-issue <Issue番号>`** を実行すると、影響範囲分析→修正→検証（typecheck / lint / 実画面確認）→自己レビュー→PR作成まで自動で進み、PRのURLが提示される。

運用ルール（スキルに組み込み済み）:

- **複数Issueは直列で対応**する（並行処理しない）。1件をPR作成まで進めてから次に着手。同じファイルに触るIssue同士は前のPRマージ後に次へ
- 同じ作業ディレクトリで複数の Claude Code セッションを同時に走らせない（ブランチが衝突する）
- 認証・RLS・秘密情報に触れる修正は security-reviewer の通過が必須（自動フローでも省略しない）

### 12.4 ③ 設計確認が必要になるケース

次のいずれかに該当する修正は、AIが実装前に設計確認を求めてくる（CLAUDE.md に明記済みの基準）:

- DBスキーマの変更を伴う
- 外部APIの認証フロー変更
- 既存APIのインターフェース変更（破壊的変更）
- セキュリティ関連コードの変更
- 3ファイル以上にまたがる大規模リファクタリング

該当しないルーティンな修正（文言・表示崩れ・小さなロジック修正など）は確認なしでPR作成まで進む。

### 12.5 ⑦ PRの確認とマージ（人間）

- PR本文には概要・影響範囲分析の要約・変更点・検証結果が書かれている。差分と合わせて確認する
- **修正が意図と違う場合**: PRにレビューコメントを書く → AIが④に戻って再修正し、同じPRに追加コミットする（試運転で実証済みの差し戻しループ）
- 問題なければマージ → **Vercelが自動で本番デプロイ**し、Issueも自動クローズされる（PR本文の `Closes #N`）
- 本番反映は必ずこのマージ承認を経由する。mainへの直接pushによるデプロイはしない
- リポジトリ設定「Automatically delete head branches」を有効にしておくと、マージ後のブランチ掃除が不要

### 12.6 緊急時・フローに乗らない対応

- 重大な不具合でフローの往復を待てない場合は、通常の Claude Code セッションで直接修正を依頼してよい。その場合も**本番反映はPR経由**を維持する
- アプリのコード以外（Supabaseダッシュボード・Vercel設定・APIキーのローテーション等）は従来どおり人間が直接操作する

## 13. 制限事項・トラブルシューティング

### 既知の制限

- **シングルユーザー前提**: 共有・共同編集機能はない。端末間の同時編集は後勝ち（last-write-wins）
- **レートリミット**: 相談・掘り下げチャットは10回/分・300回/日、レビュー・校正は各3回/分・60回/日、アトリエは案出し5回/分・50回/日・画像生成2回/分・20回/日。超えると429エラー（少し待てば回復）
- **原稿ファイル**: デフォルトブランチ固定・1ファイル1MBまで・`.md` / `.txt` のみ。原稿タブでは読み込み専用（編集は縦書きエディタで）
- **講評の文字数上限**: 全原稿の合計30万字まで（15万字超は実行前に確認が入る）
- **ノートの記法**: 表・画像・コードブロックは非対応（Markdown往復の安全な範囲に限定）
- **縦書きエディタ**: 原稿リポジトリがテンプレート構成（`book.config.js`＋`manuscripts/`＋`themes/`）に従っている前提。デフォルトブランチのみ（ブランチ切替・PR連携は未対応）。スマホは崩れない表示のみ（入力/プレビューのタブ切替なし）。全体プレビューに目次ページは出ない（目次込みの最終確認は入稿ビルドで）
- **アトリエ**: 生成は1回1枚。参照画像はアプリ内の生成物のみ（外部画像のアップロード不可）。削除は物理削除で復元不可

### よくあるエラーと対処

| 症状 | 原因と対処 |
|---|---|
| AIパネルに「このプロバイダのAPIキーが未設定です」 | 該当プロバイダのAPIキーがVercel環境変数にない。設定画面のAIモデル設定で別プロバイダに切り替えるか、キーを登録する |
| 原稿タブが「PATを登録してください」誘導を出す | PAT未登録または削除済み。`/settings` で登録する |
| GitHub関連の401/403エラー | PATの失効・権限不足。GitHubで再発行して差し替える |
| 「原稿が更新されています」バナー | 前回校正後に原稿が更新された。そのまま校正し直せば最新版に対して実行される（既存の提案は残り、原文が見つからないものは適用不能表示になる） |
| 校正の提案が「適用不能」 | 原稿の該当箇所が変わって原文抜粋が見つからない。その提案は拒否し、必要なら再校正する |
| エディタの保存時に「原稿がリモートで更新されています」 | 他所（VS Code等）からのpushと競合した。マージビューでリモートの変更を取り込んでから再保存する |
| 入稿ビルドが15分でタイムアウト | Actionsの実行が失敗している可能性。案内されるGitHubのActionsページでログを確認する |
| 保留の書き戻しが失敗する | 保留提案の原文が現在の原稿で一意に見つからない。案内に従って該当提案を未処理に戻すか拒否してから再実行する |
| レビュー実行・イラスト生成が429エラー | レートリミット。1分ほど待って再実行 |
| ログインできない | 許可リスト外のGoogleアカウント。許可済みアカウントでログインする |

### 不具合を見つけたら

§12 のとおり GitHub Issue へ。エラーメッセージ・スクリーンショット・再現手順があると修正フローが最短で回る。
