## 1. シリーズ作品対応（最大の引き継ぎ項目）

### 1.1 現状

- **スキーマ・コードに「シリーズ」「巻」は一切存在しない。** 全機能の暗黙の単位は
  「1 `projects` 行 = 1冊」である
- 一方で `notes` / `tags` / `templates` / `personas` / `review_profiles` は**ユーザー資産**のため、
  巻をまたいだ共有は構造上すでに可能
- **SPEC は1本も書かれていない。** 各子Issue の着手時に、運用計画フェーズ1
  （インタビュー → SPEC → 新セッションで実装）から始める

### 1.2 確定済みの設計方針6点（2026-08-01・設計インタビュー2巡の結果）

**この6点は決定事項として引き継ぐ。** 覆すなら再インタビューから。

| # | 論点 | 決定 |
|---|---|---|
| 1 | 階層モデル | `series` テーブル新設＋`projects.series_id`（nullable）＋`volume_number`。**単巻作品は現行のまま動く** |
| 2 | シリーズ企画書 | `series_proposals` 新テーブル。**既存 `proposals` は無改修**（影響ゼロを優先） |
| 3 | リポジトリ構成 | **1リポジトリ1シリーズ・巻はサブディレクトリ**で `base_path` を巻単位に。repo-setup へ「既存リポへ巻を追加」モードを追加 |

| 5 | キャラの巻ごと状態 | **ノート方式**（「巻時点キャラ状態」テンプレートを新設）。構造化テーブルは作らない |
| 6 | 階層要約 | **レビュー時オンデマンド生成**（古い要約のみ部分再生成）。コストの予測可能性を優先 |

### 1.3 既知の衝突点（着手前に必ず確認する）

第二期の探索で判明した、シリーズ化で壊れる箇所。

- **`proposals.project_id` の unique 制約** — シリーズ企画書を置く器がない（→ 決定2 で回避）
- **repo-setup の既存ファイル全退避＋`base_path` 強制上書き** — 同一リポの2巻目セットアップで
  **1巻目が `backup-<日時>/` へ送られる**（→ 決定3 の「既存リポへ巻を追加」モードが必須）
- **project 単位で分断されているもの** — 進捗・締切・レビュー履歴・イラスト

## 3. 引き継ぐ運用ルール（第二期で機能したもの）

比較レポート §6.2 の Keep をそのまま持ち込む。特に第三期で効くもの:

1. **スキーマはプランモード承認 → マイグレーション経由**。シリーズ機能はスキーマ変更が5件あるため、
   ここが最も効く
2. **着手前に SPEC を書く**。効くのは文書の鮮度ではなく、**実装が仕様から外れないこと**
   （第二期の乖離60件のうち「実装が仕様から逸脱」は0件だった）
3. **security-reviewer の必須ゲート**。#146 は PAT とリポジトリ操作に触れるため明示的に必須
4. **dev-log をセッション単位で書く**。第二期のあらゆる事後作業がこれを索引に成立した
5. **二失敗ルール**（同じ問題に同じアプローチで2回失敗したら手を止めて人間に相談する）。
   第二期は文書化が遅れたうえ発動記録も残っておらず「効いていた」が検証不能だった——
   第三期は**発動したら dev-log に記録する**

### 第二期の Problem を繰り返さないために（比較レポート §6.4 の Try）

1. **書き戻し先を1つに決め、書式まで決める。** 第二期は「SPEC へ書き戻す」とだけ決めて書式を決めず、
   28本中18本で途絶した。**実績上は dev-log 1本に集約するのが最も現実的**（SPEC は時点記録と割り切る）
2. **監査・突き合わせの入力に「手を動かして見つけた記録」を必ず含める**（テスト結果・インシデント・Issue）
3. **数字を書くときは出典と計測条件を併記する。** 第二期の比較作業では、過去に書かれた数値4件が
   実測と食い違っていた（いずれも計測条件が書かれていなかった）
4. **バックアップを最初に用意する。** 本番 Supabase は現在 **PITR 無効・物理バックアップ0件**で、
   自前の `db dump` が唯一の復旧経路である（RUNBOOK §5.1）。
   **第三期のスキーマ設計時点で定期取得を運用に組み込む**
5. **公開規約の対象をコード内の文字列まで広げる。** 第二期の伏せ字規約は文書系（コミット・PR・dev-log）
   だけを対象にしていたため、UI の入力例・zod エラーメッセージというコード内の例示文字列に
   公開できない文字列が混入し、監査（M-2）まで発見されなかった。
   例示文字列・サンプル値・エラーメッセージも規約の対象であることを CLAUDE.md に明文化する
6. **開発側の AI 利用量・コストも記録する。** 第二期の計測はアプリ側の `ai_usage_logs` のみで、
   Claude Code による開発コストは記録がない。第三期と第二期を定量比較するなら開発側の記録が要る
