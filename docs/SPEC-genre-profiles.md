# SPEC-genre-profiles: ジャンル別標準ペルソナ・プロファイルと既定選択の自動適用

作成日: 2026-07-25（Issue #95 のインタビュー駆動で策定）
ステータス: **確定**（2026-07-25 プラン承認をもって設計確認とする）
起点Issue: #95（親Issue #93 汎用執筆支援。前提: SPEC-genre / #94 の `proposals.writing_genre`）

## 1. 目的

「技術書執筆支援なら技術者レビューを追加する」の実体。各ジャンルに適した標準AIペルソナ・
レビュープロファイルを同梱し、プロジェクトの執筆ジャンルに応じて**既定選択**を自動適用する。
選択肢の絞り込みはしない——他ジャンルのプロファイル・ペルソナも手動で選択でき、
クロスジャンルの視点（小説の読者代表に技術書を読ませる等）は引き続き使える。

## 2. 決定事項（インタビュー結果・2026-07-25）

| 論点 | 決定 |
|---|---|
| スキーマ | `personas` / `review_profiles` に `writing_genre`（text nullable・CHECK: novel/tech_book/other）。**null = 全ジャンル共通** |
| 既存標準行のタグ付け | 内容で仕分け。小説理論・物語・書店の文脈を前提とする行のみ 'novel'、ジャンル中立な行は共通のまま（§4の表） |
| 既定選択 | ジャンル優先ソート（**一致 → 共通 → 他ジャンル**）。一覧の並び自体をこの順にし、UIの「先頭＝既定」挙動に乗せる |
| 「その他」ジャンル | 専用シードなし。一致行が存在しないため共通→既存順となり、実質「現行の小説向け標準が既定」を維持 |
| 校正 | **サーバー側ジャンル解決**。/api/proofread の固定UUID直引きを廃止し、target_phase='proofreading' の**標準行**をジャンル優先で1件解決。選択UIは追加しない |
| 新規シード | ペルソナ2（技術書編集者・エンジニア読者）＋プロファイル3（技術書企画書レビュー・技術書講評・技術書校正） |
| 構成レビューの技術書版 | #96（ボードのジャンル対応）とセットで追加（レーン定義と結合するため） |
| 技術書執筆フレームワーク | プロンプト直書き（story-engineering 相当のスキル化はしない。必要になれば別Issue） |
| レビュー実行時の再検証 | `resolveProfileForPhase` はジャンルで絞らない（クロスジャンル手動選択可の仕様と整合・無変更） |
| 講評の入力充足チェック | writing_genre は加えない（SPEC-genre の決定を踏襲） |

## 3. 既定選択アルゴリズム

`lib/genre-priority.ts`（純関数・review / critique / proofread の3経路で共用）:

- `genreRank`: 一致=0 → 共通(null)=1 → 他ジャンル=2
- `sortByGenrePriority`: 取得後のJS側ソート。**PostgREST の order() では「一致優先」を表現できない**ため。
  Array.sort は安定ソートなので、DB側の並び（is_default desc → created_at）が同順位内で維持される

適用箇所と既定選択の決まり方:

| 経路 | ジャンルの解決 | 既定選択 |
|---|---|---|
| レビューパネル（`getReviewPanelBootstrap`） | `resolveTarget` で projectId 解決 → proposals.writing_genre | `initialProfileId = running最新 ?? ソート後先頭`（旧「is_default を探す」はソート後先頭に包含） |
| 講評（`getCritiqueBootstrap`） | 取得済みの proposals select に追加 | UI が一覧先頭を既定採用（無変更）。サーバーソートがそのまま既定になる |
| 校正（/api/proofread） | manuscript_links → projects → proposals | 標準行（is_default=true）限定でソート後先頭を採用（§5） |
| 設定画面 | プロジェクト文脈なし | ソート変更なし（is_default desc → created_at のまま）。ジャンルはラベル表示のみ |

企画書行が存在しない場合は 'novel' にフォールバックする。

「その他」ジャンルの帰結（意図した設計）: 一致行が存在しないため、共通（校正・校閲等）→
他ジャンル（created_at 順＝novel が先）となり、各フェーズの既定は現行と同じになる。

## 4. 標準行のジャンル一覧

| 種別 | 名前 | writing_genre |
|---|---|---|
| ペルソナ | 担当編集 / 読者代表 / 近所の書店員 | novel |
| ペルソナ | 校正さん / アシスタント / 喫茶店のマスター / イラストレーター | 共通（null） |
| ペルソナ | **技術書編集者**（high/all）/ **エンジニア読者**（medium/manuscript_plus_target） | tech_book（新規） |
| プロファイル | 企画書レビュー / キャラクターレビュー / 構成レビュー / シーンレビュー / 読者講評 / 売り込み分析 / あらすじ作成 / キャッチコピー作成 | novel |
| プロファイル | 校正・校閲 | 共通（null） |
| プロファイル | **技術書企画書レビュー**（proposal→技術書編集者）/ **技術書講評**（manuscript→エンジニア読者）/ **技術書校正**（proofreading→校正さん） | tech_book（新規） |

固定UUIDは `lib/ai/personas.ts` の定数群に追加（ペルソナ …0008/0009、プロファイル …1010〜1012）。
シードは `supabase/migrations/20260725000003_genre_personas_and_profiles.sql`。
既存行のタグ付けUPDATEは標準行がRLSで書き込み不可のため同マイグレーション内で実施。

## 5. 校正のサーバー側ジャンル解決

- 従来: `PROOFREADING_PROFILE_ID` の固定UUID直引き（選択UIなし・実質標準固定）
- 変更後: `target_phase='proofreading'` かつ **`is_default=true`（標準行限定）** を created_at 順で取得し、
  `sortByGenrePriority` の先頭を採用。担当ペルソナは従来どおり `default_persona_id` 経由
- 標準行限定の理由: 選択UIがない以上、ユーザー作成の proofreading プロファイルが
  暗黙に校正経路を乗っ取らない従来セマンティクスを保つため
- 帰結: 技術書プロジェクト→技術書校正（コードブロック校正除外・技術用語の表記統一）、
  小説・その他→校正・校閲（従来どおり）

## 6. 技術書プロンプトの設計方針

既存様式（`# 今回の仕事:` → `## 観点` → `## 進め方` → `## 出力形式`・常体・800〜1500字）を踏襲。

- **技術書企画書レビュー**（ゲート系）: テーマの一文性と差別化／対象読者と前提知識の下限／
  本のゴールの行動レベル検証可能性／イベント締切・ページ数に対するスコープ実現可能性（学習曲線）／目次案。
  末尾判定行は既存と**一字一句同一**（`判定: 承認` / `判定: 差し戻し`。parseVerdict が構造参照）
- **技術書講評**（判定行なし）: 詰まった箇所＝前提知識の穴を体験順に／コード例の追従可能性／
  学びの実感／人に薦めるか。技術的正誤の検証はしない（感想として挙げるにとどめる）
- **技術書校正**: 出力形式節は校正・校閲（20260713000003 改訂版）と**一字一句同一**
  （streamObject の original_text/suggested_text/reason 互換）。観点に技術用語の表記統一・文体統一を追加し、
  **コードブロック・インラインコード・コマンド出力は校正対象外**（本文の説明とコードの食い違いは指摘可）
- **ペルソナ**: 技術書編集者は「技術的正確さは自分で実行検証できない前提で、動作確認を促す形で指摘」を明記。
  エンジニア読者は設定資料を読まない（読者代表と同じ思想）

## 7. 設定画面

- 一覧: プロファイル・ペルソナのメタ行に「ジャンル: 共通/小説/技術書/その他」を表示（`genreScopeLabel`）
- 編集ダイアログ: 「対象ジャンル」select（既定「共通（全ジャンル）」= null）
- 複製: `writing_genre` もコピー対象（技術書プロファイルの複製はジャンル一致扱いのまま）
- 標準行は従来どおり読み取り専用＋複製のみ

## 8. スコープ外

- 構成レビュー・ビートボードのジャンル対応 → #96
- 講評・校正のプロファイル選択UIの相互乗り入れ（SPEC-dashboard-critique-settings §7 の決定を維持。
  校正は選択UIなしのままサーバー解決のみ）
- ダッシュボード相談（conversational）のジャンル対応（プロジェクト横断のため概念が紐づかない）
- 技術書向けの売り込み分析・あらすじ・キャッチコピー（実需が出たらIssue起票）

## 9. E2E検証手順

1. 技術書プロジェクト: 企画書レビューパネルの初期選択=技術書企画書レビュー・担当=技術書編集者。
   一覧順が 一致→共通→小説 になっている
2. 技術書プロジェクト: 講評パネルの初期選択=技術書講評・担当=エンジニア読者
3. 技術書プロジェクト: 校正実行が技術書校正のプロンプトで走る（構造化提案の保存互換を確認）
4. 小説プロジェクト回帰: 企画書レビュー=企画書レビュー、講評=読者講評、校正=校正・校閲。
   running セッション優先の既定選択が維持される
5. クロスジャンル: 技術書プロジェクトで小説プロファイルを手動選択して実行できる
6. 設定画面: ジャンル表示・複製でジャンルコピー・新規作成で「共通」保存
7. 回帰: 講評の入力充足フェイルクローズ（内容ジャンル/ターゲット層未設定）
