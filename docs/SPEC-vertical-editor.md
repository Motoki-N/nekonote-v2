# SPEC-vertical-editor: 縦書きエディタ（執筆・組版・入稿PDF）

作成日: 2026-07-15
ステータス: **確定**（2026-07-16 インタビュー済み。§8 参照）

## 1. 目的

小説の執筆から印刷所への入稿までを、GitHub上の原稿リポジトリを軸に一気通貫で支援する縦書きエディタを提供する。
要求仕様 §7 で「開発コストが大きいため既存ソフトを活用（将来的には実装したい）」としてスコープ外に置いた縦書きエディタ機能の、将来実装フェーズの仕様である。

### 1.1 コンセプト：「エディタで組版しない」

- 執筆は**横書きプレーンテキスト**（VFM = Vivliostyle Flavored Markdown）で行い、タイピングの快適さに全振りする
- 縦書き表示・ページ分割・ノンブル・目次・奥付・入稿PDFはすべて **Vivliostyle（CSS組版エンジン）** に委譲する
- 組版エンジン（禁則処理・ぶら下がり・ルビの行間調整・ページ分割）は**絶対に自作しない**。自作範囲は「執筆UI」と「接続部分」のみ
- 画面プレビューと入稿PDFを同一エンジンで生成することで、「プレビューと出力がズレる」事故を原理的に排除する

### 1.2 既存ツールとの差別化（開発動機）

| ツール | 強み | 欠けているもの |
|---|---|---|
| 縦式（iOS/Mac） | 軽快、入稿レベルのPDF出力 | Git管理不可、コメント機能なし、Apple限定 |
| TATEditor（Win中心） | アウトライン・ルビ・原稿用紙レイアウト | クラウド/Git連携なし、目次・奥付は手作業 |
| Nola（Web） | プロット管理・マルチデバイス | 独自クラウドにロックイン、入稿PDF不可 |
| Vivliostyle（CSS組版） | 入稿品質のPDF生成、theme-bunkoで文庫組版が既製 | 執筆UIを持たない |

「執筆体験」勢はGit管理と入稿出力が弱く、「組版」勢は執筆UIがない。両者を繋ぐ層が空白であり、そこを本エディタが埋める。原稿がGitHubにあることで、ネコノテのAIレビュー・進捗管理とそのまま接続できる点が既存ツールにない独自価値となる。

## 2. 要件（5項目・確定）

1. **原稿データはGitHubで管理**（ネコノテとのシナジー考慮）
2. **ノンブル・目次・奥付などの作成機能**（印刷所にそのまま提出できる）
3. **PDFの書き出し機能**（印刷所にそのまま提出できる）
4. **入力とプレビューの分離**（タイピングのしやすさとレイアウト確認のしやすさの両立）
5. **コメント機能**（プレビューや出力には影響しない、構成のメモなどを書く）

## 3. 全体アーキテクチャ

```
GitHubリポジトリ（原稿モノレポ・要求仕様 §3.4 の構成を継承）
 my-manuscripts/
 ├─ {プロジェクト名}/
 │   ├─ manuscripts/
 │   │   ├─ 01-prologue.md      … 本文（VFM形式、章ごとに1ファイル）
 │   │   ├─ 02-chapter1.md
 │   │   └─ ...
 │   ├─ book.config.js          … 書誌情報（タイトル・著者・判型・組み設定）
 │   └─ themes/                 … 組版CSS（文庫判・B6判テンプレート）
 └─ .github/workflows/build-pdf.yml … タグpush → 入稿PDF自動生成
        │
        ├──▶ 縦書きエディタ（本SPEC）… 執筆・プレビュー・コメント・コミット
        └──▶ ネコノテAI … 同じmdを読んでレビュー・進捗管理・校正
```

- 章ファイル分割により「Gitの差分」「ネコノテのレビュー単位」「目次の章立て」が1対1で対応する
- ファイル名の数字プレフィックスで章順を表現する（`book.config.js` の entry 列挙を正とし、プレフィックスは可読性のための慣習とする）

### 3.1 原稿フォーマット: VFM（Vivliostyle Flavored Markdown）

- プレーンテキストなので diff が読める＝ネコノテのAIレビュー・校正コミットがそのまま機能する
- ルビ: `{漢字|かんじ}`（VFM標準記法）
- 傍点・圏点: テーマCSS＋クラス指定で対応（記法はPhase 3で入力補助を設計）
- 改ページ・扉・空行などはVFMのフロントマター＋テーマCSSの規約で表現する

### 3.2 役割分担（ネコノテとの棲み分け）

| 関心事 | 担当 |
|---|---|
| 執筆・組版・入稿 | 縦書きエディタ（本SPEC） |
| AIレビュー・校正・進捗管理 | ネコノテ（既存機能） |
| 原稿の実体・履歴 | GitHubリポジトリ（共有） |

ネコノテ側は原稿を読み込み専用で取得する既存方針（要求仕様 §3.4）を変えない。書き込み（保存＝コミット）は縦書きエディタの責務とする。

## 4. 各要件の実現方式

### 4.1 GitHub管理（要件①）

- エディタはGitHub API（Contents API）でリポジトリを直接読み書きする。ローカルclone は持たない
- **保存＝コミット**。明示保存操作でコミットメッセージ（自動生成＋編集可）付きコミットを作成する
- 未保存の編集はブラウザ（IndexedDB）に自動待避し、リロード・クラッシュで失わない
- 推敲はブランチ＋PRで行い、ネコノテのAIレビューをPR上で受ける運用を可能にする（エディタからのブランチ切替・作成をサポート）
- 認証はネコノテの `GitCredentialProvider` 抽象（要求仕様 §3.4）を共有し、**共通トークンをwriteスコープへ昇格**する（論点2で確定。要求仕様 §5 でネコノテ自体も「校正コミットの書き戻し」でwriteを予定しており整合）。トークン権限の変更は security-reviewer ゲートの対象（§9）

### 4.2 ノンブル・目次・奥付（要件②）

すべて CSS Paged Media の守備範囲とし、手動レイアウトを持たない。

- **ノンブル・柱**: `@page` margin box（`@bottom-center { content: counter(page) }` 等）で自動付与。偶奇ページでの小口/ノド側出し分けに対応
- **目次**: 章ファイルの見出しから自動生成。ページ番号は `target-counter()` で組版時に自動解決（手動更新ゼロ）
- **奥付**: `book.config.js` の書誌情報（書名・著者・発行日・発行者・連絡先・印刷所名）からテンプレートで生成
- **前付・後付**: 扉・中扉・あとがきをテンプレートとして提供
- **入稿制約の検証**: ビルド時に総ページ数を検査し、4の倍数（印刷所標準）になるよう白ページの自動挿入を提案する

### 4.3 入稿PDF書き出し（要件③）

- `@vivliostyle/cli` でPDF生成 → `press-ready` でフォント埋め込み・PDF/X-1a変換・グレースケール検証
- headless Chromium が必要で重いため、**Vercel上では実行しない。GitHub Actions で実行する**
  - 入稿タグ（例: `v1.0-nyuko`）のpushをトリガーに、入稿PDFを生成してGitHub Releasesに添付
  - 「どのコミットの原稿を入稿したか」がGitで完全に追跡できる
- エディタUIからは「入稿ビルドを実行」ボタンでタグ作成→Actions起動→完了通知→ReleasesのPDFリンク表示、まで面倒を見る
- 判型・基本版面（文字数×行数・余白・フォント）は `book.config.js` ＋テーマCSSで定義。初期テーマは**文庫判（A6）・B6判**の2種（論点5で確定）。文庫判は `@vivliostyle/theme-bunko` をほぼそのまま、B6判は theme-bunko にページサイズ・版面（文字数×行数）調整を加えた派生テーマとして用意する

### 4.4 入力とプレビューの分離（要件④）

2ペイン構成とする。

- **入力ペイン（横書き）**: CodeMirror 6 ベースのプレーンテキストエディタ
  - 縦書き入力のIME相性問題を根本回避し、タイピング体験を最優先する
  - VFM記法（ルビ・コメント・見出し）のシンタックスハイライト
  - 字数カウント（本文のみ。コメント・記法は除外）＋ページ数見積り表示
- **プレビューペイン（縦書き）**: Vivliostyle Viewer を埋め込み、**実際の判型・ページ分割・ノンブル込み**で表示
  - 再組版は打鍵ごとではなく、保存時＋数秒のデバウンスで実行（組版は重い。入力の軽快さを損なわない）
  - 編集中の章のみを対象とした部分プレビュー（高速）と、書籍全体プレビュー（目次・ノンブル確認用）を切り替え可能にする
- レイアウト: デスクトップ=左右2ペイン（比率可変・プレビュー折りたたみ可）、スマホ=タブ切替

### 4.5 コメント機能（要件⑤）

- 記法は **HTMLコメント** をそのまま使う: `<!-- ここ、三章の伏線と矛盾してないか要確認 -->`
- VFM→HTML→PDF のどの段階でも出力に一切現れない（「プレビュー・出力に影響しない」を仕様レベルで満たす）
- 入力ペインでは色付き表示。サイドバーにコメント一覧（クリックで該当行へジャンプ）
- テキスト埋め込みなのでGit管理され、ネコノテのAIが「作者のメモ」として読める（構成メモを踏まえたレビューが可能になる。ネコノテ側の対応はスコープ外・将来連携）
- 行コメント（行全体をコメントアウト＝没にした文章の保留）も同記法で自然に表現できる

### 4.6 挿絵・画像（追加要件）

画像ファイルもリポジトリに置き、Markdown標準記法（`![](../images/sashie-01.png)`）で本文に挿入する。技術的な壁はVivliostyleが吸収するため、本エディタで用意するのは「印刷向けテンプレート」と「入稿品質の検査」の2点。

- **挿絵テンプレート**（テーマCSSにクラスとして用意。記法はクラス指定ひとつ）:
  - 全面挿絵: 改ページして単独ページに全面配置。裁ち落とし用に仕上がりサイズ＋3mmの塗り足し込みの寸法をCSSに組み込む
  - 本文中カット: 版面内に収まる小さめの画像＋任意のキャプション
  - 配置制約: 「挿絵は奇数ページ（右ページ）に置く」等のページ位置調整をCSS規約で表現する
- **ビルド時の画像検査**（GitHub Actions 内）:
  - 実効解像度の検査（モノクロ二値600dpi・グレースケール350dpiを目安に、不足時は警告）
  - カラー画像の検出（本文はモノクロ印刷前提。`press-ready` のグレースケール検証をパイプラインに組み込む）
- **画像の管理**: 実体は原稿リポジトリの `images/` に置く（テキストと同じくGit管理・ネコノテと共有）。点数が増えてリポジトリが太る場合はGit LFSへ移行する（§8 論点8）
- エディタUIからの画像アップロード・挿入補助（ドラッグ&ドロップ→コミット＋記法挿入）は Phase 3 で提供する

## 5. 実装方式

- **配置**: ネコノテ第二期と同一アプリ内の別モジュール（`app/(app)/editor/` 配下）として始める（論点1で確定。認証・GitHub連携・テーマ基盤・shadcn/ui を共有し、肥大化したら切り出す）
- **依存追加**: `codemirror`（v6系パッケージ群）、`@vivliostyle/viewer`（プレビュー埋め込み）、VFMパーサ `@vivliostyle/vfm`
- **原稿リポジトリ側の依存**: `@vivliostyle/cli` `press-ready` `@vivliostyle/theme-bunko`（GitHub Actions 内でのみ使用。アプリ本体には入れない）
- **色**: テーマ用CSS変数のみ（プレビューiframe内の組版CSSは例外——印刷物の見た目は書籍テーマが正であり、アプリのライト/ダークに追従させない）
- **エラー処理**: 共通 `AppError`＋共通ハンドラーを踏襲。GitHub APIのレート制限・コンフリクト（他所からのpushとの競合）は日本語メッセージで明示し、コンフリクト時はリモート優先で再取得→ローカル待避分をマージ支援する

### 5.1 開発フェーズ

| フェーズ | 内容 | 完了条件 |
|---|---|---|
| **Phase 1: 骨格** | リポジトリ構造＋VFM＋GitHub ActionsでのPDFビルドパイプラインのみ（エディタなし）。挿絵テンプレート＋画像検査を含む | VS Codeで書いてpushすれば入稿品質のPDFがReleasesに出る。手持ち原稿で組版品質を検証 |
| **Phase 2: エディタ** | 2ペインWebエディタ（CodeMirror＋Vivliostyle Viewer）＋GitHub読み書き | ブラウザだけで執筆→保存（コミット）→縦書きプレビューが回る |
| **Phase 3: 快適性** | コメントUI・ルビ入力補助・画像アップロード/挿入補助・字数/ページ数見積り・目次/奥付の設定UI | §2 の5要件＋挿絵（§4.6）をすべてUI上で満たす |
| **Phase 4: ネコノテ連携** | エディタ⇄ネコノテの相互リンク、レビュー結果のコメント書き戻し等 | 別途SPEC策定 |

Phase 1 を先行させるのは、最大のリスク（Vivliostyleの組版品質が入稿に耐えるか）を最小コストで検証するため。Phase 1 の成果物は原稿リポジトリ側のテンプレートであり、アプリのコード変更をほぼ伴わない。

## 6. データ

- **原稿・設定・コメントの実体はすべてGitHubリポジトリ**。アプリDBには置かない（第一期の反省「原稿のDB管理は差分がわかりにくい」を徹底）
- アプリDB（Supabase）に追加するのは、プロジェクトと原稿リポジトリ/パスの対応付け等の最小限のメタデータのみ
- **スキーマ変更が必要になった場合は、規約どおりプランモードで承認を得てからマイグレーション経由で行う**（本草案の段階では新テーブルを確定しない）
- 未保存編集のブラウザ待避（IndexedDB）はキャッシュであり、正は常にGitHub側

## 7. スコープ外

- 組版エンジンの自作（禁則処理・ページ分割等はVivliostyleに全面委譲）
- 縦書きでの直接入力（入力ペインは横書きのみ）
- EPUB等の電子書籍出力（Vivliostyleの能力的には将来可能。入稿PDFを先に完成させる）
- リアルタイム共同編集
- ネコノテ側のレビュー機能変更（Phase 4 で別途SPEC）
- 挿絵の高度なレイアウト（見開きまたぎ・本文の回り込み・カラー口絵など。基本の挿絵は §4.6 でスコープ内）
- 縦中横・割注などの高度な組版指定のUI化（テーマCSS＋手書き記法では可能。UIはPhase 3以降で検討）

## 8. 決定事項（インタビュー結果・2026-07-16）

| # | 論点 | 決定 |
|---|---|---|
| 1 | 配置 | **ネコノテ同一アプリ内モジュール**（`app/(app)/editor/` 配下）。認証・GitHub連携・UI基盤を共有し、肥大化したら切り出す |
| 2 | GitHub書き込み権限 | **共通トークンをwriteスコープへ昇格**。要求仕様のネコノテ「校正コミット書き戻し」計画と整合し、管理も1本で済む。security-reviewer ゲート必須（§9） |
| 3 | プレビューの既定 | **編集章のみ部分プレビュー**。全体組版（目次・通しノンブル確認）は明示操作。速度実測後に再判断 |
| 4 | コメント記法 | **HTMLコメント（`<!-- -->`）のみ**。VFM標準で出力から確実に消える。打ちにくさはショートカット（入力補助）で解決 |
| 5 | 対応判型の初期セット | **文庫判（A6）＋B6判**の2種。新書判は不採用（必要になった時点でテーマ追加） |
| 6 | 入稿ビルドの起動方式 | **エディタUIからも起動**（中身はタグ作成の代行→Actions起動→完了通知→PDFリンク表示）。タグ直pushも引き続き有効 |
| 7 | book.config.js の編集UI | **Phase 3でフォーム化**（奥付・判型・組み設定）。Phase 1・2 の間はテキスト直編集でしのぐ |
| 8 | 画像の格納方式 | **通常のGit管理**で開始。リポジトリが太ったら Git LFS へ移行（後から移行可能） |

## 9. セキュリティ・ゲート

- GitHubトークンのスコープ変更（read→write）・保存方式の変更は、規約どおり **security-reviewer の通過を省略しない**
- GitHub Actions のワークフローはフォーク由来のPRでは実行しない設定とする（secrets流出防止。原稿リポジトリはprivate前提だが明示する）
- 入稿PDF（Releases成果物）はprivateリポジトリ内に留まることを確認する

## 10. E2E検証手順（Phase 1〜3 の完了条件）

1. **Phase 1**: 原稿リポジトリにVFM原稿＋設定を置きタグをpush → Actionsが入稿PDF（PDF/X-1a・フォント埋め込み済み）をReleasesに添付。ノンブル・目次（ページ番号自動）・奥付が正しく組まれている。ルビ `{漢字|かんじ}` が正しく組版される。総ページ数が4の倍数でない場合に検知される。全面挿絵が塗り足し込みの寸法で単独ページに組まれ、低解像度・カラー画像を混ぜるとビルド時に警告が出る
2. **Phase 2**: エディタで章を開く→編集→保存でコミットが作られる→リロードで復元。未保存のままリロードしてもIndexedDB待避分が復元される。縦書きプレビューが判型どおりのページ分割・ノンブルで表示される。他所からのpushと競合した場合に日本語エラー＋マージ支援が出る
3. **Phase 3**: コメント `<!-- -->` がエディタで色付き表示・一覧からジャンプでき、プレビューとPDFのどちらにも一切現れない。ルビ入力補助で記法を知らなくてもルビが振れる。字数カウントがコメント・記法を除外して本文のみを数える。画像をドラッグ&ドロップすると `images/` へのコミット＋挿入記法の追記が行われ、プレビューに反映される。エディタUIから入稿ビルドを起動しReleasesのPDFに到達できる
4. **回帰**: ネコノテ既存機能（レビュー・進捗管理）が同一リポジトリの原稿に対して従来どおり動作する
