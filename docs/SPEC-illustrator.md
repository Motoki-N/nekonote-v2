# SPEC-illustrator: AIイラストレーター（アトリエ・イラスト依頼）

作成日: 2026-07-17（インタビュー駆動で策定）
ステータス: **確定**（2026-07-17 レビュー済み）
起点: Issue #13「AIエージェント『イラストレーター』の追加」

## 1. 目的

原稿・設定資料を参照しつつ、作家のリクエスト（カラー/モノクロ・構図・描いてほしい対象）に
応じてイラストを生成する新ペルソナ「イラストレーター」を追加する。生成対象は4種:

- **表紙イラスト**
- **文中の挿絵**（原稿の指定シーンに合わせて描く）
- **キャラクターイラスト**（キャラクター設定資料に載せる想定）
- **コンセプトアート**（世界観を表すイラスト）

要求仕様書のスコープ外だった「表紙・挿絵の生成機能」を、ペルソナ制AIエージェントの
枠組みで実現する。イラスト作成は作家の仕事の範囲外であり、AI活用が妥当な領域。

## 2. 決定事項（インタビュー結果・3巡）

| 論点 | 決定 |
|---|---|
| 画面形態 | **独立ページ「アトリエ」**（`/atelier`）。グローバルナビに追加し、ページ内でプロジェクトを選択。機能の独自色が高いため既存画面に同居させない |
| 生成フロー | **2段階方式**。①イラストレーター（LLM）が資料を読んで**複数案（2〜3案）**を提案 → ②ユーザーが選択・微調整して画像モデルで生成。クオリティコントロールを案の段階で効かせる |
| 参照資料 | **依頼種別ごとに自動選択**（§5.2）。全部盛りにせず、種別に最適な文脈だけ渡す |
| シーン指定（挿絵） | **原稿ファイルを選択＋自由記述**。GitHubの原稿ツリーから1ファイルを選び、「どの場面か」を言葉で補足 |
| 参照画像 | **初版から対応**。ギャラリーの既存イラストを1枚添付して「このキャラで挿絵を」と依頼できる（キャラクター一貫性の要） |
| 表紙の文字入れ | **絵のみ生成→確定後に文字入れを編集依頼**。参照画像の仕組みの応用（生成済み画像＋「タイトル○○を入れて」指示）で実現 |
| 画像モデル | **デフォルトは Google（Gemini画像生成系）**。キャラ一貫性・生成速度（10〜15秒）・参照画像入力への対応が用途に合う。`ai_model_settings` に新capability `image` を追加し、設定画面で差し替え可能に |
| 枚数・上限 | **1回1枚**。レートリミットは**分2回・日20回**（既存 `enforceRateLimit` 流用） |
| 保存・管理 | **全生成を自動保存**（Supabase Storage）＋**ギャラリー**で一覧・ダウンロード・削除。失敗作も比較検討の材料として残る |
| プロンプトの保存 | **依頼プロンプトを画像とセットで保存**し、ギャラリーで**説明文として表示**する。追加依頼（編集・リテイク）時の参考としてフォームへ引き継げる |
| タイトル | 各画像に**ユーザーが任意で編集できるタイトル**を持たせる。初期値は**プロジェクト名＋種別**（例:「星の航路 表紙」）。重複は許容（絵と説明文で判別できる） |
| 削除 | **確認ダイアログ＋物理削除**（Storageからも消す）。ごみ箱は作らない（画像は再生成できる）。他画像の参照元になっている場合は警告を添える |

## 3. インタビューで聞かずに設計原則で決めた点（レビューで確認）

- **ペルソナ「イラストレーター」を標準同梱で追加**（ai_capability: high・persona_type は新値
  `illustrator`）。`conversational` にするとダッシュボード相談への混入を個別ガードで防ぐ必要が
  生じるため、型で分離する。description（性格・口調・作画方針）は他ペルソナ同様ユーザー編集可
- **reference_scope は `all`**。実際の参照は §5.2 の種別ごとの組み立てをコードが担う
  （SPEC-conversational-personas §4.2 と同じ「コードが役割に応じて同梱する」解釈）
- **案出し（第1段階）はDBに保存しない**。採用されて画像になった案だけが `illustrations` 行に
  残る（手帳→浄書: 読み捨ての提案を構造化しない）
- **生成は同期実行**（`maxDuration 60` のAPI Route）。デフォルトのGemini系は10〜15秒で収まる。
  遅いモデル（gpt-image系）に差し替えた場合のタイムアウトは既知の制約として扱い、非同期化は
  必要になってから（頼まれていない最適化をしない）
- **失敗した生成は保存しない**（レートリミットにはカウントされる）。`illustrations` に
  status 列は持たない＝行が存在する時点で画像がある
- **編集依頼（文字入れ・修正リテイク）は新規生成と同じエンドポイント**。参照画像＋指示文の
  組を渡すか否かの違いだけで、フローを分岐させない
- **アスペクト比は種別ごとのデフォルト＋依頼時変更可**: 表紙・挿絵・キャラクター=縦（2:3）、
  コンセプトアート=横（16:9）。選択肢は縦/横/正方形の3種
- **画像の表示は短寿命の署名URL**（バケットは非公開）。公開URLにしない

## 4. 画面とUX

### 4.1 アトリエページ（`/atelier`）

- グローバルナビに「アトリエ」を追加
- ページ上部に**プロジェクトセレクタ**（自分のプロジェクト。既定値はダッシュボードの
  選択中プロジェクト `user_settings.selected_project_id`、なければ最新更新）
- 2ペイン構成: **依頼フォーム＋案・生成結果**（主）と**ギャラリー**（従）。
  lg未満は縦積み。テーマCSS変数のみ使用（色ハードコード禁止）

### 4.2 依頼フォーム

- 種別（表紙/挿絵/キャラクター/コンセプトアート）
- カラー/モノクロ
- アスペクト比（種別デフォルト自動設定・変更可）
- 描いてほしい対象・構図・雰囲気（自由記述）
- 挿絵のみ: 原稿ファイル選択（GitHubの原稿ツリー）＋場面の補足（自由記述）
- 参照画像（任意）: ギャラリーから1枚選択。「このキャラ・この絵柄を保って」系の依頼に使う
- 「案を出してもらう」ボタン → 第1段階へ

### 4.3 案の提示と生成

- イラストレーターが2〜3案を提示（各案: タイトル・狙いの説明・画像生成プロンプト）
- ユーザーは案を選択し、**プロンプトを微調整してから**「この案で描いてもらう」
- 生成中はスピナー＋多重送信抑止。完了で画像を表示し、ギャラリーに自動追加
- 生成結果の直下に「修正を依頼」導線: 生成画像を参照画像にした編集依頼
  （文字入れ・ポーズ修正・色味変更など）をワンステップで開始できる

### 4.4 ギャラリー

- 選択中プロジェクトのイラストをグリッド表示（新しい順）。種別バッジ＋**タイトル**付き
- 各画像: 拡大表示・ダウンロード・削除（確認ダイアログ。参照元になっている場合は警告文言）・
  「参照画像にして依頼」
- タイトルは**その場でインライン編集**できる（初期値はサーバーが「プロジェクト名＋種別」で
  自動付与。重複可）
- 拡大表示では**依頼プロンプトを説明文として表示**する。「参照画像にして依頼」から編集依頼を
  始めると、このプロンプトが依頼フォームに引き継がれ、追加依頼の下敷きにできる
- 空状態: イラストレーターの自己紹介と依頼のいざない

## 5. 実装方式

### 5.1 データ（マイグレーション1本・プランモード承認）

```sql
-- 1) personas: persona_type に 'illustrator' を追加（CHECK制約の張り替え）
--    ＋イラストレーターのシード行（固定UUID。lib/ai/personas.ts と対応）

-- 2) ai_model_settings: capability に 'image' を追加（CHECK制約の張り替え）

-- 3) 生成イラストのメタデータ
create table public.illustrations (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null default auth.uid() references auth.users (id) on delete cascade,
  project_id uuid not null references public.projects (id) on delete cascade,
  kind text not null check (kind in ('cover', 'insert', 'character', 'concept')),
  -- ユーザー編集可能なタイトル。初期値はサーバーが「プロジェクト名＋種別」で付与（重複可）
  title text not null,
  -- 依頼内容（カラー/モノクロ・アスペクト比・自由記述・挿絵の対象ファイル等。zodで検証）
  request jsonb not null,
  -- 画像モデルに渡した最終プロンプト（採用案の微調整後）。
  -- ギャラリーの説明文・追加依頼時の引き継ぎ元を兼ねる
  prompt text not null,
  -- 参照画像（編集依頼・キャラ一貫性）。参照元が消えても行は残す
  reference_illustration_id uuid references public.illustrations (id) on delete set null,
  storage_path text not null,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now() -- タイトル編集用（set_updated_at トリガー）
);

-- 4) Storage: 非公開バケット 'illustrations'（png/jpeg/webp・10MB上限。
--    出力形式はモデル依存のため決め打ちにしない）。
--    パスは {user_id}/{illustration_id}.{拡張子}。storage.objects に所有者のみの
--    select / insert / delete ポリシー（RLS）を定義する
```

- enums.ts の `personaTypes` / `aiCapabilities` に対応値を追加（CHECK制約と同時更新の規約）
- `DEFAULT_MODEL_MAP` に `image` 行を追加。モデルIDは実装時にAI SDKの対応状況と
  最新の世代を検証して決める（Gemini画像生成系を第一候補とする）

### 5.2 参照資料の組み立て（種別ごと・サーバー側）

| 種別 | LLMに渡す資料 |
|---|---|
| 表紙 / コンセプトアート | 企画書一式（proposals.content＋紐づくノート群）＋原稿全文（講評と同じ `fetchAllManuscriptContents`。原稿未接続なら企画書のみ） |
| キャラクター | 企画書一式（キャラ設定はここに含まれる。SPEC-character-review §5.1 と同じ解決） |
| 挿絵 | 選択した原稿ファイルの全文＋ユーザーの場面補足 |

### 5.3 API Route（2本）

- **POST `/api/illustration/propose`**（第1段階・案出し）
  - 認証 → レートリミット（分5回・日50回。テキスト生成なので generate より緩い）
  - zod検証 → §5.2 の資料組み立て → capability **high** のテキストモデルで
    `generateObject`（2〜3案: title / description / imagePrompt）
  - system はイラストレーターの description＋種別ごとの作画指針
- **POST `/api/illustration/generate`**（第2段階・画像生成）
  - 認証 → レートリミット（**分2回・日20回**）
  - zod検証 → capability **image** のモデルを解決 → 参照画像があればStorageから取得して
    入力に添付 → 生成 → Storageアップロード → `illustrations` insert → 署名URL返却
  - 初期タイトルは**サーバー側で**「プロジェクト名＋種別」から組み立てて insert する
    （クライアント任せにしない）
  - `maxDuration = 60`

### 5.4 Server Actions（`lib/actions/illustrations.ts`）

- `listIllustrations(projectId)`: RLS越しの一覧（タイトル・プロンプト含む）＋署名URL発行
- `updateIllustrationTitle(id, title)`: タイトルのインライン編集（RLSが所有確認を担う。
  空文字は不可・重複は許容）
- `deleteIllustration(id)`: 所有確認（RLS）→ Storage実体削除 → 行削除。
  参照元として使われているかを返し、クライアントの確認ダイアログで警告に使う
- `deleteIllustrations(ids)`: 一括削除（1〜50件・採用⛳は除外。§12・Issue #332）

### 5.5 設定画面

- モデル設定（`components/settings/model-settings.tsx`・labels.ts）に `image` 枠を追加
- ペルソナ一覧にイラストレーターが並ぶ（description 編集は既存機構がそのまま効く）

## 6. セキュリティ（security-reviewer 必須ゲート）

- `illustrations` テーブルとStorageバケットのRLS（所有者のみ）
- 署名URLの寿命は短く（1時間目安）。公開バケットにしない
- propose / generate の入力はzod検証。参照画像IDはRLS越しの取得で所有確認
- レートリミットでコスト暴走を防止（画像生成は本アプリ最高コストの操作）

## 7. スコープ外（今回はやらない）

- チャット（相談パネル）への組み込み・チャット内画像表示
- 1回複数枚の同時生成
- 生成画像のノート・企画書への添付
- 原稿からの挿絵位置の自動提案
- ごみ箱（復元可能な削除）
- ~~外部画像のアップロード（参照画像はアプリ内生成物のみ）~~ → **Issue #104 でスコープ入り**（§9）

## 9. 追補: 参照画像のアップロード（Issue #104・2026-07-23）

生成イラストの雰囲気・キャラを統一するためのリファレンスとして、外部画像を
アップロードして参照画像に使えるようにする（§7 のスコープ外項目を昇格）。

- **保存方式**: アップロード画像は `illustrations` の1行として保存する。kind に保存専用の
  新値 **`reference`**（表示ラベル「参照用」）を追加（CHECK制約の張り替え。20260723000001）。
  既存の参照フロー（`reference_illustration_id`）・署名URL・ギャラリー・削除（被参照警告つき）を
  そのまま流用し、生成APIには変更を入れない
- **`reference` は生成の依頼種別ではない**: `illustrationKinds`（zod）には追加せず、
  propose / generate の入力からは遮断する。DB保存されうる種別の全体は
  `storedIllustrationKinds` として型を分ける
- **入口**: ギャラリーヘッダーの「参照画像をアップロード」ボタン（Server Action
  `uploadReferenceImage`）。受け入れは png / jpeg / webp・10MB以下
  （バケットの allowed_mime_types / file_size_limit と同値の事前検証＝多層防御）。
  レートリミットは分10回・日100回
- **行の中身**: prompt は空文字（ギャラリーの説明文・依頼フォームへのプロンプト引き継ぎは
  空のときスキップ）。request は出所の記録のみ（`{ source: 'upload', fileName }`）。
  初期タイトルはファイル名（拡張子抜き・100字以内）、空ならプロジェクト名＋「参照用」

## 10. 追補: 画風の指定（Issue #254・2026-10-22）

イラストのテイストを揃えるため、依頼フォームに「画風」の選択肢を追加する。
これまで画風は「描いてほしい内容」の自由記述か、案出しの LLM 任せだった。

- **選択肢**: 小説の表紙・挿絵向けに厳選した17種＋「指定なし」（既定）。系統見出しつきの
  選択欄（装画・絵画 / 手描き・画材 / 絵本・児童書 / 版画・印刷 / 線画・漫画・雑誌）。
  Webサービス向け・アイコン・教材系のような小説に使わない画風は置かない。
  ユーザー定義の画風（カスタム登録）はスコープ外（DBが要るため）
- **定義の置き場所**: ID・表示名・系統は `lib/schemas/illustration.ts`（クライアントと共用）、
  画像モデルへの英語の STYLE 文は `lib/ai/illustration-styles.ts`（サーバーのみ）。
  STYLE 文は外部記事の文面を転載せず、自前で書き起こす（本リポジトリは public）
- **反映方法（2段構え）**:
  1. 案出し（propose）の LLM に画風名を伝え、構図・光・色調を画風に合わせさせる。
     画風・画材・タッチの記述は imagePrompt に書かせない（2. と重複・矛盾させないため）
  2. propose API が、画風ごとの英語 STYLE ブロックを各案の imagePrompt の末尾へ機械的に付加する。
     プロンプト欄に見えるので微調整でき、保存プロンプトにも残るためリテイクで再現できる
- **「手描き感を残す」チェックボックス**（既定オフ）: オンなら、手描きの揺らぎを残す指示と
  ツルツルしたAIイラストを避ける指示を STYLE ブロックに足す。画風「指定なし」でも使える
- **カラー/モノクロとの矛盾**: 組み合わせは制限しない（例: モノクロ＋水彩）。STYLE ブロックの
  最後にカラー/モノクロの指示を置き、画風が示唆する色より優先させる。LLM への指示にも明記する
- **案出しを経ない生成**: プロンプト欄が正。直接書いたプロンプトには STYLE ブロックを付加しない
  （画風の選択欄の下に「案出しのときにプロンプト末尾へ付く」旨を表示する）
- **保存**: 依頼内容の `request.style` / `request.humanMade` として jsonb に入る
  （**マイグレーション不要**。既存行・アップロード参照画像は「指定なし」扱い）
- **引き継ぎ**: 「参照画像にして依頼」では、参照元の画風も選択欄へ復元する
  （`IllustrationItem.style`。参照元が指定なしなら入力中の選択を消さない）。
  ギャラリーでの画風表示・絞り込みは #328（☆・⛳）の絞り込み欄で一緒に扱う

## 11. 追補: お気に入り☆と原稿への配置・採用マーク⛳（Issue #328・2026-10-22）

生成画像を選別し（☆）、縦書きエディタから直接原稿へ配置して、どの画像が本線の原稿に
載っているかをギャラリーで分かるようにする（⛳）。§7 の「ノート・企画書への添付」は引き続きスコープ外で、
対象は原稿（縦書きエディタ）のみ。

- **データ**（マイグレーション 20261022000001・純追加型・RLS 変更なし）: `illustrations` に
  `is_favorite`（既定 false）／`placed_at`（⛳）／`placed_image_path`（リポジトリ内のコピー先）を追加
- **☆お気に入り**: ギャラリーのカードの☆で切り替える（`setIllustrationFavorite`）。
  ギャラリーの絞り込みは「すべて／お気に入り／採用」の3つ（件数つき・クライアント側で絞る）。
  画風（§10）はカードと拡大表示に表示のみ（画風での絞り込みは作らない）
- **原稿への配置**: エディタのツールバー「アトリエ」→ ピッカー（☆で絞り込み可。kind `reference` は出さない）→
  既存の挿入ダイアログ。Server Action `placeIllustration` が Storage から取り出して
  `images/atelier-<UUID>.<拡張子>` へコピーコミットする。Storage は非公開・署名URLは短寿命で、
  組版ビルドにはリポジトリ内の実ファイルが要るため、Storage を直接参照しない
  - 配置できるのはそのプロジェクトのイラストのみ（RLS 越しの取得＋`project_id` 一致）
  - ファイル名に UUID が入るので、同名が既にあれば同じイラストとみなし再コミットしない（生成画像は不変）
- **⛳の意味は「既定ブランチ（本線）の原稿に載っている画像」**:
  - 既定ブランチへ配置したときだけ `placed_at` を付ける。作業ブランチへの配置では `placed_image_path` だけ記録し、
    マージ後の走査で⛳が付く。既定ブランチかどうかはサーバーが `getDefaultBranch` と比較して判定する
  - 記録の失敗は配置（コミット済み）を失敗させない（エディタが補足トーストで走査を案内する）
- **原稿の配置状況の走査**: ギャラリーの「原稿の配置状況を更新」（`syncIllustrationPlacements`）。
  既定ブランチの `manuscripts/*.md` を読み（`getAllChapterContents`）、`images/atelier-<UUID>(-n)?.<拡張子>` の
  記法があるイラストに⛳を付け、ないものから外す。レート制限は分2回・日30回（1回で章数＋2回程度の GitHub API）
  - 既知の制約: HTML コメント内に残った記法も配置済みと判定する／`manuscripts/` の外は見ない
- **削除**: `placed_image_path` があれば確認ダイアログに「リポジトリ内のコピーと原稿の記法は残る」旨を添える

## 12. 追補: ギャラリーの一括削除（Issue #332・2026-10-23）

失敗作や比較用の生成を整理しやすくするため、ギャラリーで複数の画像を選んでまとめて削除できるようにする。
§2 の「確認ダイアログ＋物理削除・ごみ箱なし」はそのまま。単体の削除（カードのゴミ箱）も残す。

- **選択モード**: ギャラリーのヘッダー「選択」で切り替える。モード中はカードにチェックボックスを出し、
  画像のクリックは拡大表示ではなく選択の切り替えになる。操作バーは「n件選択中／表示中をすべて選択／
  選択解除／まとめて削除／完了」。普段のカードは変えない
- **絞り込みとの関係**: 「表示中をすべて選択」は表示中のものだけが対象。絞り込みを切り替えたら選択を解除する
  （見えない画像を選んだまま消す事故を防ぐ）
- **採用⛳は選択不可**（`placed_at` があるもの。「表示中をすべて選択」でも飛ばす）。サーバー側でも対象から外す。
  作業ブランチに配置しただけ（`placed_image_path` のみ）の画像は選択できる
- **確認ダイアログ**: 件数と、選択に含まれる「お気に入り」「他の画像の参照元」「原稿リポジトリにコピー済み」の
  件数を警告として添える
- **Server Action `deleteIllustrations(ids)`**: 1〜50件を検証 → RLS 越しの取得で所有確認 → ⛳を除外 →
  Storage 実体をまとめて削除 → 消せた実体の行だけ削除。戻り値は削除できたid・失敗件数・除外件数
- **部分失敗**: 消せた分だけ消し「n件削除・m件失敗」と通知する。失敗分は選択したまま残し、そのまま再試行できる
- **件数上限**: 1回50件（`BULK_DELETE_MAX`）。超えたら「まとめて削除」を無効にして案内する
