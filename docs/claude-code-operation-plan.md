- **作成日**: 2026-07-12
- **対象**: ネコノテAI 第二期開発（仕様策定〜実装〜レビュー）
- **目的**: 公式ベストプラクティスを第一期KPTの反省に紐づけて運用ルール化し、COMITIA158（12/13）・技術書典21（11/23）に間に合う開発体制を作る

## 1. 前提となる原則（公式ベストプラクティスの要約）

1. **コンテキスト管理が最重要制約**
   コンテキストウィンドウは埋まるほど性能が劣化する。無関係なタスク間は `/clear`。同じ問題で修正指示が2回失敗したら、セッション継続より「学びを反映した新プロンプトで新規セッション」の方がほぼ常に良い。
2. **検証手段を必ず与える**
   テスト・ビルド・リンター・スクリーンショット比較など、pass/fail を返すチェックを与えると Claude が自律的に修正ループを回せる。最もレバレッジが高い施策。
3. **探索 → 計画 → 実装 → コミットの分離**
   プランモードで読み取り専用の探索・計画を先に行い、承認後に実装へ。ただし1文で差分を説明できる小修正は計画をスキップする。
4. **CLAUDE.md は短く、常時必要なものだけ**
   毎セッション読み込まれるため、広く適用される内容のみ。時々しか使わない知識はスキルへ。各行に「削除すると Claude がミスするか？」を問い、しないなら削る。
5. **強制は hooks、知識は skills、調査は subagents**
   CLAUDE.md の指示は助言的、hooks は決定論的に実行される。subagents は別コンテキストで動き、メイン会話を汚さず調査・検証を委任できる。
6. **レビューは別コンテキストで**
   書いた直後のコードにはバイアスがかかる。レビュアーには「正しさと要件に影響するギャップのみ報告」と指示し、過剰設計を防ぐ。
7. **大きめの機能は「インタビュー → SPEC.md → 新セッションで実装」**
   AskUserQuestion によるインタビューで仕様を固め、SPEC を書き出し、クリーンなコンテキストで実装する。良い SPEC は対象ファイル・スコープ外・E2E 検証手順を含む。

### 第一期からの転換点

第一期の「詳細指示書としての CLAUDE.md」（開発速度3〜5倍の成果）は、現在の推奨とは逆方向。第二期は **短い CLAUDE.md ＋ SPEC ファイル ＋ skills ＋ hooks ＋ subagents** の分業構成へ移行する。この移行プロセス自体を技術書典の題材として記録する。

## 2. 第一期KPT → 第二期運用の対応表

| 第一期の課題 (Problem) | 第二期の運用対策 |
|---|---|
| 認証機能の後付けで設計が不安定 | 認証を最初のインタビュー対象にし、SPEC-auth.md を先に確定。認証・RLS変更は security-reviewer subagent を必須ゲート化 |
| スキーマ不整合（user_id エラー等） | スキーマはプランモードで事前合意・承認後にマイグレーション作成。migrations への直接書き込みを hook でブロック |
| エラーハンドリングの後回し | 編集後の typecheck / eslint 自動実行 hook で品質を強制（助言ではなく決定論で担保） |
| 仕様変更の連鎖による大量修正（Day16: 14項目） | 修正2回ルール：2回失敗したら /clear → SPEC 書き直し。1機能=1セッションでスコープ固定 |
| ドキュメントと実装の乖離 | チェックポイントごとに SPEC へ進捗を書き戻す。セッションを唯一の記録にしない |
| テストデータ準備の遅れ | SPEC に E2E 検証手順とテストデータ要件を必須項目として含める |

## 3. リポジトリ構成（Claude Code 関連）

```
nekonote-v2/
├── CLAUDE.md                      # 常駐コンテキスト（50行以内目標）
├── docs/
│   ├── SPEC-auth.md               # 機能別仕様（実装時に @ 参照）
│   ├── SPEC-notes.md              # 草稿→浄書モデル
│   ├── SPEC-beatboard.md          # ビジュアルビートボード
│   ├── SPEC-review-profiles.md    # 編集レビュープロファイル
│   └── dev-log.md                 # 技術書典用：うまくいった/失敗したパターンの記録
├── .claude/
│   ├── settings.json              # hooks・permissions 設定
│   ├── skills/
│   │   ├── story-engineering/     # 6コアコンピテンシーの知識
│   │   ├── draft-to-clean-model/  # 草稿→浄書のデータ設計思想
│   │   └── review-profiles/       # レビュープロファイル仕様
│   ├── agents/
│   │   └── security-reviewer.md   # 認証・RLS 専門レビュアー
│   └── commands/                  # 高頻度ワークフローのスラッシュコマンド
```

### CLAUDE.md に含めるもの（それ以外は含めない）

- 技術スタックの制約: Next.js App Router / TypeScript strict / Supabase / Vercel
- デフォルトと異なるコーディング規約のみ
- 検証コマンド: `npm run typecheck`, `npm run lint`, テスト実行方法
- 「最もシンプルな方法を選ぶ。頼まれていない抽象化を追加しない」
- 猫テーマのトンマナ（UIテキスト関連の作業時のみ影響する場合は skill 化を検討）
- スキーマ変更はプランモード経由で承認を得ること

### hooks（初期セット）

| フック | タイミング | 内容 |
|---|---|---|
| typecheck | ファイル編集後 | `tsc --noEmit` 実行、エラーで通知 |
| lint | ファイル編集後 | `eslint` 実行 |
| migration-guard | 書き込み前 | `supabase/migrations/` への直接書き込みをブロック |

※ hooks は「〜を実行するフックを書いて」と Claude 自身に書かせてよい。

- [x] `docs/dev-log.md` 作成（技術書典用の記録先）

### フェーズ1: 仕様策定（インタビュー駆動）

進め方（全機能共通のサイクル）:

1. プランモードで開始し、「AskUserQuestion で私にインタビューして。自明な質問ではなく、考えていないエッジケースを掘って」と依頼
2. インタビュー完了後、SPEC-*.md に書き出させる（対象ファイル・スコープ外・E2E 検証手順を必須）
3. SPEC をレビュー・修正して確定
4. **新規セッション**で SPEC を @ 参照して実装へ

対象と順序:

1. **SPEC-auth.md** — 認証（第一期最大の反省点のため最優先。セッション切れ・複数デバイス・RLS を掘る）
2. **スキーマ全体** — プランモードでレビュー・承認後にマイグレーション化
3. **SPEC-notes.md** — 草稿→浄書モデル
4. **SPEC-beatboard.md** — ビジュアルビートボード
5. **SPEC-review-profiles.md** — 編集レビュープロファイル（GitHub 連携含む）

### フェーズ2: 実装ループ（1機能 = 1セッションの規律）

日次リズム（7時・13時・18時チェックポイント）との統合:

- **各チェックポイント = セッション境界**。進捗を SPEC / dev-log に書き戻してから `/clear`
- タスクステップごとに Claude にコミットさせる（失敗時の巻き戻し用）
- 実装指示には検証条件を含める（例: 「実装後にテストを実行し、失敗があれば根本原因を修正。テスト出力を見せて」）
- 小修正（1文で説明できる差分）はプランモードを使わず直接依頼
- **修正2回ルール**: 同じ問題で2回修正が失敗したら `/clear` → 学びを反映して SPEC を更新 → 新セッション
- 調査タスクは「subagent で調査して」と委任し、メインコンテキストを実装用に温存

### フェーズ3: レビュー体制（機能完了ごと）

1. **正しさレビュー**: 新規コンテキスト（subagent）で diff を SPEC と突き合わせ。指示文には「要件がすべて実装されているか、スコープ外の変更がないかを確認。正しさと要件に関わるギャップのみ報告。スタイルの好みは報告しない」と明記
2. **セキュリティレビュー**: 認証・RLS・APIキー関連の変更は security-reviewer を必須通過
3. レビュー指摘の修正 → 再レビュー → コミット・デプロイ

このゲート式フロー（提案 → レビュー → 承認 → 次へ）はアプリの「編集レビュープロファイル」と同型。開発プロセスでのドッグフーディングとして設計検証に使い、気づきは dev-log に記録する。

### フェーズ4: Issue駆動の修正自動化フロー（保守・ドッグフーディング期、7/14設計確定）

不具合・要望対応の円滑化のため、GitHub Issue を起点とした修正フローを自動化する（Sprint 6 で構築）。

```
① 人間：Issue起票
        ↓
② AI：影響範囲の分析・調査
        ↓
③ 分岐：アーキテクチャ変更が必要？
   ├─ YES → 人間に設計確認（承認待ち）
   └─ NO  ↓
④ AI：コード修正 + テスト実行
        ↓
⑤ AI：自己レビュー → 問題あれば④に戻る
        ↓
⑥ AI：PR作成（説明・変更サマリー付き）
        ↓
⑦ 人間：最終確認 → マージ承認
        ↓
⑧ 自動デプロイ（CI/CD）
```

**各ステップでのClaudeの役割と精度感**:

| ステップ | Claudeの役割 | 精度感 |
|----------|-------------|--------|
| ② 影響範囲分析 | 依存関係の洗い出し・リスク評価 | ★★★★☆ |
| ③ 設計判断 | 「これは確認が必要」の判断自体 | ★★★☆☆ |
| ④ 修正・テスト | コード変更・テスト生成・実行 | ★★★★★ |
| ⑤ 自己レビュー | diffチェック・ロジック検証 | ★★★★☆ |
| ⑥ PR作成 | 説明文・変更点サマリーの生成 | ★★★★★ |

**③の判断基準**（フロー安定化の要。構築時に CLAUDE.md へ明記する）:

以下に該当する場合は必ず人間に確認を求める：

- DBスキーマの変更を伴う
- 外部APIの認証フロー変更
- 既存APIのインターフェース変更（破壊的変更）
- セキュリティ関連コードの変更
- 3ファイル以上にまたがる大規模リファクタリング

**人間の関与は実質2箇所**（①起票・⑦マージ承認。③は条件付き）。ルーティンな修正なら ①→④→⑦ と最小化される。本番到達は必ず⑦の人間承認を経由し、デプロイはマージ後の CI/CD のみとする。既存の必須ゲート（認証・RLS・秘密情報まわりの security-reviewer 通過）は自動フローでも省略しない。

### 7.2 §2 対応表の効き目（Step 8 の KPT 素材）

第一期 Problem への対策のうち、**「ドキュメントと実装の乖離 → チェックポイントごとに SPEC へ進捗を書き戻す」だけが想定どおりには機能しなかった**。

- 実際に機能したのは **dev-log への書き戻し**だった。94セッション分の記録は Step 3 の突き合わせで全件正確であることが確認でき、突き合わせ自体が dev-log を索引に成立した
- SPEC への書き戻しは、`SPEC-beat-board` のように冒頭へ「改訂: 日付＋Issue番号＋要点」を積む運用を採った SPEC でのみ続いた。この形を採らなかった SPEC では、後続 SPEC が決定を上書きした事実が本文に残らなかった（Step 3 で改訂行を補って解消）
- 他の5対策（認証の先行 SPEC 化・スキーマのプランモード承認・hook による typecheck/lint 強制・二失敗ルール・SPEC への E2E 手順必須化）は狙いどおり機能した
