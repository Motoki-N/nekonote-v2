# SPEC-auth: 認証・セッション管理

作成日: 2026-07-12（インタビュー駆動で策定）
ステータス: 確定待ち（レビュー後に確定）

## 1. 目的

第一期最大の問題「セッション切れ頻発・再ログイン強制」を根本解消する。
認証・セッション管理を設計初期（Sprint 0）から組み込み、トークンリフレッシュの挙動まで本仕様で確定させる。

## 2. 決定事項（インタビュー結果）

| 論点 | 決定 |
|---|---|
| 認証方式 | Google OAuth（Supabase Auth）のみ。メール/パスワード認証は提供しない |
| 新規サインイン制御 | メール許可リスト方式。リスト外のGoogleアカウントは拒否 |
| 拒否のタイミング | DBトリガーで auth.users への作成自体を拒否（ゴミレコードを残さない） |
| 許可リストの管理 | 環境変数ベース（詳細は 4.2） |
| セッション寿命 | 使い続ける限り無期限（リフレッシュトークン自動更新）。長期放置時のみ再ログイン |
| 複数デバイス | PC・スマホ・複数タブの同時利用を無制限に許可。強制ログアウト機能は作らない |
| セッション切断時UX | 執筆中の入力内容をローカルに保持し、再認証後に復元・保存する |
| 環境分離 | Google OAuth対応は本番URL＋localhostのみ。Vercelプレビューデプロイでのログインは非対応 |

## 3. アーキテクチャ

### 3.1 セッション管理方式

- `@supabase/ssr` によるCookieベースのセッション管理（Next.js App Router標準パターン）
- **middleware.ts で全リクエスト時に `supabase.auth.getUser()` を呼び、セッションCookieを更新する**。
  これが第一期の「切れる」問題への直接の対策（リフレッシュがユーザー操作に依存しない）
- アクセストークン（JWT）有効期限: Supabaseデフォルトの1時間
- リフレッシュトークン: ローテーション有効（Supabaseデフォルト）。
  複数タブ・複数デバイスの同時リフレッシュ競合は、Supabaseのreuse interval（旧トークンの猶予期間）で吸収される。
  この設定（Auth > Sessions の Refresh token reuse interval = 10秒以上）を Sprint 0 で確認・記録すること
- セッションのタイムボックス（Inactivity timeout / Time-box）は**設定しない**（無期限方針のため）

### 3.2 認証フロー

1. 未認証ユーザーが保護ページへアクセス → middleware が `/login` へリダイレクト（元URLを `returnTo` クエリで保持）
2. `/login` で「Googleでログイン」ボタン → `signInWithOAuth({ provider: 'google' })`（PKCEフロー）
3. Google認証後 `/auth/callback` へ戻り、`exchangeCodeForSession` でセッション確立
4. `returnTo` があればそこへ、なければトップへリダイレクト

### 3.3 保護範囲

- **全ページ認証必須**。例外（公開ルート）は `/login` と `/auth/callback` のみ
- API Route / Server Action も同様に認証チェックを通す（middlewareのmatcherで静的アセット以外を対象にする）

## 4. 許可リスト（サインイン制限）

### 4.1 拒否の仕組み（一次ゲート: DB）

- `auth.users` への BEFORE INSERT トリガーで、メールアドレスが許可リストに含まれない場合は例外を投げて**ユーザー作成自体を失敗させる**
- 拒否されたユーザーには `/login` 上でエラーメッセージを表示（「このアカウントは利用を許可されていません」）

### 4.2 許可リストの持ち方（設計上の注意）

環境変数管理の方針とDBトリガー拒否の組み合わせには制約がある：
**PostgresのトリガーはVercelの環境変数を読めない**。そのため以下の2層構成とする。

- **DB側（一次ゲート）**: マイグレーションで `ALTER DATABASE ... SET app.allowed_emails = 'motoking55@gmail.com'` としてPostgres設定に保持し、トリガー関数は `current_setting('app.allowed_emails')` を参照する。
  Postgres設定は「DB側の環境変数」に相当し、許可リスト変更時はマイグレーション（または SQL 1文）で更新する
- **アプリ側（二次ゲート・多層防御）**: 環境変数 `ALLOWED_EMAILS`（カンマ区切り）を middleware でチェックし、リスト外のセッションは強制サインアウト。
  DB側とアプリ側の値は手動で同期する（ソロ利用・実質1件のため許容）

将来のマルチユーザー化時は `allowed_users` テーブル＋管理画面へ移行する（本仕様のスコープ外）。

## 5. RLS（Row Level Security）

- ユーザーデータを持つ**全テーブルで作成時からRLSを有効化**する（後付け禁止）
- 基本ポリシー: `user_id uuid not null default auth.uid()` カラム＋ `auth.uid() = user_id` によるSELECT/INSERT/UPDATE/DELETEポリシー
- `service_role` キーはサーバーサイドの明確な必要箇所（トリガー管理等）以外で使用しない。クライアントに渡るのは `anon` キーのみ
- **認証・RLSに関わる変更は security-reviewer subagent のレビューを必須ゲートとする**（運用計画準拠）

## 6. セッション切断時のUX（執筆内容の保護）

- ノート編集画面は、入力内容を一定間隔（目安: 数秒のdebounce）で `localStorage` にドラフト退避する
- 保存API呼び出しが認証エラー（401）で失敗した場合:
  1. 入力内容はドラフトとして `localStorage` に残す
  2. `/login?returnTo=<編集中のURL>` へ誘導（モーダルまたはリダイレクト）
  3. 再ログイン後、編集画面復帰時に localStorage のドラフトとサーバー値を比較し、ドラフトが新しければ復元して保存する
- ドラフトのキーはノートID単位。保存成功時にドラフトを削除する
- ※ 本項の実装はノート機能（SPEC-notes）実装時に行うが、**要件の確定はこの仕様が正**

## 8. スコープ外

- **GitHub PAT の登録・暗号化保存**（GitHub連携機能のSPECで扱う）
- マルチユーザー管理UI・招待機能（許可リストのテーブル化を含む）
- Vercelプレビューデプロイでのログイン対応
- メール/パスワード認証・パスワードリセット
- アカウント削除・退会処理
- 全デバイス一括ログアウト機能

## 9. E2E検証手順（Sprint 0 完了条件）

1. **基本ログイン**: 許可リストのGoogleアカウントでログインでき、トップページが表示される
2. **許可リスト拒否**: リスト外のGoogleアカウントでサインインを試み、エラー表示されること。**Supabaseダッシュボードで auth.users にレコードが残っていないこと**を確認
3. **セッション永続（短期）**: ログイン後、ブラウザを完全に閉じて再起動 → 再ログインなしで利用できる
4. **セッション永続（トークン更新）**: ログイン状態で1時間以上放置（またはJWT有効期限を一時的に短縮）→ 操作再開時に再ログインを要求されない
5. **複数デバイス**: PCでログイン後、スマホでもログイン → 両方で同時に操作でき、どちらも切れない
6. **複数タブ**: 同一ブラウザで3タブ以上開いて放置 → 全タブでセッションが維持される（リフレッシュ競合が起きない）
7. **未認証ガード**: ログアウト状態で保護ページのURLを直接開く → `/login` にリダイレクトされ、ログイン後に元のページへ戻る
8. **RLS**: 別ユーザー（テスト用に一時許可）のデータが、APIレスポンス・画面のどちらにも一切現れないこと。テスト後にテストユーザーを削除
9. **ログアウト**: サインアウト後、保護ページへ戻れないこと

※ 6項のドラフト復元はノート機能実装時に検証項目として持ち越す。
