## 6. 前回との比較と教訓

| | 前回（2026-08-12） | 今回（2026-11-11） |
|---|---|---|
| きっかけ | 締めくくり作業 Step 3（計画済み） | ユーザーの依頼（計画外） |
| 対象期間 | 開発開始から1か月 | 前回から3か月（機能追加15・修正47） |

| 主に遅れていた文書 | SPEC の本文・要求仕様・manual | manual・TESTING・CHANGELOG・dev-log |
| 前回の対策の効き目 | — | SPEC の改訂行は定着した |
| 構造的な原因 | SPEC への書き戻しが改訂行のある SPEC でしか起きない | 書き戻しの手順が SPEC と dev-log にしかない |

- **対策は、対象にした文書にしか効かない**。前回「改訂行を積む」と決めた SPEC は追従し、何も決めなかった manual・TESTING・CHANGELOG が
  同じ形で遅れた。今回は `/fix-issue` の手順に入れたので、次の突き合わせではこの手順が効いたかを見る
- **前回の監査が拾えなかった誤りが1件、3か月残っていた**（MAN-04。7月に実装済みの機能を「できない」と書いていた）。
  前回は dev-log と SPEC を索引にしたため、UI 側から見ないと分からない記述が入力に入っていなかった。
  今回はコンポーネントの文言を直接読んで見つけた。**文書同士の突き合わせでは、両方が古い箇所は見つからない**
- **数を書いた箇所は必ず古くなる**（標準13種・マイグレーション29本・環境変数8つ・標準7人）。今回の誤りの多くは数値だった。
  数を書くなら確認日を添えるか、数えられる場所（コード・ディレクトリ）を指す
- **「何もしなくても壊れない」文書ほど遅れる**。型チェックもCIも、マニュアルの記述が古いことは教えてくれない。
  次回の突き合わせを待たずに済むかどうかは、④-7 が実際に踏まれるかで決まる
