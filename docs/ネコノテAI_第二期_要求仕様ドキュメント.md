## 1. 目的・背景

### 1.1 目的
- AIを活用して、完成度の高い小説を効率的に執筆するため
- 小説そのものは人間が執筆し、AIはネタ出し・資料調査・文章の推敲・校正などを行う
- 第一期（v0.1.0）の実用検証で明らかになった問題点を解消し、実際の執筆で使い続けられるツールにする

### 1.2 想定利用環境・対象ユーザー
- ユーザーは開発者本人のみ（ただし将来のマルチユーザー化に備え、ユーザー管理機能は維持する）
- ブラウザ経由で操作し、PC／スマートフォンのマルチデバイスで利用可能であること

### 1.3 第二期の設計思想
第一期からの主な方向転換は以下の3点。

| 観点 | 第一期 | 第二期 |
|---|---|---|
| 構想の入力 | 先にカテゴリ（器）を決めてから書く | 白紙に自由に書き、後からタグ付けしてプロットに落とし込む（手帳→プロットモデル） |
| AIの位置づけ | 校正フェーズ限定の単機能 | ペルソナを持つエージェントとして全フェーズに伴走 |
| 原稿の実体 | アプリ内DBに保持 | GitHubリポジトリに保持し、アプリはレビュー・進捗管理に専念 |

創作フレームワーク（ラリー・ブルックス『工学的ストーリー創作入門』の6要素：コンセプト・キャラクター・テーマ・構成・シーン・文体）は、**システムのデータ構造として固定せず、AIへのレビュー観点（プロンプト）として保持する**。これにより創作の自由度を保ちつつ、プロンプトの差し替えだけでフレームワークを調整できる。

## 2. 第一期の問題点と対応方針

| # | 問題点 | 対応方針 |
|---|---|---|
| 1 | 認証が頻繁に切れ、再読み込み・再ログインを強いられる（認証機構を後付けしたことが原因と推定） | 認証・セッション管理を設計初期から組み込む。トークンリフレッシュの挙動を仕様策定段階で確認する |
| 2 | 構想メモのフォーマットが硬く自由度が低い。Markdown非対応。結局Notionに流出 | 白紙のMarkdownノートによるフリーフォーマット入力＋後からのタグ付け分類（→ 3.1） |
| 3 | AIアシストが校正フェーズ限定。構想のネタ出しや企画のスケジュール提案も欲しい | 役割ごとのペルソナを持つ複数AIエージェント制（→ 3.5） |
| 4 | 原稿のDB管理は差分がわかりにくい | 原稿の実体をGitHubに移し、アプリは読み込み＋校正結果のコミットのみ行う（→ 3.4） |
| 5 | 構成・シーンのつながりが見えづらい | 付箋ボード方式のビジュアルな構成管理（ビートボード）を導入（→ 3.3） |
| 6 | ライト/ダークテーマ対応に失敗し断念 | テーマ変数を設計初期から組み込み、今回は必ず実現する（→ 4.3） |

## 3. 機能要件

### 3.1 構想支援機能（手帳→プロットモデル）

**コンセプト**：紙の手帳にアイデアを書き留め、後からプロットに落とし込んでいく体験の再現。ここで言う「プロット」とは、コンセプト・キャラクター・テーマなどのストーリー構成要素を書き留めて整理したものを指す。

- **フリーノート**
  - 白紙のMarkdownノートに、フォーマット・カテゴリの事前指定なしで自由にメモを書ける
  - Markdown記法に対応（見出し・リスト・強調・リンク等）
  - 日常的な散発的メモの受け皿として、作成の手数を最小にする
- **タグ付け・分類**
  - ノートに対して後から「何に関する構想か」をタグ付けする（キャラクター・世界観・あらすじ等。複数タグ可、カテゴリ横断可）
  - **仮タイトル**（作品の卵の名前）もタグとして付与でき、仮タイトルによる絞り込みで、同じ作品候補に属するノート群を一覧できる
  - タグによる分類・検索・一覧表示
- **プロットに落とし込む（テンプレート挿入）**
  - ノートの内容が充実してきたら、コンセプト・テーマ・キャラクターなどの**分類に応じたテンプレートをノートに挿入**し、そのフォーマットに沿ってプロットに落とし込んでいく
  - テンプレートはMarkdownの雛形であり、DB上の固定スキーマではない（構造を固定せずテキストとして持つ、という本仕様の設計思想と一貫）
  - 落とし込み後もノートはMarkdownのままであり、自由な追記・逸脱が可能
- **AIによるネタ出し支援**
  - 書き留めたネタについて、AI（アシスタント・喫茶店のマスター等）から掘り下げのアドバイスを受けられる

**データモデルの方針**：`notes`（Markdown生データ）＋`tags`（多対多、仮タイトル含む）を中核とする。キャラクター設定等は独立テーブルではなく「テンプレートが挿入されたノート」として保持し、システムが管理する構造を最小限にする。

### 3.2 企画支援機能（企画書とレビューゲート）

- 書き上げる本ごとにプロジェクトを作成し、参加イベント・目標ページ数・締切を設定する
- **企画書の作成**：プロットが十分に煮詰まったら、**定型フォーマット**の企画書を作成する。コンセプト・キャラクター・テーマ（コアの三要素）に加え、**ジャンル・ターゲット層**を記載する
  - 企画書には該当するプロットに落とし込み済みのノート群を**紐づける**（企画書＝レポートの表紙、各ノート＝本文、という関係）
  - ジャンル・ターゲット層は、担当編集の企画レビュー観点（狙った層に刺さる企画か）や、読者代表AIの入力（どの層になりきるか）として活用される
- **企画レビューゲート**：担当編集AIのレビューを受け、フィードバックを反映して**企画が「通る」まで反復**する。実際の出版ワークフローに近い緊張感を演出する
- **執筆スケジュール支援**：締切・目標ページ数から、AIが執筆スケジュールを提案・管理する

### 3.3 構成・設計支援機能（4部構成とビートボード）

- **構成テンプレート（4部構成・5転換点）**
  - パート1：設定 →（プロットポイント1）
  - パート2：反応 →（ピンチポイント1 → ミッドポイント）
  - パート3：攻撃 →（ピンチポイント2 → プロットポイント2）
  - パート4：解決
  - 5つの転換点をプロジェクトの構成上のアンカー（固定ポイント）として登録できる
- **ビートボード**
  - **UIモデル**：構造化ボード方式（カンバン型）を採用する
    - 4部構成（設定・反応・攻撃・解決）をレーンとして固定し、5つの転換点をレーン間のアンカーとして表示する
    - シーンカードはレーン内・レーン間をドラッグ&ドロップで並び替え・配置できる
    - カードの並び順がそのまま構成順序としてDBに保存され、AIレビューに「現在の構成」を渡せる
    - スマートフォンでは縦積みレイアウトに対応する（タッチ操作前提）
  - **実装ライブラリ**：dnd-kit（軽量・タッチ対応・アクセシビリティ対応）
  - シーンカードには「感情の起点→終点（プラス/マイナス）」を記録でき、カード上のバッジ表示やボード下部の折れ線表示により、物語全体の感情の起伏を視覚化できる（発展要素）
- **シーンカードの記録項目**（自由記述ベース。以下は観点の目安）
  - シチュエーション（場所・時刻など）
  - シーンで起きること
  - 感情の変化（プラス→マイナス／マイナス→プラス)
  - 葛藤
- **構成・シーンへのAIレビュー**：組み立ての各段階で、担当編集AIのレビューを都度受けられる

### 3.4 原稿管理・校正機能（GitHub連携）

**コンセプト**：執筆は外部エディタ、原稿の実体はGitリポジトリ。ネコノテは「AIによる差分レビュー」の場（PRレビューに近い体験）。

- 執筆は既存の外部エディタ（縦書き対応等）で行い、原稿ファイルをGitへコミットする（第一期からの「車輪の再発明回避」方針を継承）
  - **2026-07-16 追記**：縦書きエディタ機能（→ 3.6）のスコープ内昇格により、アプリ内のWebエディタでの執筆も可能になった。外部エディタとの併用は引き続き可能（原稿の実体がGitにあるため、どちらで書いても同じフローに合流する）
- ネコノテはGitHub連携により原稿を**読み込み専用**で取得する
- **認可方式**：MVPでは**Fine-grained Personal Access Token**を採用する
  - ユーザーが発行したPAT（対象リポジトリ限定、Contents: Read/Write権限）を設定画面から登録し、Supabase側で暗号化して保存する
  - トークン取得部分はインターフェースとして抽象化しておき（例：`GitCredentialProvider`）、将来のマルチユーザー化時にGitHub Appへ差し替え可能な設計とする
- **リポジトリ構成**：**原稿モノレポ**を基本とする
  - 1つの原稿リポジトリ（例：`my-manuscripts`）内に`{プロジェクト名}/`フォルダを切って各作品の原稿を置く
  - DB側ではプロジェクトごとに`{repo, base_path}`のペアを保存する設計とし、特定の作品だけ別リポジトリに置く運用も後から可能にしておく
  - コミット履歴はパスでフィルタして作品単位で参照する
- **AI校正・校閲**
  - 原稿の一部または全部について、AIによる文章改善・推敲・校正を実行（表記揺れ検出、誤字脱字の自動検出、一貫性チェックなど）
  - **文体のチェックもこの校正フェーズでフォローする**（6要素の「文体」に対応）
- **修正提案の確認フロー**
  - AIからの修正提案を1件ずつ確認し、受け入れ／拒否を選択する。即断できない提案は**保留**（提案のまま残す）にすることもできる
  - 修正提案の粒度：基本は**文単位**（誤字の訂正や表記揺れの指摘など）。構成に関する指摘や「書くべき内容が書かれていない」ことへの指摘は**シーン単位**
  - 確定した修正内容は**まとめて1コミット**としてリポジトリへ書き戻す（ネコノテからGitへの書き込みはこの操作のみ）。保留中の提案はコミット後も残り、後から受け入れ／拒否を選べる
- **進捗管理**
  - Git連携で取得した原稿から文字数等を集計し、進捗を記録・可視化する（原稿の編集は行わない）

### 3.5 AIエージェント機能（ペルソナ制）

**コンセプト**：AIを「フェーズ限定の機能」ではなく「役割を持つキャラクター」として配置する。

- **ペルソナ**：役割ごとに異なるペルソナを持つ複数のAIエージェントを配置する。各ペルソナには担当役割・AI能力レベル（コスト最適化のため）・参照範囲を割り当てる

| ペルソナ | 能力 | 主な役割 | 参照範囲 |
|---|---|---|---|
| 担当編集 | 高 | 企画書レビュー、原稿の校閲（プロット・キャラクター設定との整合性チェック含む）。不十分な部分の指摘や深掘りの質問を投げかけるスタンスで、頭ごなしに否定しない | 企画・構成・設定・原稿すべて |
| 校正さん | 低〜中 | 表記揺れ・誤字脱字・文法の機械的なチェックに特化（コスト最適化のため担当編集から分離） | 原稿テキストのみ |
| アシスタント | 中 | スケジュール・進捗管理（締切に対するペース配分の助言）、キャラ名などの名称のネタ出し。チャットベースでやり取りし、プロット等の資料把握は不要 | チャット文脈のみ |
| 喫茶店のマスター | 中 | 壁打ち相手。漠然とした考えを説明すると、要約しつつ深掘りの質問を投げかけ、最後にメモにまとめて残す | その場の会話 |
| 読者代表 | 中 | 企画書のターゲット層になりきり、感情ベースの主観的な感想を返す（「ここが刺さった」「ここで飽きた」など）。書店員の客観評価とは異なり、一読者の"体験"を返す | 原稿＋企画のジャンル・ターゲット層設定 |
| 近所の書店員 | 高 | 書き上がった原稿を客観評価する。売れそうか、小説として優れているか、どの層に受けそうかを評価。場合によっては辛辣なことも言う | 原稿のみ（設定資料は参照しない） |

  - ペルソナ＝役割の性格・口調・能力レベル・参照範囲、レビュープロファイル＝その役割が使う評価基準、として分離して管理する
  - 「校正さん」と「担当編集」を分離することで、重い整合性チェック（高AI）と軽い表記チェック（低〜中AI）をモデルレベルで使い分け、コストを最適化する
  - 「読者代表」は設定資料を参照せず原稿と読者層のみを見る。読者は設定資料を読まずに本を手に取るため、その体験のシミュレーションとなる
- **レビュープロファイル**
  - AIに渡す「どういう観点でレビューするか」のプロンプトを、プロファイルとして管理する
  - ネコノテ標準テンプレートを最初から用意しつつ、ユーザーが複製・編集・新規作成できる（テンプレあり＋自由編集可）
  - プロンプトの差し替えでレビューのフレームワークを調整できる（例：別の指南書の観点への切り替え）
- **データ構造**
  - `personas`：`name`（名前）、`description`（性格・口調・スタンス）、`ai_capability`（high / medium / low。モデル選定にマッピング）、`reference_scope`（参照範囲）、`persona_type`（レビュー型 / 対話型）、`is_default`（標準同梱か、ユーザー作成か）
  - `review_profiles`：`name`、`target_phase`（企画 / キャラクター / 構成 / シーン / 校正）、`prompt_template`（編集可能なプロンプト本文）、`default_persona_id`（デフォルト担当ペルソナへの参照）、`is_default`
  - **プロファイルにデフォルト担当ペルソナを紐づける方式**を採用する（例：「企画書レビュー」の担当は担当編集）。レビュー実行時は原則デフォルト担当が起用されるが、ユーザーが変更することも可能
  - 壁打ち（喫茶店のマスター）・ネタ出し（アシスタント）のような観点評価を伴わないペルソナは**対話型**とし、レビュープロファイルを持たずチャットベースで動作する。読者代表・書店員は原稿全体への講評を返す**レビュー型**として扱う
- **標準テンプレート（初期セット）**：『工学的ストーリー創作入門』に基づく以下のプロファイルを同梱する

#### (a) 企画書レビュー（コンセプト・キャラクター・テーマ）
コアの三要素が説明された企画書として成立しているかをレビューする。

#### (b) キャラクターレビュー
1. 主役は誰か（タイプ・特徴・価値観・欠点）が明確か
2. 何を求めているか（欲求と目標）が具体的か
3. なぜ求めているか（動機と必要性）に説得力があるか
4. 失敗したらどうなるか（代償の大きさ）が物語を駆動するほど大きいか
5. どのように変わるか（内面的変化の軌跡＝アーク）が設計されているか

#### (c) 構成レビュー（4部構成・5転換点チェックリスト）
- **ストーリーの始まり**
  - 出だしにフックはあるか
  - プロットポイント1の前で主人公は何をしているか
  - プロットポイント1までにどんな危機感が設定されるか
  - 人物のバックストーリーは何か
- **プロットポイント1**
  - 適切な位置にあるか
  - 主人公をどう変えるか
  - 主人公に新たに生まれる必要性／旅は何か
  - その必要性の裏で何が危機に晒されるか
- **ミッドポイント**
  - 主人公や読者に新情報をどう提示するか
  - ストーリーの流れをどう変えるか
  - ドラマ的なテンションやペースはどう上がるか
  - 主人公はどう前進／攻撃するか
- **プロットポイント2**
  - その出来事は主人公をどのように積極的な態度に変えるか
  - 主人公はどのように主導権を握って問題解決に向かうか
  - その役割は主人公の望みをどう満たすか
  - 主人公の内面の悪魔の克服はどう表れるか

#### (d) シーンレビュー
- シチュエーション（場所・時刻など）が読者に伝わるか
- シーンで起きること（出来事）が明確か
- 感情の変化（プラス→マイナス／マイナス→プラス）が設計されているか
- 葛藤が存在するか

#### (e) 校正・校閲（文体チェック含む）
表記揺れ・誤字脱字・一貫性のチェックに加え、文体・表現の観点をフォローする。

#### データ構造の方針

ペルソナ（誰が）とレビュープロファイル（どんな観点で）を分離して管理し、**プロファイル側にデフォルト担当ペルソナを持たせる**（必要に応じて変更可能）。実際のワークフローでは「企画書レビューといえば担当編集」のように役割が概ね固定されるため、この形がUIもシンプルになる。

**personas テーブル（誰が）**
```
- id
- name            … 担当編集、校正さん、など
- description     … 性格・口調・スタンス（プロンプトに反映）
- ai_capability   … high / medium / low（使用モデルの選定にマッピング）
- reference_scope … 参照範囲（all / manuscript_only / chat_only /
                     manuscript_plus_target など）
- persona_type    … reviewer（レビュー担当）/ conversational（対話専用）
- is_default      … 標準同梱か、ユーザー作成か
```

**review_profiles テーブル（どんな観点で）**
```
- id
- name               … 企画書レビュー、キャラクターレビュー、など
- target_phase       … 企画 / 構成 / シーン / 校正 …
- prompt_template    … 編集可能なプロンプト本文
- default_persona_id … デフォルト担当ペルソナ（変更可能）
- is_default         … 標準同梱か、ユーザー作成か
```

- レビューの実行時は「プロファイル＋担当ペルソナ（デフォルトから変更可）＋対象データ」の組でAIを呼び出す
- 「喫茶店のマスター」（壁打ち）や「アシスタント」（ネタ出し・スケジュール）、「読者代表」「近所の書店員」（感想・評価）のような、観点チェックリスト型のレビューではないペルソナは `persona_type: conversational` として扱い、レビュープロファイルを持たずに対話・評価用のプロンプト（description）のみで動作する

### 3.6 縦書きエディタ機能（2026-07-16 スコープ内へ昇格）

**コンセプト**：ブラウザだけで「書く→保存（コミット）→縦書きプレビュー→入稿PDF」が完結する執筆環境。原稿の実体はGitリポジトリのまま（3.4 の方針を維持）で、エディタはその読み書きクライアントとして振る舞う。

当初はスコープ外（§6）としていたが、Vivliostyle（CSS組版）の活用により想定より低コストで入稿品質を実現できると判明したため、スコープ内へ昇格した。詳細仕様は `SPEC-vertical-editor.md`（親SPEC）および各フェーズの詳細SPECに従う。

- **原稿フォーマット**：VFM（Vivliostyle Flavored Markdown）。ルビ `{漢字|かんじ}`・縦中横・HTMLコメント（出力に現れない執筆メモ）に対応
- **入稿PDFビルド**（Phase 1・実装済み）：原稿リポジトリのGitHub Actionsで、タグpush→組版→検査→PDF/X-1a変換→Releases添付まで自動化
- **2ペインWebエディタ**（Phase 2・実装済み）：CodeMirrorエディタ＋Vivliostyle Viewerによる縦書きプレビュー。保存＝コミット（楽観ロック・競合時はマージ支援）、未保存分のIndexedDB待避
- **快適性**（Phase 3）：コメントUI・ルビ入力補助・画像アップロード/挿入補助・字数/ページ数見積り・目次/奥付の設定UI
- **ネコノテ連携**（Phase 4）：エディタ⇄ネコノテの相互リンク、レビュー結果のコメント書き戻し等（別途SPEC策定）

## 4. 非機能要件

### 4.1 安定性・認証
- 認証・セッション管理を設計初期から組み込む（後付けにしない）
- セッション切れによる再読み込み・再ログインの頻発を解消する
- トークンリフレッシュ・セッション永続化の挙動を仕様策定段階で明確にする

### 4.2 アクセス・同期
- ブラウザ経由でのアクセス、PC／スマートフォン両対応のレスポンシブUI
- 異なる端末間でのデータ同期（選択中プロジェクト等の状態はlocalStorage頼みにせず、サーバー側で保持する）

### 4.3 テーマ対応
- ライトテーマ／ダークテーマの切り替えに対応する（第一期で断念した機能。今回は必達）
- テーマ用CSS変数を設計初期から組み込む
- システム設定への追従・手動切り替え・切り替え時のちらつき（フラッシュ）対策を含む

### 4.4 AI利用
- 複数のAIプロバイダ（Anthropic / OpenAI / Google）のモデルを、用途（ペルソナの能力レベル）に応じて使い分ける
- **能力レベル→実モデルのマッピングは設定として持ち、変更可能とする**
  - ペルソナ側は能力レベル（high / medium / low）のみを持つ（`personas.ai_capability`）
  - 設定（`ai_model_settings`）に、能力レベルごとの`provider`＋`model_id`のペアを保存する
  - モデルの世代交代や料金改定があっても、設定変更のみで追従できる（コードやペルソナ定義には手を入れない）
- **初期マッピング（2026年7月時点）**

| 能力レベル | 担当ペルソナ | 初期モデル |
|---|---|---|
| high | 担当編集、近所の書店員 | Claude Sonnet 5（Anthropic） |
| medium | アシスタント、喫茶店のマスター、読者代表 | GPT-5.4-mini（OpenAI） |
| low | 校正さん | Gemini 3.1 Flash-Lite（Google） |

  - 選定理由：high帯は日本語の文芸的な質の判断が中核となるため創作文に定評のあるモデルを、medium帯は対話の応答速度を重視した高速モデルを、low帯は呼び出し回数が最多となる定型チェック向けに最安帯モデルを採用
  - 具体的な料金は変動が激しいため本仕様書には記載せず、実装時に各社公式のPricingページで確認する

## 5. システム構成・技術スタック

- **フロントエンド**：Next.js（App Router）+ TypeScript
- **UI**：shadcn/ui ベース（テーマ変数と親和性が高い）
- **バックエンド／DB**：Supabase（PostgreSQL）
- **原稿管理**：GitHub（API／OAuth連携。読み込み＋校正コミットの書き戻し）
- **AI連携**：Vercel AI SDK によるマルチプロバイダ構成（Anthropic / OpenAI / Google を統一インターフェースで呼び分け。第一期のOpenAI SDK直接利用からの変更点）
- **デプロイ・運用**：Vercel + GitHub

### 開発方針（第一期の反省を反映）
- ER図によるDBスキーマの事前確定（実装前に固める）
- Zodによるスキーマ定義→型生成（型安全性・バリデーションを最初から）
- 共通AppErrorクラス＋ハンドラーを最初から用意
- パフォーマンス最適化はMVP段階では実装しない（YAGNI）
