# SPEC-vertical-editor-phase4: ネコノテ連携（相互リンク・レビュー結果のコメント書き戻し）

作成日: 2026-07-16
ステータス: **確定**（2026-07-16 インタビュー2巡済み。§8 参照）
親SPEC: SPEC-vertical-editor §5.1 Phase 4

## 1. 目的

縦書きエディタ（執筆）とネコノテ（AIレビュー）は同じGitHubリポジトリの原稿を見ているが、
現状は画面間の行き来も、レビュー結果を原稿へ持ち帰る手段もない。
Phase 4 では両者を「原稿ファイルを共通言語」として接続し、
**レビュー結果をエディタのコメント（`<!-- -->`）として原稿に書き戻す**ことで、
執筆→レビュー→推敲のループをアプリ内で一周させる。

役割分担（親SPEC §3.2）は変えない: 原稿の実体はGitHub、レビューはネコノテ、執筆・コメント消化はエディタ。

## 2. スコープ（確定）

| # | 機能 | 概要 |
|---|---|---|
| 1 | 相互リンク | エディタ⇄原稿レビュー画面（校正/講評）を、同じ章を開いたまま行き来できる |
| 2-a | 校正の保留提案の書き戻し | 保留にした提案をファイル単位で一括、該当箇所の直前に `<!-- -->` コメントとして即コミット |
| 2-b | 講評の書き戻し | 講評の全文を専用メモファイル `manuscripts/00-review-notes.md` へ `<!-- -->` コメントとして追記・即コミット |

### スコープ外

- AIレビューが作者コメント（`<!-- -->`）を読んで文脈に使う連携（親SPEC §4.5 の将来連携。次期以降）
- エディタ画面内からの校正・講評の直接起動
- DBスキーマ変更（既存列 `revision_suggestions.committed_sha` を流用し、マイグレーションなしで実現する）
- 書き戻したコメントの自動消化・自動削除（消化は人間がエディタ上で行う）

## 3. 機能仕様

### 3.1 相互リンク

両画面にクエリパラメータ `?file=<リポジトリ相対パス>` での初期章選択を追加する。

- **エディタ** `/projects/[id]/editor?file=…`: 章一覧に該当パスがあればその章を初期選択して開く。なければ従来どおり未選択で開く（フォールバック・エラーにしない）
- **原稿レビュー画面** `/projects/[id]/manuscript?file=…`: ファイル一覧に該当パスがあればそのファイルを初期表示する。なければ従来どおり
- **リンクの設置**:
  - エディタのツールバーに「ネコノテでレビュー」リンク → `/projects/[id]/manuscript?file=<編集中の章>`（章未選択時は `file` なし）
  - 原稿レビュー画面のファイル表示ヘッダに「エディタで開く」リンク → `/projects/[id]/editor?file=<表示中のファイル>`
- `file` の値は**取得済み一覧との一致でのみ採用**する（URL由来の値でAPIを直接叩かない。多層防御）
- エディタに未保存編集がある状態での遷移は、既存のIndexedDB自動待避（Phase 2）が下書きを保持するため安全。特別な確認ダイアログは設けない

### 3.2 校正の保留提案のコメント書き戻し（一括・即コミット）

校正パネルに「**保留をコメントで書き戻す**」ボタンを追加する（「まとめてコミット」と同格の一括操作）。

- **対象**: そのファイルの提案のうち `status = 'on_hold'` かつ `committed_sha IS NULL` の全件
- **挿入位置**: 原文抜粋（`original_text`）が現在の原稿に**一意に見つかる**位置を含む行の直前に、単独行のコメントを挿入する。判定は校正適用と同じ一意一致アンカー（`lib/proofread-apply.ts`）を共用する
- **コメント書式**（1提案＝1行）:

  ```
  <!-- [ネコノテ校正・保留] 「原文の先頭20字…」→「修正案（全文）」 理由: …（全文） -->
  ```

  - 原文は挿入位置の直下にあるため先頭20字＋`…` に切り詰める。修正案・理由は全文を残す
  - コメント本文中の `--` はHTMLコメントを壊すため全角 `−−` へ、改行は空白へ無害化する
- **原子性**: 校正適用と同じ作法。1件でも一意に見つからない提案があれば**コミットせず全体を失敗**にし、該当提案の扱い（未処理に戻す/拒否）を日本語メッセージで案内する（部分書き戻しを作らない）
- **複数件の挿入**: 文書内の出現位置を先に全件確定し、後方から挿入する（位置ズレ防止）
- **コミット**: `putFileContent`（blob SHA 楽観ロック）で1コミット。メッセージ: `校正: <ファイル名> に保留N件をコメントで書き戻し（ネコノテAI）`
- **コミット後**:
  - 対象提案の `committed_sha` にコミットSHAを記録する（リトライ3回・失敗時は警告つき成功とする既存作法を踏襲）
  - `manuscript_links.last_reviewed_commit` を自コミットSHAへ進めて自己バナーを抑止する（既存作法）
- **書き戻し済みの提案の扱い**（インタビュー確定）:
  - ステータスは `on_hold` のまま。`on_hold` かつ `committed_sha` ありを「**コメント書き戻し済み**」バッジで表示する
  - 書き戻し済み提案はステータス変更・適用・再書き戻しの対象外（**消化はエディタのコメント一覧に一本化**する）
  - ※ `committed_sha` の意味は status で分岐する: `accepted` なら「適用コミット」、`on_hold` なら「書き戻しコミット」。両者が同時に立つことはない（適用は accepted のみ、書き戻しは on_hold のみを対象とするため）

### 3.3 講評のコメント書き戻し（専用メモファイル・即コミット）

講評パネルの各講評（履歴含む）に「**レビューメモへ書き戻す**」ボタンを追加する。

- **書き戻し先**: `{base_path}/manuscripts/00-review-notes.md`（固定名）
  - `book.config.js` の `entry` には載せない＝本文・PDFには一切出ない（entry 列挙が正、の既存設計をそのまま利用）
  - エディタの章一覧には「entry 未登録」の印つきで末尾に表示される（Phase 3 の既存挙動）ため、エディタから開いて読める
  - 新規章作成の entry 自動追記（Phase 3）はこのファイルには**適用しない**（エディタの新規作成経路を通らないため自然に回避される。将来 entry 追加候補に出ても、追加は人間の明示操作なので許容）
- **追記内容**: 講評**全文をそのまま**（追加のAI呼び出しなし）、以下のブロックをファイル末尾へ追記する:

  ```
  <!-- [ネコノテ講評 YYYY-MM-DD プロファイル名（ペルソナ名）]
  講評本文…
  -->
  ```

  - 本文中の `--` は全角 `−−` へ無害化する（改行は保持してよい。HTMLコメントは複数行可）
  - 日付は講評セッションの作成日時（JST）
- **ファイルが無ければ作成**（見出し `# レビューメモ（ネコノテAI）` を先頭に置く）。あれば取得→末尾追記→`putFileContent`（blob SHA 楽観ロック）
- **コミットメッセージ**: `講評: レビューメモへ書き戻し（ネコノテAI）`
- **重複防止**: 恒久的な重複記録は持たない（スキーマ変更なしの制約）。ボタンは書き戻し成功後、その表示中は無効化する。万一重複追記しても日時・プロファイル名つきなので判別・手動削除が容易（追記型のため実害は小さい）

### 3.4 エディタ側の受け口

追加実装なし。書き戻されたコメントは Phase 3 のコメント一覧・ジャンプ・色付き表示にそのまま載り、
プレビュー・PDFに出ないことは VFM の仕様（親SPEC §4.5）で保証済み。
書き戻しコミットとローカル下書きの競合は、Phase 2 の競合検知＋手動マージ支援がそのまま機能する。

## 4. 実装方式

- **変更ファイル（予定）**:
  - `lib/proofread-apply.ts` … 書き戻し用の純関数 `writeBackAsComments(content, suggestions)` を追加（挿入位置確定＋後方挿入。クライアント/サーバー共用）
  - `lib/actions/manuscripts.ts` … Server Action `writeBackOnHoldSuggestions(manuscriptLinkId)`（`commitAcceptedSuggestions` と対称の構造: RLS所有確認→パス再検証→最新取得→適用→PUT→記録）
  - `lib/actions/critique.ts` … Server Action `writeBackCritique(sessionId)`（RLS所有確認→講評取得→メモファイル取得/新規→追記→PUT）
  - `components/manuscript/proofread-panel.tsx` … 一括ボタン・書き戻し済みバッジ
  - `components/manuscript/critique-panel.tsx` … 書き戻しボタン
  - `components/manuscript/manuscript-workspace.tsx`／`app/projects/[id]/manuscript/page.tsx` … `?file=` 初期選択・「エディタで開く」リンク
  - `components/editor/vertical-editor.tsx`（＋ツールバー）／`app/projects/[id]/editor/page.tsx` … `?file=` 初期選択・「ネコノテでレビュー」リンク
- **DB**: スキーマ変更なし。既存列の流用のみ
- **GitHub書き込み**: 既存の `putFileContent`（PAT・blob SHA 楽観ロック）を流用。トークンスコープの変更なし
- **エラー処理**: 共通 `AppError`＋`toActionError`。コンフリクト（他所からのpush競合）は既存の日本語メッセージ方針を踏襲
- **色**: テーマ用CSS変数のみ（規約どおり）

## 5. セキュリティ

- トークンスコープ・認証フロー・RLSの変更は**なし**
- ただしGitHubへの**書き込みServer Actionを2本追加**するため、実装後の security-reviewer を省略しない
- URL由来の `file` パラメータは一覧との一致でのみ採用し、Server Action 側でも既存の `manuscriptFilePathSchema`＋base_path 配下検証を通す（多層防御の既存作法）

## 6. E2E検証手順（完了条件）

1. **相互リンク**: エディタで章を開く→「ネコノテでレビュー」→原稿レビュー画面が同じ章で開く。原稿レビュー画面でファイルを開く→「エディタで開く」→エディタが同じ章で開く。存在しない `?file=` を与えても落ちず既定表示になる
2. **保留の書き戻し**: 校正で提案を保留にする→「保留をコメントで書き戻す」→GitHubに1コミットができ、該当行の直前に `<!-- [ネコノテ校正・保留] … -->` が入る。エディタのコメント一覧に表示され、ジャンプできる。プレビューに現れない。提案には「コメント書き戻し済み」バッジが付き、再実行は対象0件で拒否される
3. **一意一致の安全弁**: 書き戻し前に原文該当箇所を書き換えて競合させると、コミットされず日本語エラーで案内される
4. **講評の書き戻し**: 講評を実行→「レビューメモへ書き戻す」→ `manuscripts/00-review-notes.md` が作成（2回目は追記）され、エディタの章一覧の末尾（entry 未登録の印つき）から開ける。全体プレビュー・入稿対象には含まれない
5. **回帰**: 既存の校正適用（受入→まとめてコミット）・講評の実行・エディタの保存＝コミットが従来どおり動作する

## 7. 積み残し（次期以降）

- AIレビューが作者コメント・書き戻し済みコメントを読んで文脈に使う（親SPEC §4.5）
- 書き戻しコメントの「消化済み」トラッキング（エディタでコメント削除→提案側への反映）
- エディタ内からの校正・講評の直接起動

## 8. 決定事項（インタビュー結果・2026-07-16）

| # | 論点 | 決定 |
|---|---|---|
| 1 | スコープ | **相互リンク＋レビュー結果のコメント書き戻し**の2本。AIの作者コメント読取・エディタからのレビュー起動は見送り |
| 2 | 書き戻し対象 | **校正の保留提案＋講評**。受入提案は既存の適用コミットがあるため対象外 |
| 3 | 反映方式 | **即コミット**（既存の blob SHA 楽観ロック方式を流用。エディタ側の競合はマージ支援が吸収） |
| 4 | 書き戻した保留提案の扱い | **保留のまま＋書き戻し済み印**。`committed_sha` 流用でスキーマ変更なし。消化はエディタに一本化 |
| 5 | 保留書き戻しの起動単位 | **ファイル単位の一括**（「まとめてコミット」と同じ作法） |
| 6 | 講評の書き戻し先 | **専用メモファイル** `manuscripts/00-review-notes.md`（entry 非掲載＝本に出ない） |
| 7 | 講評の要点の作り方 | **全文をそのまま**（追加AI呼び出しなし。専用ファイル行きなので長さは問題になりにくい） |
