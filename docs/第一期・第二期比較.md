## 0. 計測条件（重要）

第一期の数値は **`v0.1.0` タグ時点（2025-07-05）** で測る。理由は次のとおり。

- 第一期リポジトリの HEAD には、v0.1.0 の**1年以上あと**に打たれたコミットが8件ある
  （2025-07-09 のバグ修正2件、2026-08 の環境復旧・CVE対応・ログイン修正5件、CHANGELOG追加1件）。
  これらは第二期の開発期間と重なる保守作業であり、「第一期の開発成果」に含めると比較が歪む
- **計画書 §2 Step 8 の実測ベースライン（2026-08-07 時点）は HEAD で測った値**（41コミット / 130ファイル /
  23,495行）で、本書の v0.1.0 時点の値（37コミット / 118ファイル / 22,421行）とずれる。
  **本書の値を正とする**。計画書の表は策定時のもので、そちらは修正しない（時点記録のため）

第二期の数値は **`v0.2.0` タグ時点（2026-08-12）**。

## 2. 開発の進め方（構造の差）

### 2.1 Claude Code の使い方

| 項目 | 第一期 | 第二期 |
|---|---|---|
| 常駐コンテキスト | `.claude/old.md` **5,173行**（指示書型。リポジトリ直下の CLAUDE.md は空） | `CLAUDE.md` **50行**（分業型） |
| 事前仕様（SPEC） | 0本 | **28本・4,083行** |
| skills | なし | 4種（story-engineering / draft-to-clean-model / review-profiles / fix-issue） |
| subagents | なし | 1種（security-reviewer・必須ゲート） |
| hooks | なし | 3種（typecheck / lint / migration-guard） |

常駐コンテキストは **5,173行 → 50行（約1/100）**。減った分は SPEC・skills・hooks・subagents へ分散した。

### 2.2 ドキュメントの作り方

| 項目 | 第一期 | 第二期 |
|---|---|---|
| 主要ドキュメント | **7本・4,357行**（API / ARCHITECTURE / COMPONENTS / DATABASE / DEPLOYMENT / DEVELOPMENT / TESTING） | SPEC **28本・4,083行**＋運用・保守文書 |
| 書いたタイミング | **開発5日目に6本を1コミットで一括生成**（2025-06-30・3,169行）。TESTING.md のみ v0.1.0 当日（07-05） | **機能ごとに、実装の直前**（インタビュー → SPEC → 新セッションで実装） |
| 書いたあとの更新 | v0.1.0 までに **2コミットのみ**（いずれも 07-05） | 改訂行を積む運用を採った **10/28本**では継続（残り18本は後続SPECの上書きが本文に残らず。Step 3 で補完） |
| セッション記録 | なし | dev-log **98セッション・1,200行**＋incident-log |
| docs 全体 | 4,357行（上記7本） | **9,587行・43本** |

**分量はほぼ同じ（4,357行 vs 4,083行）。違うのは書いた単位と、書いたあとの扱い。**

**従来「第一期のドキュメントは完成後に書いた」と記録してきたが、これは事実誤り**（本書の計測で判明）。
実際は開発10日間の**5日目**に、`ネコノテAI 仕様書・ドキュメントを作成` という1コミットで6本が一括生成されている。
つまり第一期も「完成後」ではなかった。差は**書いた時点**ではなく、

- **単位**: 第一期はアプリ全体を1回で網羅／第二期は機能ごとに実装の直前
- **更新**: 第一期はその後ほぼ更新せず（2コミット）／第二期は書式を決めた SPEC でのみ継続

この訂正は Step 8 観点C の論点そのものを変える——「完成後に書いたから乖離した」という説明は成立しない。

### 2.3 スキーマ管理

| 項目 | 第一期 | 第二期 |
|---|---|---|
| 適用機構 | **なし**（`supabase/` ディレクトリ自体が存在しない） | Supabase CLI（`supabase db push`） |
| SQL ファイル | `database/` に**手書き9本**（`schema.sql`＋`migration_001`〜`008`＋`schema_optimized.sql`・`apply_all_optimizations.sql`） | `supabase/migrations/` に**29本**（タイムスタンプ順・適用済みを追跡） |
| 変更の承認 | なし | プランモードでの事前合意が必須。`migration-guard` hook が直接書き込みに確認を挟む |

**従来「第一期はマイグレーション0本」と記録してきたが、正確ではない**。SQLファイル自体は9本あった。
無かったのは**バージョン管理された適用機構**であり、実運用は「ファイルを書く → SQL Editor に手で貼る」だった。
そのため「ファイルの状態」と「DBの実状態」が一致している保証がなく、`schema.sql` と `schema_optimized.sql` の
二重管理も発生している。第二期との差は**本数ではなく、適用が追跡可能かどうか**にある。

### 2.5 データモデルの思想

第一期が持っていた構造化テーブル（`characters` / `chapters` / `scenes` / `ideas` ほか計17）のうち、
**`characters` / `chapters` は第二期で意図的に作らなかった**。キャラクター設定は「キャラクターテンプレートを
挿入したノート」として保持する方式に置き換えている（skill `draft-to-clean-model`）。

第二期で構造を持たせたのは、**AIと画面が構造として読む必要のあるもの**に限定した——
`scenes`（並び順・パート・転換点・感情）、`proposals`（ジャンル・ターゲット層）など。

この判断が正しかったかの評価は **Step 8 観点A の「意図的に捨てたもの」**で行う。
