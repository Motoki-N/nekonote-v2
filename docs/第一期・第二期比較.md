### 3.1.1 問題#1（認証切れ）の判定根拠

第一期には計測データがないため、**「同じ問題が第二期で再発しなかったか」**の形で検証する。

**再発の証跡はゼロ**:

- Issue **108件**のうち「セッションが切れる／再ログインを強いられる」に該当する起票は**0件**。
  認証関連の起票は #28（Vercelプレビューデプロイでのログイン対応・CLOSED）と
  #29（アカウント削除・退会・全デバイス一括ログアウト・OPEN）の2件だけで、どちらも切断問題ではない
- `docs/incident-log.md` に認証起因のインシデントなし（INC-2 事象B のセッション切断は、
  検証スクリプトが誤ってログアウトフォームを送信したもので、アプリの不具合ではない）

**設計の差**:

| | 第一期 | 第二期 |
|---|---|---|
| セッション更新 | **クライアント側**（`auth-context.tsx` + `auth-guard.tsx`。middleware なし） | **サーバー側**（`proxy.ts` が全リクエストで `getUser()` を呼び Cookie を更新） |
| 更新のきっかけ | ユーザー操作に依存 | 画面遷移のたびに自動 |
| 設計の決定時期 | 実装8日目に認証を追加（10日間の開発のうち） | **着手前**（`SPEC-auth` が最初の仕様書。リフレッシュトークンのローテーション・reuse interval まで策定時に確定） |

**第一期の認証問題は v0.1.0 で終わっていなかった**——これが判定の決め手になった。
第一期リポジトリには v0.1.0 の**1年後**（2026-08-08）に `src/lib/database/auth-lock.ts` が追加されている。
コメントによれば、`supabase-js` 既定の Web Locks 実装が無制限待ちに入ると全タブで `getSession()` が返らなくなり、
**画面がローディングのまま固着する**。その回避策である。

つまり第一期の「切れる」問題の一部は、クライアント側で `getSession()` に依存する構造そのものに由来していた。
第二期はサーバー側の proxy でセッションを更新するため、**この経路自体が存在しない**。
「認証を最初に設計する」という対策は、**症状ではなく発生経路を消す形で効いていた**。

#### 3.2.1 「読み込み専用」からの逸脱について

要求仕様 §3.4 は「ネコノテはGitHub連携により原稿を**読み込み専用**で取得する」「Gitへの書き込みは
確定した修正提案のコミットのみ」と定めていた。実際の書き込み経路は、校正コミット／保留のコメント書き戻し／
講評の書き戻し／エディタの保存＝コミット／新規章作成／画像アップロード／書籍設定の書き換え／
入稿タグ作成／ブランチ・PR作成／リポジトリ初期セットアップ／Zenn投稿——と大きく広がった。

これを**逸脱ではなく、転換の徹底として評価する**。§1.3 の転換は「原稿の保管場所をDBからGitへ移す」ことであり、
読み書きの向きは手段にすぎない。縦書きエディタがスコープ内へ昇格した時点（2026-07-16）で
「アプリで書いてGitに保存する」形になり、書き込みが必要になった。**保管場所の方針は一度も揺らいでいない**。

#### 4.2.1 第一期は RLS を「無効化」していた

第一期のスキーマには、次の行がコメント付きで並んでいる。

```sql
-- RLS無効化（個人利用のため）
ALTER TABLE projects DISABLE ROW LEVEL SECURITY;
ALTER TABLE ideas DISABLE ROW LEVEL SECURITY;
ALTER TABLE characters DISABLE ROW LEVEL SECURITY;
（以下、全テーブル）
```

**「まだ書いていない」のではなく、意識的に外していた。** 理由も明記されている——個人利用だから。

第二期は同じ「個人利用」という前提のまま、全24テーブルで RLS を有効にした。
判断が変わったのは、**アプリの利用者が1人でも、コードを書く主体が増えた**からである。
AIエージェントが Server Action を量産する体制では、認可の最後の砦をDB側に置いておかないと、
1本のクエリの書き漏らしがそのまま全データの露出になる。**RLS は多人数向けの機能ではなく、
書き手が増えたときの防壁**だった、というのが第二期を通して得た理解にあたる。

なお第一期はAPIキーの扱いも緩く、v0.1.0 時点でも OpenAI キーを **localStorage から読むフォールバック**が
残っていた（開発9日目に「環境変数ベースに移行」しているが、フォールバック経路は残置）。
第二期は秘密情報をクライアントにもDB平文にも置かない方針で統一している
（プロバイダのAPIキーは環境変数、GitHub PAT は暗号化して `user_settings` に保存し復号は server-only）。

### 4.3 規模が3倍になっても検証水準が落ちなかったか

セキュリティ監査を2回実施しているため、これは**実測で答えられる**数少ない品質指標になる。

| | 1回目（2026-07-14） | 2回目（2026-08-12） |
|---|---|---|
| マイグレーション | 9本 | **29本** |
| Route Handler | 3本 | **12本** |
| Server Action | 8ファイル | **20ファイル・106関数** |
| 結果 | Medium 1・Low 5 | **Critical / High ゼロ**・Medium 2・Low 6 |

**規模が約3倍になっても Critical / High はゼロのまま**で、1回目に確立した規律——作成時RLS・
USING/WITH CHECK 対・参照先の所有検証・anon の多層遮断・「zod → 認証 → RLS → 0件チェック」——が
全件で維持されていた。リファクタリング（Step 1）を挟んだ後も検証水準は落ちておらず、
認証をスキップするパラメータ分岐も作られていない。

### 4.4 運用コスト（第一期に対応データなし）

2026-07-18〜08-12（26日間）の実測: AI呼び出し **94回**・入力 502,755 tok・出力 110,862 tok。
Anthropic 分の概算は約 $2.0（リスト価格換算）で**月額数ドル規模**。DB 14MB・Storage 約9MB。

先に効く制約は容量ではなく**バックアップの不在**だった（本番 Supabase は PITR 無効・物理バックアップ0件。
`docs/RUNBOOK.md` §5.1 に警告として明記し、月次点検に自前 `db dump` を入れた）。
