### 3.1.1 問題#1（認証切れ）の判定根拠

第一期には計測データがないため、**「同じ問題が第二期で再発しなかったか」**の形で検証する。

**再発の証跡はゼロ**:

- Issue **108件**のうち「セッションが切れる／再ログインを強いられる」に該当する起票は**0件**。
  認証関連の起票は #28（Vercelプレビューデプロイでのログイン対応・CLOSED）と
  #29（アカウント削除・退会・全デバイス一括ログアウト・OPEN）の2件だけで、どちらも切断問題ではない
- `docs/incident-log.md` に認証起因のインシデントなし（INC-2 事象B のセッション切断は、
  検証スクリプトが誤ってログアウトフォームを送信したもので、アプリの不具合ではない）

**設計の差**:

| | 第一期 | 第二期 |
|---|---|---|
| セッション更新 | **クライアント側**（`auth-context.tsx` + `auth-guard.tsx`。middleware なし） | **サーバー側**（`proxy.ts` が全リクエストで `getUser()` を呼び Cookie を更新） |
| 更新のきっかけ | ユーザー操作に依存 | 画面遷移のたびに自動 |
| 設計の決定時期 | 実装8日目に認証を追加（10日間の開発のうち） | **着手前**（`SPEC-auth` が最初の仕様書。リフレッシュトークンのローテーション・reuse interval まで策定時に確定） |

**第一期の認証問題は v0.1.0 で終わっていなかった**——これが判定の決め手になった。
第一期リポジトリには v0.1.0 の**1年後**（2026-08-08）に `src/lib/database/auth-lock.ts` が追加されている。
コメントによれば、`supabase-js` 既定の Web Locks 実装が無制限待ちに入ると全タブで `getSession()` が返らなくなり、
**画面がローディングのまま固着する**。その回避策である。

つまり第一期の「切れる」問題の一部は、クライアント側で `getSession()` に依存する構造そのものに由来していた。
第二期はサーバー側の proxy でセッションを更新するため、**この経路自体が存在しない**。
「認証を最初に設計する」という対策は、**症状ではなく発生経路を消す形で効いていた**。

#### 3.2.1 「読み込み専用」からの逸脱について

要求仕様 §3.4 は「ネコノテはGitHub連携により原稿を**読み込み専用**で取得する」「Gitへの書き込みは
確定した修正提案のコミットのみ」と定めていた。実際の書き込み経路は、校正コミット／保留のコメント書き戻し／
講評の書き戻し／エディタの保存＝コミット／新規章作成／画像アップロード／書籍設定の書き換え／
入稿タグ作成／ブランチ・PR作成／リポジトリ初期セットアップ／Zenn投稿——と大きく広がった。

これを**逸脱ではなく、転換の徹底として評価する**。§1.3 の転換は「原稿の保管場所をDBからGitへ移す」ことであり、
読み書きの向きは手段にすぎない。縦書きエディタがスコープ内へ昇格した時点（2026-07-16）で
「アプリで書いてGitに保存する」形になり、書き込みが必要になった。**保管場所の方針は一度も揺らいでいない**。

#### 4.2.1 第一期は RLS を「無効化」していた

第一期のスキーマには、次の行がコメント付きで並んでいる。

```sql
-- RLS無効化（個人利用のため）
ALTER TABLE projects DISABLE ROW LEVEL SECURITY;
ALTER TABLE ideas DISABLE ROW LEVEL SECURITY;
ALTER TABLE characters DISABLE ROW LEVEL SECURITY;
（以下、全テーブル）
```

**「まだ書いていない」のではなく、意識的に外していた。** 理由も明記されている——個人利用だから。

第二期は同じ「個人利用」という前提のまま、全24テーブルで RLS を有効にした。
判断が変わったのは、**アプリの利用者が1人でも、コードを書く主体が増えた**からである。
AIエージェントが Server Action を量産する体制では、認可の最後の砦をDB側に置いておかないと、
1本のクエリの書き漏らしがそのまま全データの露出になる。**RLS は多人数向けの機能ではなく、
書き手が増えたときの防壁**だった、というのが第二期を通して得た理解にあたる。

なお第一期はAPIキーの扱いも緩く、v0.1.0 時点でも OpenAI キーを **localStorage から読むフォールバック**が
残っていた（開発9日目に「環境変数ベースに移行」しているが、フォールバック経路は残置）。
第二期は秘密情報をクライアントにもDB平文にも置かない方針で統一している
（プロバイダのAPIキーは環境変数、GitHub PAT は暗号化して `user_settings` に保存し復号は server-only）。

### 4.3 規模が3倍になっても検証水準が落ちなかったか

セキュリティ監査を2回実施しているため、これは**実測で答えられる**数少ない品質指標になる。

| | 1回目（2026-07-14） | 2回目（2026-08-12） |
|---|---|---|
| マイグレーション | 9本 | **29本** |
| Route Handler | 3本 | **12本** |
| Server Action | 8ファイル | **20ファイル・106関数** |
| 結果 | Medium 1・Low 5 | **Critical / High ゼロ**・Medium 2・Low 6 |

**規模が約3倍になっても Critical / High はゼロのまま**で、1回目に確立した規律——作成時RLS・
USING/WITH CHECK 対・参照先の所有検証・anon の多層遮断・「zod → 認証 → RLS → 0件チェック」——が
全件で維持されていた。リファクタリング（Step 1）を挟んだ後も検証水準は落ちておらず、
認証をスキップするパラメータ分岐も作られていない。

### 4.4 運用コスト（第一期に対応データなし）

2026-07-18〜08-12（26日間）の実測: AI呼び出し **94回**・入力 502,755 tok・出力 110,862 tok。
Anthropic 分の概算は約 $2.0（リスト価格換算）で**月額数ドル規模**。DB 14MB・Storage 約9MB。

先に効く制約は容量ではなく**バックアップの不在**だった（本番 Supabase は PITR 無効・物理バックアップ0件。
`docs/RUNBOOK.md` §5.1 に警告として明記し、月次点検に自前 `db dump` を入れた）。

## 5. 観点C: 開発の進め方の比較

§2 に並べた構造の差が、**主張どおりに機能したか**を検証する。運用計画 §1「第一期からの転換点」は
「短い CLAUDE.md ＋ SPEC ＋ skills ＋ hooks ＋ subagents の分業構成へ移行する」と宣言していた。

### 5.1 常駐コンテキスト 5,173行 → 50行

**機能した。** ただし「減らしたから良くなった」ではなく、**減らせる形に分けたから機能した**というのが実態に近い。

5,173行の指示書は、第一期の条件下では機能していた（開発速度3〜5倍という実感がある）。
問題は行数そのものではなく、**全部が「助言」だったこと**である。指示書に何を書いても、
守られるかはその時のモデルの判断次第で、守られなかったことを検知する手段もない。

第二期は同じ内容を性質で仕分けた。

| 性質 | 置き場所 | 第二期での実体 |
|---|---|---|
| **必ず守らせたい** | hooks（決定論で実行） | typecheck / lint / migration-guard |
| **必要なときだけ要る知識** | skills | story-engineering / draft-to-clean-model / review-profiles / fix-issue |
| **別コンテキストで検証させたい** | subagents | security-reviewer（認証・RLS・秘密情報の必須ゲート） |
| **機能ごとの設計** | SPEC | 28本・4,083行 |
| **常時必要な最小限** | CLAUDE.md | **50行** |

CLAUDE.md に残った50行は「削除すると Claude がミスするか？」を1行ずつ問うて残したものだけになった。
実際、**入れなかったもの**もある——猫テーマのトンマナは、UIテキスト作成時にしか効かないため除外した。

### 5.2 ドキュメントの作り方——当初の説明は間違っていた

**当初「第一期は完成後に書いたから乖離した」と説明していたが、これは事実ではなかった**（§2.2）。
第一期のドキュメント6本は開発10日間の**5日目**に1コミットで一括生成されている。第一期も先に書いていた。

正しい差はこうだった。

| | 第一期 | 第二期 |
|---|---|---|
| **単位** | アプリ全体を1回で網羅 | 機能ごとに、実装の直前 |
| **更新** | v0.1.0 まで2コミットのみ | 書式を決めた10/28本では継続、残り18本では途絶 |

そして**第二期も、更新については同じ失敗をしていた**（→ §6 の Problem）。
違いが出たのは乖離の**方向**で、第二期の乖離60件は全件が「実装が先、文書が後追い」、
**仕様に反する実装は0件**だった。

**「機能ごとに、実装の直前に書く」ことの効果は、文書を最新に保つことではなく、
実装が仕様から外れるのを防ぐことに出ていた。** これが観点C で最も意外だった発見にあたる。

### 5.3 スキーマ管理

**機能した。** 差は本数（9本 vs 29本）ではなく、**適用が追跡可能かどうか**だった（§2.3）。

第一期は `database/` に手書きSQLを置き、SQL Editor へ手で貼っていた。
そのため「ファイルの状態」と「DBの実状態」が一致している保証がなく、
`schema.sql` と `schema_optimized.sql` の二重管理も発生している。

第二期はプランモードでの事前合意 → マイグレーションファイル経由に統一し、
`migration-guard` hook が直接書き込みに確認を挟む。結果として、
**Step P の本番確認で「29/29 適用済み・全24テーブルRLS有効」と一発で言い切れる状態**になっていた。
これは第一期では原理的に確認できなかったことである。

なお migration-guard は当初「直接書き込みを**ブロック**」の設計だったが、
運用の中で `permissionDecision: "ask"`（確認を求める）に落ち着いた。
完全ブロックだと承認済みのスキーマ変更まで止まり、**迂回手段を探させることになる**ためである。

### 5.4 変更の通し方——手戻りの比較

第一期 Day16 の「14項目の大量修正」に相当する事象が第二期に起きたか、という問いへの答え。

**起きなかった。ただし「問題が出なかった」のではなく、問題の受け止め方が違った。**

| | 第一期（開発7日目・2025-07-02） | 第二期（開発6日目・2026-07-17） |
|---|---|---|
| 出来事 | 「不具合修正 **Part1 / Part2 / Part3**」を同日にコミット | Issue を**40件**まとめて起票 |
| 中身 | プロジェクト・AI機能・ページアクセス制御／アイデア・原稿・進捗管理／キャラクター機能 | ドッグフーディングで気づいた不具合・要望 |
| その後 | まとめて直し、翌日も追い修正。**何をどう直したかはコミットメッセージ以上に残らない** | 1件＝1 Issue＝1 PR で**直列に消化**。23件を数日〜数週間かけて解消、**17件は運用期間へ持ち越し**（＝カット可能な状態で保持） |

**同じ「一度に大量の問題が見つかる」局面で、第一期は修正をまとめ、第二期は起票をまとめた。**
これが「1機能=1セッションでスコープ固定」という規律の実際の効き方だった。
まとめて直すと個々の変更の是非が判断できなくなるが、まとめて起票する分には後で削れる。

なお運用計画 §2 が記録する「Day16: 14項目」は git と一致しない（第一期の開発は10日間で終わっている）。
**当時の体感で書かれた数字がそのまま1年以上引用されていた**というのも、この比較で得られた発見の一つである。

### 5.5 開発リズム

| 指標 | 第一期 | 第二期 |
|---|---|---|
| コミット / 日 | 3.7 | **10.9** |
| PR | 1（外部サービスの自動CVE修正のみ） | **79**（全件が人間のマージ承認を経由） |
| Issue | 0 | **108** |
| セッション記録 | なし | **98セッション** |

コミット/日が2.9倍になったのは生産量ではなく**粒度**の話である。
段階ごとにコミットさせる（失敗時の巻き戻し用）・1機能=1セッションでスコープを固定する、という
規律の結果として、1コミットあたりの変更が小さくなった。

**二失敗ルール**（同じ問題に同じアプローチで2回失敗したら手を止めて人間に相談する）については、
発見が2つある。第一に、**この規律は運用計画の §1-1／§4 を除き、どの文書にも書かれていなかった**。
CLAUDE.md に明文化されたのは開発が終わった後の Step 3（2026-08-12）である。
第二に、**発動した記録も残っていない**——dev-log 98セッションに「2回失敗して手を止め、人間に相談した」
という記録は1件もない。抑止として働いた（3回目に進む前に自分でアプローチを変えた）のか、
発動する場面自体がなかったのかは、記録からは区別できない。つまり「効いていた」は体感であって、
検証可能な主張ではない（本レポートで唯一、根拠を付けられなかった判定である）。
**効いている暗黙知は、文書化が遅れるだけでなく、効いた証跡も残らない。**

### 5.6 レビューゲート——作る側と受ける側

運用計画 §4 フェーズ3 は「アプリのレビュープロファイル機能と開発のレビューフローは同型であり、
ドッグフーディングとして設計検証に使う」と書いていた。これは**狙いどおりに機能した**。

- アプリ側: 企画書レビュー →（差し戻し／承認）→「企画を通す」。第1回の実運用で**4巡**（差し戻し×3 → 承認）し、
  企画書と紐づけノートの矛盾まで検出した
- 開発側: 実装 → subagent の自己レビュー →（指摘があれば修正して再レビュー）→ PR → 人間のマージ承認。
  security-reviewer は実際に Medium / Low を複数回捕まえている

どちらも「提案 → レビュー → 承認 → 次へ」の同じ形で、**開発フローで納得できた設計をアプリ機能へ、
アプリで使ってみて気づいたことを開発フローへ**、と双方向に流れた。

## 6. KPT（第二期の振り返り）

### 6.1 第一期 KPT の Try は機能したか（＝是正の効果測定）

運用計画 §2 の対応表6件の判定。

| 第一期の Problem | 第二期の対策 | 判定 |
|---|---|---|
| 認証の後付けで設計が不安定 | 認証を最初のインタビュー対象にし、security-reviewer を必須ゲート化 | **機能した**（§3.1.1。発生経路ごと消えた） |
| スキーマ不整合 | プランモードで事前合意・migration-guard hook | **機能した**（§5.3） |
| エラーハンドリングの後回し | 編集後の typecheck / lint 自動実行 hook | **機能した**（助言ではなく決定論で担保） |
| 仕様変更の連鎖による大量修正 | 二失敗ルール・1機能=1セッションでスコープ固定 | **機能した**（§5.4。ただし判定の根拠はスコープ固定の側にあり、二失敗ルールは文書化も発動記録もない——§5.5） |
| **ドキュメントと実装の乖離** | **チェックポイントごとに SPEC へ進捗を書き戻す** | **機能しなかった**（→ Problem 1） |
| テストデータ準備の遅れ | SPEC に E2E 検証手順とテストデータ要件を必須項目として含める | **機能した**（28本すべてが E2E 節を持ち、Step 0 の TESTING.md の素材になった） |

**6件中5件が機能。** 詳細は `docs/dev-story/09-documents-fall-behind.md`（書籍第9章）。

### 6.2 Keep（第三期でも続けること）

1. **性質による仕分け**——必ず守らせたいことは hooks、知識は skills、検証は subagents、設計は SPEC、
   残りだけ CLAUDE.md（§5.1）
2. **着手前に SPEC を書く**。効くのは文書の鮮度ではなく、**実装が仕様から外れないこと**（§5.2）
3. **スキーマはプランモード承認 → マイグレーション経由**。DBへの直接変更を禁止する（§5.3）
4. **大量の問題は、まとめて直さずまとめて起票する**（§5.4）
5. **dev-log をセッション単位で書く**。事後のあらゆる突き合わせがこれを索引に成立した
6. **incident-log を「なぜ軽微で済んだか」まで書く**。INC-1 の教訓が RUNBOOK の削除前チェックリストになった
7. **二失敗ルール**。ただし今度は最初から文書化し、発動したら dev-log に記録する（§5.5・Try 7）
8. **security-reviewer の必須ゲート**。規模が3倍でも Critical / High ゼロを維持できた（§4.3）

### 6.3 Problem（第二期で起きた問題）

1. **書き戻しの対策が「書式」を決めていなかった**——「SPEC へ進捗を書き戻す」とだけ決めて、
   どのファイルのどこにどんな形で書くかを決めなかったため、28本中18本で途絶した。
   続いたのは書式が決まっていた10本（冒頭の「改訂:」行）と dev-log だけだった
2. **監査の入力にテスト結果を入れていなかった**——Step 3 の突き合わせは dev-log と SPEC を索引にしたため、
   Step 0 の回帰テストが既に発見していた乖離（マニュアルの「シーンレビューに合否判定なし」）を取りこぼした。
   Step 5 で再発見して解消
3. **過去の記録が検証されないまま引用され続けた**——比較のベースライン数値・「ドキュメントは完成後に書いた」・
   「マイグレーション0本」・「Day16 に14項目」の4件が、実測と食い違っていた。
   いずれも当時の体感で書かれ、1年以上そのまま引用されていた
4. **効いている規律ほど文書化が遅れ、証跡も残らない**——二失敗ルールが CLAUDE.md に載ったのは
   開発終了後で、発動した記録も dev-log に1件もない。「効いていた」が体感のまま検証不能になっている（§5.5）
5. **バックアップの不在に、書くまで気づかなかった**——本番 Supabase は PITR 無効・物理バックアップ0件。
   RUNBOOK を書こうとして初めて「そもそも防壁がない」と分かった（監査でもテストでも出てこなかった）
6. **公開規約がコード内の文字列を対象にしていなかった**——伏せ字規約（CLAUDE.md）は
   コミット・PR・dev-log 書き戻しという**文書系だけを対象に書かれており**、UIコンポーネントの入力例や
   zod エラーメッセージといった**コード内の例示文字列がスコープ外**だった。結果、未公開作品の実タイトルに
   由来する文字列が3ファイル4箇所に混入し（うち2箇所はクライアントバンドルにも搭載）、
   Step 2 の監査（M-2）まで発見されなかった。規約はあったが規定範囲が実態に足りていなかった——
   「対策が書式を決めていなかった」（Problem 1）と同型の失敗である

### 6.4 Try（第三期でやること）

1. **書き戻し先を1つに決め、書式まで決める**。「〜を心がける」で終わっている対策は対策ではない。
   第二期の実績では、**dev-log 1本に集約するのが最も現実的**（SPEC は時点記録と割り切る）
2. **監査・突き合わせの入力に「手を動かして見つけた記録」を必ず含める**（テスト結果・インシデント・Issue）
3. **数字を書くときは出典と計測条件を併記する**。「41コミット」がどの時点の何を数えたのか書いていなかったため、
   1年後に誤った比較の土台になった
4. **バックアップを最初に用意する**。第三期のスキーマ設計時点で、`db dump` の定期取得を運用に組み込む
5. **シリーズ機能の設計確定分を、実装前に SPEC 化する**（→ 第三期引き継ぎメモ。次セッション）
6. **公開規約の対象をコード内の文字列まで広げる**。例示文字列・サンプル値・エラーメッセージは
   コードであっても公開物であり、伏せ字規約の対象に含めることを CLAUDE.md に明文化する（Problem 6 / 監査 M-2 の再発防止）
7. **効いていると感じた規律は、感じた時点で文書化し、発動したら dev-log に記録する**。
   証跡がないと第三期で効果測定ができない——第二期の二失敗ルールがその実例になった（Problem 4）
8. **開発側の AI 利用量・コストも記録する**。第二期の実測（§4.4）はアプリ側の `ai_usage_logs` のみで、
   Claude Code による開発コストは第一期と同様に計測していない。「第一期には計測データが存在しない」（§4.1）を
   比較不能の原因として挙げながら、開発プロセスについては第二期も同じ状態を繰り返している。
   第三期との比較を定量で行うなら、開発側の記録が要る
