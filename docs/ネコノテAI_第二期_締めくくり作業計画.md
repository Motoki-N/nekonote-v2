**目的**: 半年後の自分・第三者が運用できる状態にする。

**注意**: 公開リポジトリになった後の作成となるため、実値・実識別子は書かない（手順と参照先のみ）。

**キーローテーション手順の執筆時の注意（2026-08-06 事前調査）**:

- **共通原則は「新旧併存 → 切替 → 検証 → 旧失効」**。旧キーを先に失効させない。Vercel は環境変数をデプロイ時にスナップショットするため、値の更新だけでは反映されず**再デプロイが必須**（INC-1 で確認済みの仕様）
- **`ENCRYPTION_KEY` の暗号化対象は GitHub PAT のみ**（`user_settings.github_pat_ciphertext`。暗号化は `lib/actions/settings.ts`、復号は `lib/git/credentials.ts` に限定。ノート本文は暗号化しておらず pgcrypto 利用もなし）。したがって現状のローテーションは再暗号化スクリプト不要で「新32バイト鍵に差し替え → 設定画面で PAT 再登録」で完結する。ただし**再発行不能な唯一の鍵**である点は変わらない。将来暗号化対象を増やしたら「差し替えるだけ」は成立しなくなる（旧鍵復号→新鍵再暗号化の移行スクリプトが必須になる）ことを RUNBOOK に明記する
- **`CRON_SECRET` は外部整合が不要**（Vercel Cron は環境変数の値をそのまま Bearer で送る）。新しい乱数への差し替えと再デプロイだけで完結する
- **Supabase キーの失効は方式依存**: 旧来の JWT ベースのキー（`eyJ...`）は失効が JWT secret ローテーションを伴い全セッションが切れる。新方式（publishable / secret key）なら個別ローテーション可。手順執筆前に Dashboard の API Keys 画面で現行方式を確認する
- **キー値を出力しない作法を手順に織り込む**: 存在確認は `grep -c '^KEY='` 形式（dev-log セッション記録の教訓）、疎通確認の curl は値を直接タイプせず環境変数経由で渡す
- **執筆時に直す既知の記述ズレ**（RUNBOOK 完成と同時に修正する）:
  - `.env.local.example` の `ENCRYPTION_KEY` コメント「ノート等の暗号化キー」→ 実態は GitHub PAT のみ
  - README の環境変数表の同項目も同様
  - incident-log INC-1 の重大化シナリオ「暗号化済みデータ（ノート・PAT）」→ 実際の影響は PAT 再登録に留まる（記録の改変ではなく追記形式で訂正する）
