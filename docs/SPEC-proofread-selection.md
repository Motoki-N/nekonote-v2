# SPEC-proofread-selection: 選択範囲の校正（縦書きエディタ）

作成日: 2026-07-24（Issue #32 のインタビュー駆動で策定）
ステータス: **確定**（2026-07-24 レビュー済み）
親SPEC: SPEC-proofreading（§7スコープ外項目のうち「選択範囲の校正」を切り出し。「長文の自動分割」は本SPECの対象外＝Issue #32 に残置）

## 1. 目的

縦書きエディタで執筆中に「いま書いた範囲だけ」を校正できるようにする。
章全体を投げ直さないことでトークンコストと待ち時間を抑え、執筆リズムの中で校正さんを使えるようにする（Issue #32）。

## 2. 決定事項（インタビュー結果・2026-07-24）

| 論点 | 決定 |
|---|---|
| 対象画面 | **縦書きエディタのみ**。CodeMirror の選択APIで確実に範囲を取れ、「いま書いた範囲だけ校正」という実需に直結する。原稿タブ（読み取り専用ビュー）は従来どおり全文校正のみ |
| 既存pendingの扱い | **範囲内のみ置き換え**。原文抜粋が選択範囲テキスト内に見つかる pending だけ削除して新提案と入れ替え、範囲外の pending は残す。全文校正は現行どおり全 pending 置き換え。on_hold / accepted / rejected は従来どおり常に残す |
| AIへの入力 | **選択範囲のみ**。コスト最小・実装シンプル。範囲外との表記揺れ（同一語の表記不一致）は検出できないが、全体チェックは従来の全文校正が担うと割り切る |

インタビューで聞かずに設計原則で決めた点（レビューで確認）:

- **選択の受け渡しはテキスト（文字列）で行う**。オフセットは使わない。サーバーは実行時点の最新原稿を取得し、選択テキストが最新原稿に**部分文字列として見つかること**を検証する（見つからなければ「選択範囲が最新の原稿に見つかりません」エラー）。原文抜粋アンカー方式（SPEC-proofreading §3.5）と同じ思想で、画面表示と実体のズレに安全に対処する
- **`last_reviewed_commit` は更新しない**。部分校正は「ファイル全体を校正した」ことにならないため、更新バナー（前回の全文校正以降の変更検知）の意味を保つ
- **選択の最小長は10文字**。それ未満は校正の意味が薄く、範囲内置き換え判定の誤爆リスクも上がるためボタンを無効化する（サーバー側でもZodで検証）
- **選択の最大長は講評と同じ思想の上限を設けない**（ファイル全文選択も可。その場合も「部分校正」のセマンティクス＝範囲内置き換え・SHA非更新で動く。全文のつもりなら従来の「校正を受ける」を使う）
- **エディタが dirty のときは選択範囲校正も不可**。既存の校正パネル起動フロー（Issue #18: dirty 時は保存ダイアログへ誘導）を踏襲する。パネルを開いた後に編集して選択した場合は、上記のサーバー側検証（最新原稿に見つかるか）が安全弁になる
- **DBスキーマ変更なし**。granularity='sentence' 固定・revision_suggestions の列は既存のまま
- **レート制限・使用量記録は全文校正と共通**（feature キー 'proofread' を共用。部分校正は入力が小さいだけで実行回数の性質は同じ）

## 3. 画面とUX（縦書きエディタ）

- CodeMirror の選択状態を監視し、**10文字以上選択中**であることを校正パネルへ伝える
- 校正パネル（ProofreadPanel）のフッターに「**選択範囲を校正（N字）**」ボタンを追加:
  - エディタから開いたパネルで、かつ10文字以上選択中のときだけ表示（原稿タブから開いたパネルには出さない）
  - 既存の「校正を受ける／再校正を受ける」（全文）ボタンは従来どおり併置
  - 実行中の stop・多重実行抑止・逐次カード表示・完了後の取り直しは全文校正と同一の作法
- 提案カードの表示・受入/拒否/保留・まとめてコミット・保留書き戻し・該当箇所ジャンプは既存機能をそのまま使う（部分校正で作られた提案も区別しない。ライフサイクルは revision_suggestions.status が担う）
- 「選択範囲が最新の原稿に見つかりません」エラー時は、日本語メッセージをパネル内表示（既存のエラー表示枠）。保存し直し→再選択が復帰手順

## 4. API・データフロー

`POST /api/proofread` のリクエストを後方互換で拡張する（新規ルートは作らない）:

```
{ manuscriptLinkId: uuid, selection?: string }  // selection 省略時は従来の全文校正（挙動変更なし）
```

selection 指定時のサーバー処理:

1. 認証・レート制限・RLS越し所有確認・PAT取得・最新原稿取得は従来と共通
2. `selection` を検証: 10文字以上、かつ最新原稿に部分文字列として存在すること（なければ AppError validation）
3. `streamObject` の prompt に **selection のみ**を渡す（system は従来と同じ: 校正さん＋校正プロファイル＋コメント指針）
4. onFinish の保存:
   - 該当リンクの pending を取得し、`selection.includes(original_text)` が真のものだけ削除（範囲内置き換え）
   - 新提案を一括 insert（granularity='sentence'・status='pending'）
   - `last_reviewed_commit` は**更新しない**
5. 使用量記録（recordAiUsage・feature='proofread'）は従来どおり

全文校正（selection なし）のパスは一切変更しない（全 pending 置き換え・SHA更新を維持）。

## 6. スコープ外

- 長文の自動分割（Issue #32 に残置。ドッグフーディング継続で判断）
- 原稿タブ（読み取り専用ビュー）での範囲選択
- 選択範囲の講評（校正のみ）
- 提案カードへの「部分校正由来」の印付け・実行履歴

## 7. E2E検証手順

1. **選択→部分校正**: エディタで章を開き10文字以上選択→「選択範囲を校正（N字）」→範囲内の誤字が指摘され、範囲外は指摘されない
2. **範囲内置き換え**: 全文校正で pending を複数作る→一部を含む範囲を選択して部分校正→範囲内の pending だけ入れ替わり、範囲外の pending・保留・処理済みは残る（DB確認）
3. **SHA非更新**: 部分校正後も `last_reviewed_commit` が変わらない（更新バナーの挙動が全文校正基準のまま）
4. **陳腐化検出**: 選択→（別経路で原稿にコミット）→実行で「選択範囲が最新の原稿に見つかりません」の日本語エラー
5. **短すぎる選択**: 9文字以下ではボタンが出ない（または無効）
6. **回帰**: 全文校正（エディタ・原稿タブとも）が従来どおり動く（全置き換え・SHA更新・更新バナー）
7. **モバイル**: ボトムシート表示でも選択→部分校正が成立する
8. **レート制限**: 部分校正も 3回/分の制限に乗る

※ `/api/proofread` の変更は SPEC-proofreading の方針に従い **security-reviewer を通す**（PAT・認証コードに隣接するため。自動フローでも省略しない）。
