# 終章 終わらせ方を設計する

> 書籍『（仮）指示書5,173行から、50行へ』終章のドラフト。Zenn 記事としても単体で読める形で書いている。
> frontmatter（title / emoji / topics）は投稿時にフォームで付ける。

開発を終えたあと、**「終わらせる」ために10の工程と12セッション、17本のPRを費やした。**

作ったのはコードではない。回帰テストのチェックリスト、リファクタリング、セキュリティ監査、
リポジトリの公開化、ドキュメントの突き合わせ、運用ランブック、ユーザーマニュアルの改訂、
リリース、開発記録、そして振り返り。

最初は「片付け」のつもりだった。実際にやってみたら、**この期間がいちばん多くの発見を生んだ。**
しかもその発見は、机の上で振り返っていては絶対に出てこない種類のものだった。

この章は、その話をする。

## なぜ終わらせ方を設計したのか

第一期には、終わらせ方がなかった。

`v0.1.0` のタグを打ち、CHANGELOGを書いて、それで終わった。ドキュメントは開発5日目に一括生成したまま、
更新は2コミット。回帰テストの手順書はタグを打った当日に書かれている。

そして**1年後、環境の復旧作業をしている**。認証が固まる問題の修正、CVEへの対応、Supabase の再構築用SQL。
「終わったはず」のプロジェクトが、終わっていなかった。

第二期では、開発の終了日（8/11）と運用期間の開始（8/12）を先に決めていた。
その境目で何をやるかを、10の工程として書き出した。

| Step | 内容 |
|---|---|
| 0 | 現状の凍結（回帰テストの手順書を作り、タグで基準線を固定する） |
| 1 | コードレビュー＆リファクタリング |
| 2 | セキュリティ監査＋依存パッケージ更新 |
| P | リポジトリの公開化 |
| 3 | ドキュメントと実装の突き合わせ |
| 4 | 運用ランブックの作成 |
| 5 | ユーザーマニュアルの外部向け改訂 |
| 6 | リリース確定（CHANGELOG・タグ・Release） |
| 7 | 開発記録（本書） |
| 8 | 振り返り＋第一期との比較＋次期への引き継ぎ |

順序には1つだけ原則を置いた。**コードを変える作業を先に、コードに依存する資料を後に。**
マニュアルを先に書いてしまうと、リファクタリングのたびに書き直すことになるからだ。

## 各工程が「見つけたもの」

工程を並べたときに期待していたのは、**やるべきことを漏らさないこと**だった。
実際に効いたのは、そこではなかった。

| Step | 見つけたもの |
|---|---|
| 0 | 不具合2件（うち1件は「ドキュメントどおりに操作すると章一覧が空になる」設定の矛盾） |
| 1 | リファクタリング対象13件。うち1件は目標行数に届かず、**届かなかった理由を記録して合意**した |
| 2 | Medium 2・Low 6。**規模が3倍になっても Critical / High はゼロ**だった |
| P | 公開すべきでない文字列が**3ファイル4箇所**（うち2箇所はクライアントバンドルにも載っていた） |
| 3 | 実装とドキュメントの乖離**60件**。ただし**「実装が仕様から逸脱」は0件** |
| 4 | **本番DBのバックアップが1件も存在しない**（PITR も無効） |
| 5 | Step 3 の突き合わせが**取りこぼしていた**乖離。しかも Step 0 で既に発見されていた |
| 6 | （発見なし。淡々とリリースした） |
| 7 | 第一期について1年以上引用してきた記録の**誤り4件** |
| 8 | 上記すべてが KPT の Problem になった |

**Step 6 以外のすべての工程が、事前に想定していなかったものを見つけている。**

## 特に効いた3つの工程

### Step 0: 凍結——基準線がないと「壊れていない」が言えない

最初にやったのは、全機能の回帰テストチェックリスト（`docs/TESTING.md`）を作り、
`v0.2.0-rc` というタグを打つことだった。まだ何も直していない状態に、名前を付けた。

これがないと、次のリファクタリングで「挙動を変えていない」と言えない。
実際 Step 1 では「**挙動変更ゼロ**」を原則に5段階に分けてリファクタリングし、
各段階のあとにこのチェックリストを回した。

副産物として、凍結のための回帰テストが不具合を2件見つけた。片方は
「初期セットアップが設定する値どおりだと、エディタの章一覧が空になる」という規約の矛盾で、
ドキュメントを信じて操作すると必ず踏むものだった。
**先に直してから凍結し直した**（締めくくり作業の中で、機能の不具合を直したのはこの2件だけ。
以降のコード変更はリファクタリングとセキュリティ修正に限られている）。

### Step 4: 運用ランブック——書こうとして初めて、防壁がないと分かった

半年後の自分、あるいは引き継いだ第三者が運用できる状態にする、という目的で
`docs/RUNBOOK.md` を書いた。APIキーのローテーション手順、環境変数の操作、障害時の切り分けフロー、
そして——バックアップとリストア。

バックアップの節を書こうとして、コマンドを叩いた。

```
pitr_enabled: false
（物理バックアップ: 0件）
```

**プラットフォーム側に復元手段が存在しなかった。** 誤操作やマイグレーションの誤適用が起きても巻き戻せない。

これは監査でも回帰テストでも出てこなかった。セキュリティ監査は「攻撃されたときに守れるか」を見るし、
回帰テストは「機能が動くか」を見る。**「壊れたあとに戻せるか」は、どちらの視野にも入っていない。**
手順書を書こうとして初めて、書くべき手順が存在しないことに気づいた。

書きながら気づいたことがもう一つある。手が止まったのは手順そのものではなく、
**「なぜその順番なのか」**のところだった。そして、そこが埋まっている項目はすべて、過去に痛い目を見たものだった。
逆に痛い目を見ていない領域に、穴が空いていた。

**手順書を書く行為そのものが、監査になっていた。**

### Step 7: 再計測——過去の自分の記述を、測り直す

書籍の素材を集めるために、第一期のリポジトリを測り直した。
そこで、1年以上引用してきた記録に誤りが4件見つかった。

| これまでの記録 | 実測 |
|---|---|
| 41コミット / 130ファイル / 23,495行 | **37 / 118 / 22,421**（前者は1年後の保守コミットを含んでいた） |
| ドキュメントは**完成後**に書いた | **開発10日間の5日目**に1コミットで一括生成 |
| マイグレーション**0本** | 手書きSQL **9本**はあった（無かったのは適用機構） |
| 「Day16 に14項目の大量修正」 | git 上の該当は**開発7日目**（第一期の開発は10日で終わっている） |

どれも、当時の体感で書いたまま検証されずに引き継がれていた。
特に2番目は痛かった。**「第一期は完成後に書いたから乖離した」という、本書の柱にするつもりだった説明が、
成立しなくなった。**

第一期も、先に書いていたのだ。差は書いた時点ではなく、**書いた単位**（全体を1回で網羅したか、
機能ごとに実装の直前に書いたか）と、**書いたあとに戻ってくる仕組みがあったか**だった。

比較レポートを作る作業の半分は、**過去の自分の記述を測り直すこと**だった。

## 公開化のとき、履歴を書き換えなかった理由

Step P でリポジトリを public にした。このとき一つ、判断を求められた。
**git の全履歴をどう扱うか**である。

選択肢は3つあった——履歴を書き換える／そのまま許容する／リポジトリを作り直す。

書き換えを検討して、すぐに分かったことがある。**部分的な書き換えは成立しない**。
コミットのメタデータに含まれる author メールは全コミットにあり、
書き換えるなら全コミットを書き換えることになる。

その代償を並べた。

- **75本のPRと108件のIssueから、コミットへのリンクが全部切れる**
- dev-log に書いた31箇所のコミットSHA参照が無効になる
- 本書（開発記録）の追跡性が落ちる

**隠せるのは「履歴のdiffを掘って初めて見える情報」だけ**で、失うのは開発の記録そのものだった。
天秤にかけて、**許容**を選んだ。

代わりにやったのは、①現在のファイルから該当箇所を差し替えること（3ファイル4箇所。
うち2箇所はクライアントバンドルにも載っていた）と、②今後のコミットのメールアドレスを
noreply へ切り替えること、の2つである。

公開後、GitHub の Secret scanning で全履歴をスキャンした。**検出ゼロ**。
手作業の走査が、独立した手段で裏づけられた形になった。

判断そのものより、**判断の理由を文書に残したこと**のほうが後で効いた。
半年後の自分が「なぜ書き換えなかったのか」を掘り返さずに済む。

## 終わらせ方の設計が、振り返りの材料を作っていた

最後の工程（Step 8）で KPT を書いた。Problem に5件挙げた。

1. 書き戻しの対策が「書式」を決めていなかった
2. 監査の入力に「テスト結果」を入れていなかった
3. 過去の記録が検証されないまま引用され続けた
4. 効いている規律ほど文書化が遅れる
5. バックアップの不在に、書くまで気づかなかった

書き終えてから気づいたのだが、**このうち3件（2・3・5）は、振り返りの会議では絶対に出てこない**。

- 「監査の入力にテスト結果が入っていなかった」と分かったのは、マニュアルを改訂していて
  **Step 3 が取りこぼした乖離を踏んだ**からだ
- 「過去の記録が誤っていた」と分かったのは、書籍のために**測り直した**からだ
- 「バックアップがない」と分かったのは、ランブックを**書こうとした**からだ

**KPT の Problem は、成果物を作る過程でしか見つからない。**
「何か問題はありましたか」と自分に問うても、思い出せるのは既に知っている問題だけである。

締めくくり作業を10工程に分けて順に手を動かしたこと自体が、振り返りの入力を生んでいた。
これは設計したわけではなく、やってみて分かった副産物だった。

## 第三期へ渡すもの

最後に引き継ぎメモを書いた。主題は1つに絞った——
**シリーズ作品対応は「設計は確定している、実装はゼロ」である。**

スキーマにもコードにも「シリーズ」「巻」の概念は一切ない。一方で、設計インタビュー2巡で決めた
6つの方針と、既知の衝突点3件と、子Issue 7件の依存順は残っている。**SPEC は1本も書かれていない。**

この「確定しているが、まだ何もない」という状態を、曖昧にせず正確に渡すのが最後の仕事だった。
中途半端に実装が入っていたら、次の自分は「どこまでできているのか」の調査から始めることになる。
何もないなら、何もないと書いておくほうがいい。

そこに、KPT の Try も添えた。特に4つ目——**バックアップを最初に用意する**。
第二期は32日間、復旧手段がないまま走っていた。第三期のスキーマ設計の時点で、これを運用に組み込む。

## 終わらせ方は、次の始め方でもある

開発を終えてから、10工程・12セッション・17本のPR。
コードの変更は、Step 0 の回帰テストが見つけた不具合2件と、Step 1 のリファクタリング、
Step 2 のセキュリティ修正と依存更新だけ。あとはすべて、確認と記録である。

やってみて思うのは、**これは片付けではなく、プロジェクトの最後の1機能だった**ということだ。

第一期は終わらせ方を持たなかったから、1年後に復旧作業をした。
第二期は終わらせ方を工程にしたから、バックアップの不在も、記録の誤りも、
公開してはいけない文字列も、終わる前に見つかった。

そして、そこで見つけたものが全部、次の期への申し送りになっている。

**終わらせ方を設計するというのは、次に始めるときの自分に宛てて書く、ということだった。**
