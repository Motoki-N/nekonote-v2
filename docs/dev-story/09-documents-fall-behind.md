# 効かなかった対策——ドキュメントは実装に置いていかれる

> 書籍『（仮）指示書5,173行から、50行へ』第9章のドラフト。Zenn 記事としても単体で読める形で書いている。
> frontmatter（title / emoji / topics）は投稿時にフォームで付ける。

個人開発のアプリを、AIコーディングエージェント（Claude Code）と一緒に作り直した。
第一期の振り返り（KPT）で挙がった6つの問題に、それぞれ運用上の対策を割り当てて第二期を始めた。

32日後、5つは狙いどおりに機能していた。**1つだけ、まったく機能していなかった。**

この章は、その1つの話をする。うまくいった話より、こちらのほうが役に立つと思うからだ。

## 6つの問題に、6つの対策

第二期を始める前に、第一期の問題点と対策を1枚の表にした。この表は開発開始日（2026-07-12）に書いて、
以後まったく書き換えていない。

| 第一期の問題 | 第二期の対策 |
|---|---|
| 認証機能の後付けで設計が不安定 | 認証を最初のインタビュー対象にし、仕様を先に確定。認証・RLS変更は専用のレビューエージェントを必須ゲート化 |
| スキーマ不整合（`user_id` エラー等） | スキーマはプランモードで事前合意・承認後にマイグレーション作成。マイグレーションへの直接書き込みを hook でブロック |
| エラーハンドリングの後回し | 編集後の typecheck / lint 自動実行 hook で品質を強制（助言ではなく決定論で担保） |
| 仕様変更の連鎖による大量修正（Day16 に14項目） | 二失敗ルール：2回失敗したら仕様を書き直す。1機能=1セッションでスコープ固定 |
| **ドキュメントと実装の乖離** | **チェックポイントごとに仕様書（SPEC）へ進捗を書き戻す。セッションを唯一の記録にしない** |
| テストデータ準備の遅れ | SPEC に E2E 検証手順とテストデータ要件を必須項目として含める |

太字の行が、機能しなかったものだ。

（表中の「Day16 に14項目」は当時の体感で書いた数字で、あとで `git log` と突き合わせたら一致しなかった。
該当しそうなのは開発7日目の「不具合修正 Part1〜3」だ。**振り返りの記録は、その時点で検証されていない**——
という例としてそのまま残しておく。）

## 何が起きたか

第二期では、機能ごとに実装前の仕様書（SPEC）を書いた。最終的に28本・4,083行。
「着手前に書く」ところまでは、まったく問題なく回った。

問題は**そのあと**だった。

機能は実装後も変わる。Issue が来て仕様が変わる。後から作った機能が、前に作った機能の決定を上書きする。
そのたびに元の SPEC へ書き戻す——はずだった。

開発が終わってから、SPEC 28本・README・運用計画・実装計画・要求仕様・マニュアルを、
実装（コード・マイグレーション29本）と1件ずつ突き合わせた。結果、**乖離60件**。

内訳で目を引いたのは、分類の偏りだった。

- **「実装が仕様から逸脱している」= 0件**
- 残り60件はすべて「実装が先に進み、文書が追いついていない」方向

つまり、**仕様に反する実装は1つも作られていなかった**。SPEC は「着手前の設計図」としては完全に機能していた。
機能しなかったのは、**書き戻し**のほうだけだったのだ。

## なぜ書き戻しは続かなかったのか

意志が弱かった、では説明にならない。同じ人間（と同じAI）が、別の場所には毎回きちんと書き戻していたからだ。

書き戻しが続いた場所が2つある。

### 続いた場所1: 開発ログ

`docs/dev-log.md` に、セッション単位の記録を書き続けた。最終的に98セッション・1,200行。

**この記録は全件正確だった。** 開発終了後の突き合わせ作業そのものが、dev-log を索引にして成立した。
「この機能はいつ、どのIssueで、何を決めて実装したか」を引くのに、コードより先に dev-log を見ていた。

### 続いた場所2: 「改訂:」行を持つ SPEC

SPEC のうち10本には、冒頭にこういう行が積まれている。

```
作成日: 2026-07-13（インタビュー駆動で策定）
ステータス: 確定（2026-07-13 レビュー済み）
改訂: 2026-07-21 構成/シーンレビューのゲート化（Issue #57。verdict・「通す」ボタン…）
改訂: 2026-07-21 シーンカードへのノート・原稿ファイル紐づけ（Issue #56。…）
改訂: 2026-07-23 レビュー入力への紐づけノート全文投入（Issue #58。…）
改訂: 2026-07-31 構成テンプレート対応（Issue #54。4部構成固定を6テンプレート制に拡張。…）
改訂: 2026-08-09 シーン編集ダイアログの保存方式変更（Issue #169。…）
```

**この形式を一度採用した SPEC では、書き戻しが最後まで続いた。** 採用しなかった18本では、
後続の仕様が決定を上書きした事実が本文のどこにも残らなかった。

### 違いは「書式があるかどうか」だった

dev-log には「セッションN: タイトル（日付）」という決まった形があり、書く場所が1つに定まっていた。
「改訂:」行も同じで、**どこに、どんな形で足すかが決まっていた**。

一方、対策の文言は「チェックポイントごとに SPEC へ進捗を書き戻す」だった。
どのファイルの、どこに、どんな形で書くかは決めていない。決めていないものは、実行のたびに判断が要る。
判断が要るものは、忙しいときに飛ばされる。

**習慣は意志ではなく、置き場所と書式で決まる。** これが1つ目の教訓だ。

対策を立てるときに「〜を心がける」「〜を忘れずに」と書いたら、それはまだ対策になっていない。
「どのファイルの、どの位置に、どんな1行を足すか」まで決めて、はじめて続く。

## もうひとつ、後から見つかったこと

話はここで終わらなかった。

上の突き合わせ（乖離60件の洗い出し）は、開発終了後の「締めくくり作業」の一工程として行った。
そのあと別の工程で、**その突き合わせが取りこぼしていた乖離**が見つかった。

ユーザーマニュアルに「構成レビュー・シーンレビューに合否判定はなし」と書いてあった。
実装は逆で、判定バッジも「シーンを通す」という承認ボタンもある。明確な事実誤りだ。

しかもこの誤りは、**すでに発見されていた**。締めくくり作業の最初の工程で回した回帰テストの記録に、
「マニュアルの記述と実装が乖離 → 次の工程で解消」とはっきり書かれていた。
にもかかわらず、次の工程の突き合わせ表には載らなかった。

原因は単純だった。突き合わせを組み立てるとき、索引にしたのは **dev-log と SPEC** だった。
**回帰テストの結果を入力に入れていなかった。**

これが2つ目の教訓になる。**ドキュメント監査の入力には、「手を動かして見つけた記録」を必ず含める。**
コードと文書を突き合わせるだけでは、実際に画面を触って気づいた乖離は拾えない。
テスト結果は、監査の対象ではなく監査の**入力**だ。

## 効かなかった対策を、効いたことにしない

ここまでを、開発終了後に運用計画へ追記した。元の表は書き換えていない。
「6つの対策のうち5つは狙いどおり機能した。1つは想定どおりには機能せず、代替が自然発生した」という形で、
後日談の節を足した。

書き換えなかったのは、当時どう考えていたかの記録に価値があるからだ。
だが同じくらい大事なのは、**効かなかったという事実を、成果の集計から除かない**ことだと思う。

対策リストは、立てた時点では全部が仮説にすぎない。仮説の検証結果を書かずに次のプロジェクトへ持ち越すと、
同じ効かない対策をもう一度立てることになる。

## 第一期との比較で見えたこと

最後に、数字を1組だけ置いておく。

|  | 第一期 | 第二期 |
|---|---|---|
| 主要ドキュメント | 7本・**4,357行** | SPEC 28本・**4,083行** |
| 書いた単位 | アプリ全体を**1コミットで一括**（6本・3,169行） | **機能ごとに、実装の直前** |
| 書いたあとの更新 | v0.1.0 までに**2コミットのみ** | 書式を決めた10/28本では継続 |
| セッション記録 | なし | 98セッション・1,200行 |

**分量はほとんど同じだ。**

そして、この章を書くために第一期のリポジトリを測り直して、ひとつ思い違いをしていたことに気づいた。

第一期のドキュメントは「完成後に書いた」とずっと記録してきた。実際は違った。
`ネコノテAI 仕様書・ドキュメントを作成` という1コミットで6本が生成されたのは、
**開発10日間の5日目**だ。完成後どころか、まだ折り返し地点である。

つまり「完成後に書いたから実装と乖離した」という説明は、そもそも成立していなかった。
第一期も**先に書いていた**のだ。そのあと、v0.1.0 までにドキュメントへ触れたコミットは2つしかない。

差は書いた時点ではなく、こうだった。

- **単位**: アプリ全体を1回で網羅したか、機能ごとに実装の直前に書いたか
- **更新**: 書いたあとに戻ってくる仕組みがあったか

そして第二期は、後者を「対策」として立てたのに、書式を決めなかったせいで28本中18本で続かなかった。
**第一期と同じ失敗を、規模を大きくして繰り返していた**——というのが正直なところだ。

ただし、違いは出ていた。第二期の乖離60件は**全件が「実装が先、文書が後追い」**で、
**仕様に反する実装は0件**だった。機能ごとに実装の直前に書くことの効果は、
乖離を防ぐことではなく、**実装が仕様から外れるのを防ぐこと**に出ていた。

対策は、狙ったのとは違う場所に効いていた。それも、測り直してみるまで分からなかった。
