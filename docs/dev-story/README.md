## 本書の主題

**指示書5,173行で走っていた開発を、50行＋分業構成に組み替えたら何が起きたか。**

第一期（2025-06-26〜07-05・10日間）で作ったアプリは動いたが、認証が後付けで不安定（Google認証の実装は
開発8日目）、スキーマ不整合、開発7日目に「不具合修正 Part1〜3」の大量修正、ドキュメントは
アプリ全体を1コミットで一括生成して以後ほぼ更新なし——という状態だった。
第二期（2026-07-12〜08-12・32日間）は、その一つひとつに対策を割り当てて作り直した。

各章は「**第一期でこう失敗した → 第二期でこう変えた → 実際どうだったか**」の三段で書く。
効果測定まで書けるのは、第一期の KPT が運用計画 §2 の対応表として残っており、
第二期の全経緯が dev-log に残っているため。

## 通底する原則

書きながら守る（ドラフト執筆時の自戒）:

- **成功談だけを書かない。** 効かなかった対策も同じ強度で書く（→ 第9章）
- **数字は実測を使う。** 印象で「速くなった」と書かない。出典は比較表かdev-log
- **数字には計測窓を添える**（KPT Try 3）。締めくくり作業の工程数・セッション数・PR数は
  Step 7 の継続中も増え続ける。各章では「どの時点の何を数えたか」を本文か出典に明記し、
  **入稿前に全章の数字を最終値へ更新する**（終章の「12セッション・17PR」は Step 8 完了時点の値）
- **第一期を貶さない。** 第一期の指示書型は当時の条件では機能していた（開発速度3〜5倍の実感）。
  変えた理由は「間違っていたから」ではなく「前提が変わったから」
- **公開リポジトリ規約**: 第一期リポジトリ名・未公開作品の実タイトル・秘密情報・インフラ識別子は書かない
