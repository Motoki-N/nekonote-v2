# インシデントログ

開発・運用中に発生した事故（および事故につながり得たヒヤリハット）の記録。
ハインリッヒの法則（1件の重大事故の背後に29件の軽微な事故と300件のヒヤリハットがある）の考え方に基づき、
**結果的に軽微で済んだ事象ほど「なぜ重大化しなかったか」まで含めて記録する**。

記録の観点: 経緯（タイムライン）／直接原因・誘発要因・背景要因／影響／なぜ軽微で済んだか／対策／教訓。

---

## INC-1: `vercel env rm` による本番環境変数の消失（2026-07-23）

- **重大度**: 軽微（実害なし・同日中に完全復旧）。ただし条件次第で重大事故になり得た
- **発生セッション**: セッション59（Issue #28 プレビューデプロイでのログイン対応・PR #113）
- **影響範囲**: Vercel Production 環境の環境変数3件（`SUPABASE_SERVICE_ROLE_KEY` / `CRON_SECRET` / `RESEND_API_KEY`）が一時消失

### 経緯（タイムライン・2026-07-23）

1. Issue #28（Vercelプレビューデプロイでのログイン対応）の作業中、security-reviewer が指摘 M-1 を報告:
   「Preview 環境に本番DBのRLSをバイパスできる `SUPABASE_SERVICE_ROLE_KEY` が存在する。マージ前・人間レビュー前の
   ブランチコードが動くプレビューには不要かつ危険」（同キーは約3時間前の Issue #51 対応時に
   Preview+Production 同時指定で登録されていた）
2. ユーザー判断で「cron関連3キーを Preview から削除」を選択
3. `npx vercel env rm <KEY> preview -y` を3キーに実行 → CLIは正常終了
4. 直後の `vercel env ls` 全量確認で、**3キーが Production からも消えている**ことを発見。
   Preview スコープを指定したにもかかわらず、変数エントリ全体が削除されていた
5. 影響評価: Vercel は環境変数をデプロイ時にスナップショットするため、**稼働中の本番デプロイには即時影響なし**。
   ただし次回の本番デプロイ以降、cron（マイルストーン締切リマインド・Issue #51）が鍵欠落で停止する状態
6. ユーザーに事実関係・影響・復旧手段を報告し、承認を得て復旧:
   - `SUPABASE_SERVICE_ROLE_KEY`: `npx supabase projects api-keys` で再取得し Production へ再登録（値は非表示のままパイプ）
   - `CRON_SECRET`: 新規乱数を生成して再設定（Vercel Cron は同じ環境変数値を Bearer として送るため、値の変更で問題ない）
   - `RESEND_API_KEY`: 外部サービス（Resend）のキーで Claude 側からは再取得不能 → ユーザーが再登録
7. 消失発見から Claude 側復旧完了まで約15分。ユーザー作業分も同日中に完了し、全量が復元された

### 原因

- **直接原因**: `vercel env rm <NAME> <environment>` の挙動の誤解。変数が Preview+Production を対象とする
  **1エントリ**として登録されている場合、環境を指定してもエントリごと削除される（スコープの「部分解除」にはならない）
- **誘発要因**: 対象3キーが登録時に複数環境同時指定で1エントリになっていた。単一環境ずつ登録されていれば
  同じコマンドで意図どおりの結果になっていた——つまり**同じ操作でも事前状態によって破壊度が変わる**構図だった
- **背景要因**: 「削除してよいか」の承認（ユーザー確認）は取ったが、「このコマンドが期待どおりスコープ限定で
  働くか」の事前検証（登録形態の確認・ドキュメント確認・1キーでの試行）を省いた。
  承認プロセスは「何をするか」を守ったが、「どう実現されるか」の検証は別問題だった

### なぜ軽微で済んだか（＝重大化を防いだ防壁の棚卸し）

1. **Vercel の仕様**: 既存デプロイは環境変数をデプロイ時に固定するため、稼働中の本番が即座に壊れなかった。
   これは設計した防壁ではなく**偶然に近い仕様の恩恵**
2. **直後の全量確認の習慣**: 削除操作の数十秒後に `vercel env ls` の全環境を確認し、その場で発見した。
   発見が次回デプロイ後（cron 停止のサイレント障害）までずれ込む可能性は十分あった
3. **全キーに復旧経路が存在した**: service_role は Supabase CLI から再取得可、CRON_SECRET は再生成で足りる設計、
   RESEND のみ外部ダッシュボード依存だがユーザーが再発行可能だった

**重大化シナリオ**: もし同じ操作の対象が再発行不能な鍵（例: `ENCRYPTION_KEY`。これが失われ、かつ手元の
`.env.local` にも残っていない場合）だったら、暗号化済みデータ（ノート・PAT）が恒久的に復号不能となる
重大事故だった。今回の3キーが「全て再発行可能な鍵」だったのは結果論であり、操作時点でその区別を意識していなかった。

### 対策（再発防止）

1. **消す前に登録形態を確認する**: `vercel env ls` で対象キーが単一環境か複数環境1エントリかを確認してから操作する
2. **環境スコープ限定の削除はエントリ全消失を前提に計画する**: (a) Vercel Dashboard で操作する、または
   (b) 「削除→必要環境へ add し直す」を最初から一連の手順として組む（今回事後にやった復旧を、事前の計画にする）
3. **削除対象の復旧可能性を先に確かめる**: 値が再取得可能か（`.env.local`・CLI・外部サービス）を消す前に確認する。
   再発行不能な鍵（`ENCRYPTION_KEY` 等）は破壊的操作の対象にしない・する場合は事前バックアップを必須とする
4. **Claude のメモリに教訓を記録済み**（`vercel env rm` の罠・復旧手段一式）——以後のセッションで同じ操作をする前に想起される

### 教訓

- **スコープ指定オプションはスコープ限定の効果を保証しない**。CLI引数の意味論を推測で使わない。
  破壊的コマンドは「試しに1件」か、ドキュメントで挙動を確定させてから叩く
- **「戻せることを確認してから消す」**。復旧経路の確認は削除の前工程であって、事故後の対応ではない
- **是正措置そのものが新たなリスク源になる**。今回の削除はセキュリティレビュー指摘への対応（良い変更）だったが、
  その実行過程で別の障害の芽を作った。「正しい目的」は「安全な手段」を保証しない
- **直後の全量確認は最後の防壁として機能した**。操作結果の確認を対象スコープだけでなく全体に対して行う習慣が、
  発見をサイレント障害化する前に引き戻した
- **偶然の防壁を実力と混同しない**。デプロイ時固定の仕様・全キー再発行可能という好条件に救われた部分を
  「運が良かった」で流さず、上記対策として明文化した——これがこのログを書く理由でもある

## INC-2: 回帰テスト中の検証操作が実データ領域に波及（2026-08-12・ヒヤリハット2件）

### 事象A: 検証メッセージの実スレッド混入

- **経緯**: Step 0 回帰テスト（セッション88）の §10 相談検証で、ダッシュボード相談パネルのアシスタント・マスター両タブに検証メッセージを送信。相談パネルは「最後に更新したスレッドを再開する」仕様のため、新規スレッドを作らず**ユーザーの実スレッドに検証メッセージが追記された**（アシスタント2往復・マスター1往復）。さらにマスターへの「メモにまとめて保存して」で、実会話（作品構想の壁打ち）の要約ノートが自動生成された
- **直接原因**: 検証プレイブック（TESTING.md §0 データ保護ルール）に「相談系は必ず『新しい会話』で分離してから実施」の明記がなく、検証実施者（Claude Code）もスレッド再開仕様を失念した
- **影響**: 実スレッドに検証メッセージ3往復が残存（チャットのメッセージ単位削除機能はないため残る。実害なし・恥ずかしいだけ）。生成された要約ノートはごみ箱へ移動済み（内容は実会話由来のため完全削除はせずユーザー判断に委ねる）
- **なぜ軽微で済んだか**: 相談機能は追記型で既存メッセージ・スレッドタイトルを書き換えない設計だったため、実データの破壊・改変はゼロ。スケジュール確定ツールは検証専用プロジェクトを選択していたため実プロジェクトの schedule には触れていない
- **対策**: TESTING.md §10 に「検証は必ず『新しい会話』で新規スレッドを作ってから行う」を追記する（次回改訂時）
- **教訓**: 「get-or-create で既存を再開する」UIは検証時の分離を破りやすい。検証手順書には機能仕様への理解を前提にせず、分離手順を明文化する

### 事象B: フォーム探索フォールバックがログアウトフォームを送信

- **経緯**: §11 Zenn 投稿の自動操作で、投稿ボタンが `<form>` に属していなかったため `button.closest('form') || document.querySelector('form')` のフォールバックで**ページ先頭のフォーム＝ヘッダーのログアウトフォームを requestSubmit() し、セッションを破棄**した
- **直接原因**: 検証スクリプトのフォールバック探索が「最初に見つかった form」を無条件に送信した
- **影響**: セッション切断のみ（再ログインで復旧・データ影響なし）。偶発的に §2 ログアウト・未認証ガード・returnTo 復帰の検証を兼ねる結果になった
- **なぜ軽微で済んだか**: ログアウトは破壊的操作ではなく、アプリの認証設計（returnTo 付きリダイレクト）が正しく機能したため
- **教訓**: 自動操作でフォーム送信のフォールバックを書くときは、対象ボタンとフォームの所属関係を必ず検証してから submit する（`form.contains(button)` チェック）。「submit type のボタンがどのフォームに効くか」はUI検証の盲点になりやすい
