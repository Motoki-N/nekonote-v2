## 1. 目的

書き上げる本ごとのプロジェクト管理と、企画書の作成・担当編集AIによるレビューゲートを実装する（要求仕様 §3.2「企画支援機能」、利用フロー §3.6「企画」）。

同時に、第二期のレビュー基盤を初めて実装する:

- reviewer 型ペルソナ4人＋レビュープロファイル5種の標準シード（review-profiles スキルが正）
- レビューセッション（`review_sessions` / `review_feedbacks`）の反復ゲートフロー
- この基盤は Sprint 3 の構成/シーンレビュー、Sprint 4 の校正がそのまま使う

## 2. 決定事項（インタビュー結果）

| 論点 | 決定 |
|---|---|
| 企画書エディタ | **構造化2項目＋Tiptap本文**。ジャンル・ターゲット層は入力フィールド（AIが構造参照する2項目のみカラム化）、コンセプト/キャラクター/テーマの本文はノートと同じTiptapエディタ（Markdown保存）＋新規作成時に定型テンプレを初期挿入 |
| レビューUI | **文書ベースの反復**（チャットではない）。「レビューを受ける」→担当編集のフィードバック文書→企画書を改稿＋返答メモ→再レビュー。壁打ちはAI掘り下げの領分と役割分担 |
| 承認判定 | **AI判定＋ユーザー確定**。担当編集がフィードバック末尾で「承認 / 差し戻し」を判定し、承認が出たらユーザーが「企画を通す」ボタンで確定（status: approved） |
| ノート紐づけ導線 | **仮タイトルタグから一括候補**。プロジェクト作成時に仮タイトルタグを選ぶと、そのタグの付いたノート群を紐づけ候補としてチェックボックスで一括提示。後から個別の検索追加・解除も可能 |
| レビュー入力 | **紐づけノート全文を含める**。企画書本文＋ジャンル/ターゲット層＋紐づけノート全文を担当編集に渡す（企画書＝表紙・ノート＝本文の関係。設定との整合性まで見た指摘を可能にする） |
| 反復の文脈 | **同一セッションの全履歴**。2回目以降は過去のフィードバック＋ユーザー返答メモを全て渡し、「前回の指摘が直ったか」を見られるようにする |
| 承認後の編集 | **approved のまま維持**。承認後の編集で status は変わらない（ゲートは演出であり機械的管理ではない）。再審査したければ手動で新しいレビューを回す |
| 担当ペルソナ変更UI | **今回はデフォルト固定**（企画書レビュー＝担当編集）。変更UI・プロファイル編集UIは Sprint 5 の設定画面。スキーマは変更可能な形（review_sessions.persona_id）のまま |

## 3. 画面とUX

### 3.1 プロジェクト一覧（`/projects`）

- プロジェクトカード一覧（タイトル・status バッジ・イベント名・締切・目標ページ数・企画書 status）
- 「新規プロジェクト」ダイアログ:
  - タイトル（必須）、執筆ジャンル選択（既定: 小説。SPEC-genre）、イベント名・締切・目標ページ数（任意）
  - **仮タイトルタグ選択（任意）**: 選ぶと、そのタグが付いたノート群がチェック済み候補として一覧表示され、チェックしたものが企画書に一括紐づけされる
  - 作成と同時に企画書（proposals 行）も自動作成する（1プロジェクト1企画書・執筆ジャンル別の定型テンプレ入り）
- プロジェクトの編集（タイトル・status・イベント・締切・目標ページ数）・削除（確認ダイアログ。配下の企画書・レビュー履歴も cascade 削除される旨を明示）
- ヘッダーナビに「プロジェクト」を追加

### 3.2 企画書ページ（`/projects/[id]`）

- 上部: プロジェクト情報（タイトル・status・締切等）＋編集導線
- **企画書エディタ**:
  - 執筆ジャンル（select）/ 執筆目的 / 内容ジャンル / ターゲット層の入力フィールド（4項目。SPEC-genre）
  - 本文はノートと同じ Tiptap エディタ（Markdown保存・対応記法も同じ）。エディタ実装はノートのものを共通化して再利用する
  - 新規作成時の初期本文 = 執筆ジャンル別の定型テンプレ（小説 = コンセプト / キャラクター / テーマの見出し構成。**コード内定数**として管理。templates テーブルには入れない — ノート挿入用途ではないため。他ジャンルは SPEC-genre §3.3）
  - 自動保存（2秒デバウンス＋離脱時）はノートと同じ挙動
- **紐づけノート**: 紐づけ済みノートの一覧（タイトルチップ→ノートへのリンク）、検索して個別追加、解除。ごみ箱中のノートは非表示（AI掘り下げと同じ運命共同体パターン。完全削除で proposal_notes は cascade）
- **レビューゲートパネル**（デスクトップ=右サイドパネル、スマホ=ボトムシート。掘り下げパネルと同型）:
  - 「レビューを受ける」ボタン → 担当編集のフィードバック文書が**ストリーミング表示**される
  - フィードバック文書カードの履歴（同一セッション内の反復が時系列で並ぶ）。各カードに**判定バッジ（承認 / 差し戻し）**
  - 各フィードバックに**返答メモ**（user_response）を書ける（任意。改稿の意図や反論を次のレビューに伝える）
  - 判定が「承認」のとき「**企画を通す**」ボタンが出現 → 確定で proposals.status = approved、セッション completed。承認バッジを企画書ページとプロジェクトカードに表示
  - proposals.status: draft →（初回レビュー実行で）in_review →（ユーザー確定で）approved
  - エラーは日本語メッセージをパネル内表示（APIキー未設定 / プロバイダエラー。AppError 正規化）。生成中の多重実行は抑止、stop ボタンあり

### 3.3 レビューのプロンプトとコンテキスト

- system プロンプト = 担当編集ペルソナの `description`（性格・口調・「頭ごなしに否定しない」スタンス）＋レビュープロファイル「企画書レビュー」の `prompt_template`
- user 入力 = 執筆ジャンル（日本語ラベル）・執筆目的・内容ジャンル・ターゲット層＋企画書本文（Markdown・保存済みDB値）＋紐づけノート全文（タイトル・タグ・本文。ごみ箱中は除外）＋同一セッションの過去フィードバック・返答メモ全件
- 出力形式: Markdown のフィードバック文書。**末尾に固定形式の判定行**（例: `判定: 承認` / `判定: 差し戻し`）を出力させ、生成完了時にパースして `review_feedbacks.verdict` に保存する。パース不能時は差し戻し扱い（フェイルクローズ）
- 企画書レビューの観点（prompt_template の骨子。story-engineering スキル準拠）: コンセプト（「もし〜だったら」が成立しているか）・キャラクター・テーマの三要素＋ジャンル/ターゲット層に刺さる企画か

## 4. データ

### 4.1 マイグレーション（プランモード承認・security-reviewer ゲート対象）

テーブルは既存（20260712000002）。追加は1カラム＋シードのみ:

```
review_feedbacks に verdict 列を追加:
  verdict text null可 check (verdict in ('approved', 'needs_work'))
  … AIの承認判定。画面が構造参照する（「企画を通す」ボタンの出現条件）ためカラム化
    （draft-to-clean-model 判断基準2に該当）
```

- `review_sessions` の運用セマンティクス（スキーマ変更なし・意味の確定）:
  - 1セッション = 1つの企画書に対する反復ゲートのスレッド。`target_ref` に proposal id を格納
  - 反復中は status = running（この間の「レビューを受ける」は同セッションに feedback を追記）
  - 「企画を通す」確定で completed。failed はAI呼び出しが完了不能だった場合の記録用
  - running セッションは企画書ごとに高々1本（アプリロジックで担保。DB制約は追加しない）

### 4.2 personas 標準シード（reviewer 型4人・固定UUID採番）

| name | ai_capability | reference_scope | persona_type |
|---|---|---|---|
| 担当編集 | high | all | reviewer |
| 校正さん | low | manuscript_only | reviewer |
| 読者代表 | medium | manuscript_plus_target | reviewer |
| 近所の書店員 | high | manuscript_only | reviewer |

- `is_default = true`（user_id null のハイブリッド所有・conversational 2人と同じ流儀）
- `description`（性格・口調プロンプト）は review-profiles スキル準拠でシード時に確定
- 校正さんの能力帯は low を初期値とする（機械的チェックのコスト最適化。ai_model_settings で差し替え可能）

### 4.3 review_profiles 標準シード（5種・固定UUID採番）

| name | target_phase | default_persona | 観点の骨子（story-engineering 準拠） |
|---|---|---|---|
| 企画書レビュー | proposal | 担当編集 | コンセプト・キャラクター・テーマ三要素＋ジャンル/ターゲット層適合。末尾に判定行 |
| キャラクターレビュー | character | 担当編集 | 5つの問い（誰が・何を・なぜ・失敗の代償・どう変わるか） |
| 構成レビュー | structure | 担当編集 | 4部構成・5転換点チェックリスト |
| シーンレビュー | scene | 担当編集 | シチュエーション・出来事・感情変化・葛藤の4観点 |
| 校正・校閲 | proofreading | 校正さん | 表記揺れ・誤字脱字・一貫性＋文体・表現 |

- Sprint 2 でUIから使うのは「企画書レビュー」のみ（他は Sprint 3・4 が使う。プロンプトはシード時に全件確定）
- 固定UUIDは `lib/ai/personas.ts` の定数群に追加して安定参照する

## 5. 実装方式

- API: Route Handler `POST /api/review`（ストリーミングのため。`/api/chat` と同構成）
  1. Supabase 認証チェック（未認証401）→ proposal / session の所有確認（RLS越し取得で兼ねる）
  2. コンテキスト組み立て（§3.3）→ `resolveModel(supabase, persona.ai_capability)` → `streamText`
  3. 生成完了時（onEnd）に `review_feedbacks` 行を保存（verdict パース込み）。セッションがなければ実行前に Server Action で作成
- Server Actions（`lib/actions/projects.ts` / `lib/actions/review.ts`）: プロジェクトCRUD・企画書更新・ノート紐づけ・セッション作成・返答メモ保存・「企画を通す」確定。Zod＋AppError の既存パターン（`{ok, error}` 戻り値）
- プロンプト組み立ては `lib/ai/prompts.ts` に追加（掘り下げと並置）
- 定型テンプレ（企画書初期本文）はコード内定数（`lib/constants/proposal-template.ts` 等）
- **環境変数: `ANTHROPIC_API_KEY` の登録が新たに必須**（担当編集 = high 帯 = Anthropic claude-sonnet-5）。実装セッション冒頭で .env.local ＋ Vercel 本番環境に登録する（キーの用意・登録はユーザー実施。値の確認は `grep -c` のみ）
- 色はテーマ用CSS変数のみ（バッジ・パネル含む）

## 8. E2E検証手順（完了条件）

1. **プロジェクトCRUD**: 作成（必須/任意項目）→一覧表示→編集→削除（確認ダイアログ→配下の企画書・レビューも消滅をDBで確認）
2. **一括紐づけ**: 仮タイトルタグ付きノートを複数用意→プロジェクト作成時にタグ選択→候補一覧からチェックした分だけ proposal_notes に入る
3. **個別紐づけ**: 企画書ページで検索追加→解除。ごみ箱中のノートが一覧・レビュー入力から消え、復元で戻る
4. **企画書編集**: ジャンル/ターゲット層＋本文（初期テンプレ入り）を編集→自動保存→リロードで復元。Markdown往復はDB値で確認
5. **レビュー実行**: 「レビューを受ける」→ストリーミングでフィードバック文書が流れる→紐づけノートの内容を踏まえた指摘が含まれる→判定バッジが付く→proposals.status が in_review になる
6. **反復**: 指摘を受けて企画書を改稿＋返答メモ→再レビュー→「前回の指摘」への言及（改善確認）がある
7. **承認確定**: 承認判定→「企画を通す」→approved バッジ（企画書ページ・プロジェクトカード）→セッション completed
8. **承認後編集**: approved 後に本文を編集しても status が変わらない
9. **キー未設定エラー**: ANTHROPIC_API_KEY を外すと日本語エラーがパネルに出て落ちない
10. **RLS**: anon キーの REST SELECT が新規シード行含め拒否される（標準ペルソナ・プロファイルは認証済みユーザーのみ参照可）
11. **モバイル**: スマホ幅（375px）で 1〜8 の全操作が成立する（レビューパネル=ボトムシート）

※ マイグレーション（RLS・シード）と `/api/review`（認証・所有確認）は **security-reviewer 必須ゲート**の対象。
